Upgrading ​

This page states how EVO_AUTH versions change and what a change to the Convex component's tables may do to your data.

Versions ​

EVO_AUTH follows semantic versioning, starting at 0.1.0.

Before 1.0.0 a minor version may contain breaking changes. Every breaking change is listed under its version in CHANGELOG.md, with the steps to upgrade. Read the entries between the version you run and the version you are moving to before you upgrade.

The access-token verifier and @evo-auth/react ignore fields they do not know: a claim in an access token, and a field of publicConfig or of one of its provider entries. So you can deploy a newer server before the apps that read its tokens and its public config, and upgrade those apps afterwards.

What counts as breaking ​

Each of these is a breaking change, and a check finds it before a release rather than someone remembering it:

  • a Convex component table change that pnpm check:schema fails on (see below);
  • a new schema version of the standalone server's SQLite file: an earlier release refuses the file, so it breaks rolling back, not upgrading;
  • an export that is removed, or whose kind changes (a type that becomes a value, say), found by check:api;
  • a cookie whose name, name prefix, Path or SameSite changes;
  • a route that is removed or moved, or a method a route no longer takes;
  • an error code that is removed, or that answers with another HTTP status;
  • a setting that is removed, or whose default changes (the defaults are the ones in the configuration reference);
  • an environment variable that is removed, or that a role now requires;
  • a localization key or an admin string key that is removed or renamed;
  • a CSS custom property or class name that is removed from @evo-auth/react/styles.css;
  • an email template key, a webhook event name or an access-token claim that is removed.

A changed declaration of an export (a function's parameters, an option added to a type) is listed under its version either as a breaking change with upgrade steps, or under "Changed" marked "not breaking" when every existing use still compiles and behaves the same. Changing a default text's wording is not breaking; it goes under "Changed".

Rolling back ​

Every release's entry in CHANGELOG.md says whether you can roll back to the version before it, and how:

  • a new SQLite schema version: restore the .bak copy the migration made, then start the earlier release;
  • a Convex table that gained an optional field or a union member: change the rows that hold the new value first, since Convex refuses an older schema those rows do not fit.

What check:api enforces, and what it cannot see ​

check:api is part of node tests/acceptance/exports/check-exports.mjs. It reads, from the built packages, each entry point's exports with each one's kind and full declaration text (with the text of the declarations it names that the entry point does not export, such as an options type's helpers), and the wire surface, each part from the table it comes from: the cookie table and the route table in @evo-auth/core, the error codes, the settings and environment variables, the email template keys and the access-token claims, the localization and admin string keys and the stylesheet of @evo-auth/react, and the webhook event names of @evo-auth/server. It compares them with scripts/fixtures/api/released.json, the snapshot of the previous release, and fails on each change the CHANGELOG.md entry does not name as the rule above says. Additions pass.

It cannot see:

  • behaviour behind a declaration that did not change: a function that keeps its signature and does something else;
  • a type reached only through an inline import("...") in a declaration file;
  • the command line's flags: evo-auth and evo-auth-server parse their arguments in code, not from a table, so a removed or renamed flag is listed by hand.

The release script writes the new snapshots for the release commit, so the next release is compared with this one.

Changes to the component's tables ​

The Convex component keeps users, accounts, sessions, rate-limit counters, cleanup jobs and auth events in its own tables. A change to those tables is one of two things:

  • Backward compatible. New optional fields, new tables, new indexes, and a field whose union of allowed values gains members and loses none. Existing rows stay valid and need no migration.
  • Accompanied by a migration. Anything else ships with a migration, and the upgrade notes for that version describe it.

Backward compatible does not mean reversible. Once rows hold a new optional field or a new union value, Convex refuses an older schema that does not allow them, so rolling back to an earlier version needs those rows changed first.

A field is never removed or retyped in the same release that stops writing it. The release that stops writing a field keeps the field as it was, so rows written by the earlier release stay valid.

Email sign-in and passwords add two tables to the component, emailChallenges (the codes and links being waited for) and passwords (one hash for each user who has a password). New tables are backward compatible, so Convex needs no migration for them. Setting EVO_AUTH_PASSWORD_PEPPER is a step of its own: see Email and password.

Passkey sign-up adds no table. emailChallenges gains the purpose sign_up_passkey and three optional fields, verifiedAt, userHandle and noticedAt, and users gains the optional passkeyUserHandle. Those are backward compatible, so Convex needs no migration; once a row holds one of them, rolling back to an earlier version needs that row changed first.

Two-step sign-in adds two more, secondFactors (each user's authenticator secret, sealed, and the hashes of their backup codes) and signInChallenges (the pending sign-ins between a first factor and a second step). They are new tables too, so Convex needs no migration for them. Setting EVO_AUTH_SECOND_FACTOR_KEY is a step of its own, and only while secondFactor.enabled is on: see Two-step sign-in.

Usernames add no table. users gains the optional username and the index by_username, and the auth event's type gains the member username_changed. Those are backward compatible, so Convex needs no migration; once a row holds one of them, rolling back to an earlier version needs that row changed first. publicConfig gains usernames, which an older @evo-auth/react ignores, and GET /me gains user.username, which an older one ignores too.

Choosing a username at sign-up adds no table either. emailChallenges gains the optional pendingUsername, not indexed, and the component's completeEmailSignIn the optional argument usernames, absent read as false. Both are backward compatible, so Convex needs no migration, and the standalone server's schema version stays at 9: its challenge rows are stored whole, so the field needs no column. The answers of /email/verify and /email/verify-link can carry usernameTaken, which an older @evo-auth/react ignores; it then follows the redirect and the person adds a name from the profile.

Usernames for admins, apps and receivers add no table and leave the standalone server's schema version at 9. The component's changeUsername takes a changer, either the session or a user id with the acting admin, in place of its session arguments; the component and core are upgraded together, so nothing is left calling the old shape. The admin list and user answers gain username, which an older AdminPanel ignores. AuthApiUser and the webhook payload gain username: a receiver on an older @evo-auth/core keeps every other field, and one on this version reads a delivery without it as null.

The standalone server's SQLite file ​

The file of the standalone server holds its schema version, and each release reads one. evo-auth-server migrate, or the first start of a newer release, copies an older file to <file>.pre-v<N>-<timestamp>.bak and runs every step after its version in one transaction (see Upgrading the server). A file a newer release wrote is refused and left unchanged.

VersionAdds
1The first tables.
2The passkeys table.
3The organizations, memberships and invitations tables.
4The emailChallenges table and its indexes: the codes and links that email sign-in is waiting for.
5The passwords table and its indexes, and an index of emailChallenges by user.
6The secondFactors table and its indexes: each user's authenticator secret, sealed, and the hashes of their backup codes.
7The signInChallenges table and its indexes: the pending sign-ins between a first factor and a second step.
8No table change: passkey sign-up's fields are kept in the rows' data. The version moves so that an earlier release, which cannot read those rows, refuses the file.
9The username column of users, filled from the rows' data, and its unique index by_username.

A migration runs every step after the file's version. A file already at version 4 gets the steps for 5 to 9, and a file from before version 4 gets all of 4 to 9. This release reads version 9. A release that reads an earlier version refuses a migrated file, so to roll the server back, restore the .bak copy made before the migration.

What pnpm check:schema enforces ​

The check reads the tables from the built component and compares them with scripts/fixtures/schema/released.json, a snapshot of the tables of the previous release. Each table in the snapshot lists its fields, with each field's validator and whether it is optional, and its indexes.

It fails, naming the table and the field, when:

  • a table is gone;
  • a field is gone;
  • a field's validator changed, other than a union that gained members and lost none; a union that loses a member, or has one replaced, fails;
  • a field that was optional is now required;
  • a new field is required.

It passes when a table gains an optional field, a new table, or a new index, when a required field becomes optional, and when a union gains members and loses none. A union is compared member by member whatever its members are, so adding a type to a union of types passes in the same way as adding a literal. It compares tables only: it does not read CHANGELOG.md or the upgrade notes, and it does not run a migration.

The snapshot is refreshed when a release is cut: the release script writes the new one for the release commit, so the next release is compared with this one. Until the first release the snapshot holds the tables as they stand. A change that is meant to break compatibility needs its migration and upgrade notes before that release.
