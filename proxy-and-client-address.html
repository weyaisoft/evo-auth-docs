The proxy and the client address ​

This page is for anyone who mounts the auth proxy in an app server: a TanStack Start, Next, Hono, Bun, Deno or Node app that talks to a separate auth deployment, which is always the case with Convex. It says what the proxy does, what you must give it, and how to get the client's address on each host.

If your app server is the auth server itself (it runs the handler directly), read Handler mounts instead.

Why there is a proxy ​

The three session cookies must belong to your app's own site. Convex serves HTTP actions from another site, so a browser would treat the cookies as third-party. The fix is that your app server answers {basePath}/* itself and relays each request to the auth endpoints. publicUrl is the address the browser sees (your site plus basePath). target is where the proxy sends the request. They are different on purpose.

What you give it ​

ts
createAuthProxy(config, { target, clientAddress }, fromEnv(env, "proxy"), { logger });
ArgumentWhat it is
configThe object validateConfig returned. The proxy reads basePath, cookies.prefix and cookies.devMode from it, so they cannot drift from the auth side.
targetRequired. The origin of the auth endpoints: https, or http on a loopback host. It is never worked out from publicUrl. With Convex it is the deployment's HTTP actions origin (the .convex.site address).
clientAddressRequired, no default. A function (request, context) => string, or a promise of one. See below.
fromEnv(env, "proxy")The proxy-role secrets: EVO_AUTH_PROXY_SECRET. Without it the proxy refuses to start.
{ logger }Optional. It receives event names and reason codes only, never a header, cookie, address or secret.

The function it returns is (request, context) => Promise<Response>. It hands context to clientAddress untouched. Mount it on every method for {basePath}/*.

Set the same EVO_AUTH_PROXY_SECRET on the app server and on the auth deployment. With the secret set on the auth side, a request that did not come through the proxy is refused with proxy_refused.

What the proxy sends and keeps ​

  • The upstream URL is the origin of target plus the request's own path and query. The path must start with {basePath}/ after decoding. A path with a . or .. segment, %2f, %5c, a backslash or a doubled slash, {basePath} alone, or a path that does not decode gets a 404 and nothing is forwarded. A path is never rewritten.
  • Before forwarding it deletes Forwarded, every X-Forwarded-*, X-Real-IP, and any X-Evo-Client-IP and X-Evo-Proxy-Secret the client sent. It then sets its own X-Evo-Client-IP and X-Evo-Proxy-Secret.
  • Request headers pass through from a list of exactly twelve names, compared without regard to case: Cookie (cut down to the evo cookies), Authorization, Origin, Content-Type, Accept, User-Agent, Sec-Fetch-Dest, Sec-Fetch-Mode, Sec-Fetch-Site, Sec-Fetch-User, Sec-Purpose and Purpose. Every other header is dropped. The proxy sends nothing in place of a header the browser did not send. Sec-Purpose and Purpose carry the prefetch marker, so the handshake's own refusal of prefetches works behind the proxy.
  • Only Set-Cookie headers for the evo cookie names come back. Redirects are not followed (redirect: "manual").
  • If the runtime's fetch has already decoded a compressed upstream body, the proxy drops Content-Encoding and Content-Length. Otherwise it keeps both.
  • It logs event names only.

What clientAddress must return ​

One IPv4 or IPv6 literal, as text, and nothing else. The proxy refuses the request with proxy_refused (403), before any call upstream, when the result is not a single literal. These all count as not a literal: an empty string, a hostname, a list such as an X-Forwarded-For value, a bracketed address, an address with a port, an address with a zone id (%eth0) and an address with a prefix length (/64). A function that throws is refused the same way.

The address decides who shares a rate-limit bucket. The bucket key is a keyed hash of the address: an IPv4 address as it is, any other IPv6 address by its first 64 bits only. A wrong answer either merges every user into one bucket or trusts a value the client chose, so take the address from something the client cannot set: the socket, or a header that your platform's edge sets and overwrites.

Behind a platform load balancer the socket address is the balancer's. Every user then shares one per-address limit. On such a host, use the recipe your host's documentation gives for the real client address, not the socket recipe.

Recipes ​

Core exports the ClientAddress type and nothing host-specific, because a Fetch Request carries no peer address. Each host keeps the peer address somewhere else, so each recipe is documentation only.

Each recipe is marked verified (someone ran it, here the example app's tests) or unverified (it type-checks against the documented API, nobody has run it). Treat an unverified recipe as a starting point and test it on your host before you trust it. pnpm check:snippets compiles each marked block; it does not run it.

In every block below, config is the object validateConfig returned and secrets is fromEnv(env, "proxy"); replace those two lines with your own code.

TanStack Start: verified ​

The socket recipe is getRequestIP() from @tanstack/react-start/server, called with no options. It reads the request from Start's own request context, so it does not need the handler's context. Never call it with { xForwardedFor: true }: that reads a header the client controls. The example app's tests run this recipe. The TanStack Start guide shows the whole route.

ts
import { createAuthProxy, type AuthConfig, type ProxySecrets } from "@evo-auth/core";
import { getRequestIP } from "@tanstack/react-start/server";

// Replace these two lines with your own code: `config` is what validateConfig returned and `secrets` is
// fromEnv(env, "proxy").
declare const config: AuthConfig;
declare const secrets: ProxySecrets;

export const authProxy = createAuthProxy(
  config,
  { target: "https://your-deployment.convex.site", clientAddress: () => getRequestIP() ?? "" },
  secrets,
);

Returning "" when there is no address makes the proxy refuse the request instead of guessing.

Node: unverified ​

Node keeps the address on the socket of the incoming message. Pass that message as the context. The complete server is in Handler mounts; this block shows the part that differs.

ts
import { createServer, type IncomingMessage } from "node:http";
import { createAuthProxy, type AuthConfig, type ProxySecrets } from "@evo-auth/core";

// Replace these two lines with your own code: `config` is what validateConfig returned and `secrets` is
// fromEnv(env, "proxy").
declare const config: AuthConfig;
declare const secrets: ProxySecrets;

export const proxy = createAuthProxy(
  config,
  {
    target: "https://auth.example.com",
    clientAddress: (_request: Request, incoming: IncomingMessage) => incoming.socket.remoteAddress ?? "",
  },
  secrets,
);

// Build a Request from `incoming` as the Node mount does, then call proxy(request, incoming) and write the Response.
createServer((_incoming, outgoing) => {
  outgoing.writeHead(501).end();
}).listen(3000);

On a dual-stack socket Node may report an IPv4 client as an IPv4-mapped IPv6 literal such as ::ffff:192.0.2.1. The proxy accepts that form and counts it as the IPv4 address, so that client keeps its own bucket.

Bun: unverified ​

Bun.serve passes the server as the second argument of fetch. server.requestIP(request) states the connection address.

ts
import { createAuthProxy, type AuthConfig, type ProxySecrets } from "@evo-auth/core";

// Replace these two lines with your own code: `config` is what validateConfig returned and `secrets` is
// fromEnv(env, "proxy").
declare const config: AuthConfig;
declare const secrets: ProxySecrets;

interface PeerLookup {
  requestIP(request: Request): { readonly address: string } | null;
}

const proxy = createAuthProxy(
  config,
  {
    target: "https://auth.example.com",
    clientAddress: (request: Request, server: PeerLookup) => server.requestIP(request)?.address ?? "",
  },
  secrets,
);

Bun.serve({
  fetch(request, server) {
    if (!new URL(request.url).pathname.startsWith("/auth/")) return new Response("Not found", { status: 404 });
    return proxy(request, server);
  },
});

Deno: unverified ​

Deno.serve passes the connection information as the second argument of the handler.

ts
import { createAuthProxy, type AuthConfig, type ProxySecrets } from "@evo-auth/core";

// Replace these two lines with your own code: `config` is what validateConfig returned and `secrets` is
// fromEnv(env, "proxy").
declare const config: AuthConfig;
declare const secrets: ProxySecrets;

interface ConnectionInfo {
  readonly remoteAddr: { readonly hostname: string };
}

const proxy = createAuthProxy(
  config,
  {
    target: "https://auth.example.com",
    clientAddress: (_request: Request, info: ConnectionInfo) => info.remoteAddr.hostname,
  },
  secrets,
);

Deno.serve((request, info) => {
  if (!new URL(request.url).pathname.startsWith("/auth/")) return new Response("Not found", { status: 404 });
  return proxy(request, info);
});

Hono: unverified ​

Hono reports the connection address through its connection-information helper. The one import confirmed here is @hono/node-server/conninfo, for Node. On another runtime, import getConnInfo from that runtime's adapter; Hono's conninfo helper page lists them. No other path is printed here, because a path that was right for one version of Hono may be wrong for yours.

remote.address is optional in Hono's type, so the recipe falls back to "", which the proxy refuses.

ts
import { Hono, type Context } from "hono";
import { getConnInfo } from "@hono/node-server/conninfo";
import { createAuthProxy, type AuthConfig, type ProxySecrets } from "@evo-auth/core";

// Replace these two lines with your own code: `config` is what validateConfig returned and `secrets` is
// fromEnv(env, "proxy").
declare const config: AuthConfig;
declare const secrets: ProxySecrets;

const proxy = createAuthProxy(
  config,
  {
    target: "https://auth.example.com",
    clientAddress: (_request: Request, context: Context) => getConnInfo(context).remote.address ?? "",
  },
  secrets,
);

const app = new Hono();
app.all("/auth/*", (context) => proxy(context.req.raw, context));

export default app;

Next.js: its own guide ​

Next.js has a package of its own, @evo-auth/nextjs, which mounts this proxy for you, and its client-address recipes are in the Next.js guide: a header your edge overwrites, or the example's custom server. Bare next start gives no trustworthy address.

Checks that exist ​

The example apps' tests prove, for the TanStack Start recipe and for the Next.js custom server (examples/nextjs-server/test/client-address.test.ts), that the address the auth side sees is the socket address and that a forged X-Forwarded-For does not change it. The other recipes have no such test.
