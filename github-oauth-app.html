Register a GitHub OAuth app ​

This page is for whoever sets up sign-in with GitHub for an EVO_AUTH app. It ends with the client id and secret in the right places.

Turn wildcard redirect matching off. Register the exact callback URL below and nothing broader: no wildcard, no pattern, no list of alternatives. What GitHub does when the redirect_uri in a sign-in request differs from the one in the token exchange is unverified. Wildcard matching on the OAuth app is the real risk, and the only fix is to leave it off. PKCE does not close the gap, because an attacker can build an authorize request with no code_challenge.

One app for each environment ​

How many callback URLs one GitHub OAuth app accepts is unverified here. Make a separate OAuth app for each environment: local development, staging and production. Each has its own client id, its own secret and its own callback URL.

Steps ​

  1. Work out the callback URL. It is {publicUrl}/github/callback: your publicUrl (your site's origin plus basePath) followed by /github/callback. For the example app on your own machine it is http://localhost:3000/auth/github/callback. For production it is something like https://app.example.com/auth/github/callback. pnpm exec evo-auth check prints it in its Deployment section, built from your config: Register this callback URL with GitHub: <callback URL>. Copy it as printed.

  2. Create the app on GitHub. Open your GitHub settings, go to Developer settings, then OAuth Apps, then New OAuth App. Give it a name your users will recognise.

  3. Fill in the form. Put your site's address in Homepage URL, for example https://app.example.com. Put the exact callback URL from step 1 in Authorization callback URL. Leave any option that allows more than one callback, a wildcard or a pattern turned off.

  4. Copy the client id. GitHub shows it on the app's page.

  5. Make a client secret on the same page and copy it at once. GitHub shows it once.

  6. Put the two values in the environment. They are variables, never in the config file:

    VariableValue
    EVO_AUTH_GITHUB_CLIENT_IDthe client id
    EVO_AUTH_GITHUB_CLIENT_SECRETthe client secret

    Set them where the auth endpoints run. On Convex that is the deployment: npx convex env set NAME, with the value on standard input and not as an argument. See the Convex guide. For a local env file, add them to .env.local, which must stay out of git. Both are required once the github() provider is enabled, and a variable that is set but empty is refused.

  7. Check. Run pnpm exec evo-auth check. Its Environment section names the two variables as a problem when neither is set (are not set, and the config enables github), and never prints a value. A variable that is set but empty is refused.

What the sign-in asks GitHub for ​

The sign-in uses the authorization code flow with a state value and PKCE. It requests no scope, so it reads the public profile only: the numeric id, login, name and avatar. It does not ask for the email address. The GitHub access token is thrown away after the profile is read and is never stored.

If sign-in fails ​

A sign-in that cannot finish answers oauth_failed and the browser returns to your sign-in page with error=oauth_failed. Check that the callback URL on GitHub matches the one evo-auth check prints, character for character, and that the id and secret belong to the app for this environment. See Troubleshooting.
