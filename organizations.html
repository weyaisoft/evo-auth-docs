Organisations in React ​

This page is for a developer using organisations from @evo-auth/react: the two hooks, the five components, the admin page's Organisations section and their strings. Organisations are groups of your app's users, each member with a role. The server side is in Configuration, the organisation routes and the security model.

Turning them on ​

Set organizations.enabled, organizations.roles and organizations.invitationUrl in the server's config. publicConfig(config) then carries organizations: { enabled, roles }, each role as { key, label }. The labels are what the components show, so they are public; the roles' permissions are not sent. While enabled is false, or with a server too old to send the field, every hook below loads nothing and every component renders nothing.

A role the server holds that roles does not list is shown by its key.

Try it in the example ​

examples/tanstack-convex runs with organisations on and the default roles: Admin, who may do everything, and Member, who may see the members. Signed in, its header has the switcher and links to two pages, Organisation (OrganizationProfile) and Settings, a note for the organisation's managers behind <Protect permission="org:profile:manage">. Links open /accept-invitation, the page with AcceptInvitation. Signed out, none of this shows.

You need two GitHub accounts, one per person, each in its own browser or private window.

  1. Start the example. In examples/tanstack-convex, run pnpm convex:dev and pnpm dev with the variables in Variables set, then open http://localhost:3000. To see the steps on the admin page as well, put the first person's user id (Profile shows it under the name) in admins.userIds in shared/auth-config.ts.
  2. Sign in as two people, one in each window.
  3. Create. The first person opens the switcher in the header, chooses Create organisation, and gives it a name. It becomes active, and Settings shows the note form.
  4. Invite. From the switcher, Manage opens the Organisation page. Under Invitations, Create invitation and then Create link make a link. It is shown once. Copy it.
  5. Accept. The second person opens the link, sees the organisation and the role, and chooses Accept invitation. They are a Member now. Settings tells them only managers see it.
  6. Change a role. Under Members, the first person sets the second person's role to Admin. After a refresh, the second person's Settings shows the note.
  7. Remove. The first person chooses Remove on the second person's row. After a refresh, the second person's Settings and the organisation in their switcher are gone.

Either person can choose Personal in the switcher at any point, and the home page and Settings follow.

The settings page shows how to guard your own data. <Protect> hides the form from anyone whose role lacks the permission. convex/settings.ts checks the same permission with requireMembership on every read and write, because anyone can call a Convex function directly. The example's onInvitationCreated is an internal action that runs after the invitation is stored. It sends nothing and neither logs nor stores the link. When the inviter types an address on the invitation form, Evo Auth itself sends the link through the app's email.sender, which in the example is the development mailbox; an app with a real sender gets the same message from its mail service. It never passes the link to ctx.scheduler, because scheduled functions keep their arguments.

What the browser cases prove ​

tests/acceptance/app/organizations.spec.ts and organizations-refusals.spec.ts run the example against the local Convex backend in Chromium, Firefox and WebKit, headless, with two people in separate browser contexts. They prove that:

  • an organisation created from the switcher becomes active in the switcher, on the home page and in the access token's o claim;
  • a link copied from the Organisation page lets the second person join with the invitation's role, and the token leaves the address bar as soon as the page reads it;
  • a Member does not see the settings, and after the first person makes them Admin and they refresh, they do;
  • each person can switch to Personal and back, and the pages and the token follow;
  • after removal the second person sees no settings and has nothing to switch to;
  • after each step the admin page's Organisations section shows the member count and each member's role;
  • the settings query, run on the deployment as each person, refuses whoever the page hides the form from;
  • a slug someone else already took is refused under the slug field, and nothing is created;
  • an invitation link opened a second time says "This invitation link doesn't work".

They do not cover real GitHub sign-in, because a fake provider stands in for it, or sending an invitation by email, which the browser cases do not exercise. Leaving, revoking an invitation, editing or deleting an organisation, and the admin page's own actions are covered by the React package's unit tests, not by these cases.

Hooks ​

useOrganization() ​

The active organisation: the one the session chose, carried in the access token. It reads GET {basePath}/organizations/detail for it.

FieldMeaning
isLoadedtrue once the detail has answered. While signed out, with organisations off or with none active, it follows the provider's isLoaded.
organization{ id, name, slug, imageUrl, createdAt, memberCount }, or null when none is active, before it loads or when it failed.
roleThe user's role key in it: the token's at first, then the server's. null when none is active.
permissionsThe permissions the role gives now, as the server listed them. Empty until loaded.
has(permission)true only when the server listed that permission.
reload()Reads the detail again. The same function on every render.

useOrganizationList() ​

The user's own organisations, from GET {basePath}/organizations.

FieldMeaning
isLoaded, failedisLoaded is true once the list has answered, with data or not; failed is true when it answered without data.
organizationsOldest membership first, each { id, name, slug, imageUrl, memberCount, role }.
canCreateWhether the server lets this user create an organisation.
reload()Reads the list again.
setActive(organizationId)Makes that organisation active for the session, or none with null. The new access token replaces the held one in every tab.
create({ name, slug, imageUrl? })Creates an organisation with the user as its first member, in organizations.creatorRole. It does not make it active.

setActive and create resolve { ok: true, value } or { ok: false, error } and never reject. error is one of the refusals below, or not_found, reverification_required, rate_limited or refused (any other answer, or none).

The organisation's page ​

What the person may do comes from the permissions the server lists for their role now, never from the role's name:

  • Members lists everyone with their join date and role. With org:memberships:manage, each row has a role menu and Remove, except the person's own row. Anyone can leave.
  • Invitations, with org:invitations:manage: the open invitations with their role, who made them and when they expire, each with Revoke, and Create invitation, which takes a role and an expiry of 1, 7, 14 or 30 days and, while publicConfig says emailDelivery: true (the server has an email.sender), an optional address. With an address the server also emails the link there; the address is for delivery only and plays no part in who may accept. The new link is shown once either way, with a copy control, and kept nowhere: not in storage, not in an address, not in a log.
  • Settings: the name, slug and image with org:profile:manage, and Delete with org:profile:delete.

A person whose role holds none of these sees the members read-only and can leave.

Deleting needs a recent confirmation of identity. With a passkey this browser can use, the person confirms in place. Otherwise the browser goes to the provider and back. Before it leaves, the page keeps the user's id, the organisation's id, a random nonce and an expiry ten minutes on in this tab's sessionStorage, under evo-auth:organization-pending, and the address back carries only evo_reverified=organization-{nonce}. The delete confirmation reopens only when that nonce matches the entry this tab stored, the entry has not expired and it is the signed-in user's. Nothing is sent until the person confirms once more, and a link someone else made is a plain visit.

Accepting an invitation ​

AcceptInvitation reads evo_invitation from the page's address on its first render in the browser and removes it at once, so the token stays out of the address bar, the history and later Referer headers. From then on the token travels only in request bodies: POST {basePath}/invitations/preview shows the organisation's name and the role, and POST {basePath}/invitations/accept joins.

A visitor who is signed out sees the invitation and the sign-in card, which brings them back to this page. To find the token after sign-in, the component keeps it in this tab's sessionStorage under evo-auth:invitation, with an expiry, and deletes it once the invitation is accepted, turns out not to work, or is replaced by another link. After accepting, the organisation becomes active and the browser goes to afterAcceptUrl.

A link that is missing, expired, revoked or used says "This invitation link doesn't work", as does one whose creator can no longer grant its role: a member who has since been removed, demoted below it or to a role that cannot invite, banned or deleted, or an app admin taken off admins.userIds. Someone who is already a member is told so, with a Continue button.

The admin page ​

While organisations are on, AdminPanel adds an Organisations section beside Users and Events:

  • the organisations in creation order, 100 a page, with next and previous;
  • one organisation's members with their join date, its open invitations, its details and its public metadata (read-only);
  • Add member, by user id with a role; a role menu and Remove on each member; Create invitation, with the same optional address while emailDelivery is true, and Revoke; and Delete organisation;
  • on a user's page, the organisations they belong to, with their role and Remove.

The admin may act on any organisation whatever their own role in it, and may give any role. The server still keeps the last-manager rule, and the panel says so in a sentence when a change is refused for it. Delete asks for a recent confirmation with the provider, as banning a user does: the page keeps the admin's id, the organisation's id and a nonce in this tab's sessionStorage under evo-auth:admin-organization-pending, and the address back carries only evo_reverified=admin-org-{nonce}.

The admin page's own strings are in packages/react/src/admin/strings.ts, for example adminOrganizationsSection (Organisations), addMemberTitle (Add a user to {name}) and organizationLastManager (This would leave nobody who can manage members. Give another member that role first.).
