Next.js guide ​

This page is for a developer adding Evo Auth to a Next.js App Router app that signs people in on the standalone server, @evo-auth/server. The working reference is examples/nextjs-server/: its files are the ones on this page, with more pages around them, and its browser tests are what back the claims here.

A Next.js app on Convex is its own section, with the reference examples/nextjs-convex/.

You need Next.js 16.4 or later with the App Router, the Node runtime, and the server package set up as in the server guide. @evo-auth/nextjs asks for next ^16.4.0, react ^19.0.0, @evo-auth/core and @evo-auth/react; it was built and measured on Next.js 16.4.6.

The files ​

The shared config ​

ts
import { github, validateConfig } from "@evo-auth/core";

// publicUrl is the app's own origin plus /auth: the browser only ever talks to the app. devMode gives the cookies names
// a browser accepts on http://localhost; leave it out in production.
export const authConfig = validateConfig({
  publicUrl: "http://localhost:3000/auth",
  cookies: { devMode: true },
  providers: [github()],
});

The client address ​

For a first run on your own machine, use the custom-server recipe from the client address: copy its server.mjs and run the app with node server.mjs --dev instead of next dev. The server overwrites X-Forwarded-For with the socket's address on every request, and this module reads it. The other recipe, a header your edge overwrites, is for deployment: on a bare localhost nothing sets that header, so the address is empty and every /auth request is refused with proxy_refused.

ts
// The custom server overwrites X-Forwarded-For with the socket's address before Next.js sees the request: the whole
// header, which holds exactly one address, read with no split.
export function clientAddress(request: Request): string {
  return request.headers.get("x-forwarded-for") ?? "";
}

The auth module ​

createEvoAuth validates the config and the options when the module loads. It reads the secrets from the environment the first time a request needs them, so next build needs none: EVO_AUTH_PUBLIC_KEYS for reading sessions, EVO_AUTH_PROXY_SECRET for relaying. import "server-only" makes the build refuse any client module that imports it.

ts
import "server-only";

import { createEvoAuth } from "@evo-auth/nextjs";

import { authConfig } from "./auth-config";
import { clientAddress } from "./client-address";

// target is the server package's origin, which only the app reaches.
export const evo = createEvoAuth(authConfig, { target: "http://127.0.0.1:3011", clientAddress });

The proxy file ​

ts
import { evo } from "./lib/auth";

export const proxy = evo.proxy;

export const config = {
  matcher: [
    {
      source: "/((?!auth(?:/|$)|_next/static|_next/image|favicon.ico).*)",
      missing: [
        { type: "header", key: "next-router-prefetch" },
        { type: "header", key: "purpose", value: "prefetch" },
      ],
    },
  ],
};

Next.js reads config.matcher from the file's text when it builds, so the matcher must be this literal: not built from a variable, and not imported. It sends every page request through the proxy and leaves out:

  • the auth route itself: auth in the pattern is your config's base path, the path of publicUrl without its leading slash. If your publicUrl ends in /api/auth, the pattern starts /((?!api/auth(?:/|$)|. The proxy also leaves that path alone if a request reaches it.
  • Next.js's static files and the favicon;
  • prefetches (the two missing entries). A prefetch never runs the handshake, and its answer may be cached and shown later.

The proxy answers an expired session on a page load with the handshake: one 307 to /auth/handshake, which refreshes the session and comes back. It works the same during a client-side navigation: Next.js follows the redirect inside its payload fetch, and AuthRefresh takes the loop-guard marker out of the address afterwards.

The auth route ​

ts
import { evo } from "../../../lib/auth";

export const { GET, HEAD, POST, PUT, PATCH, DELETE, OPTIONS } = evo.routeHandlers;

It exports no runtime or dynamic. A route handler already runs on Node and for each request, and with cacheComponents on, Next.js refuses both exports.

The root layout ​

getAuth() reads the session once per request, however many server components ask. AuthRefresh keeps the server-rendered page in step with the browser: when another tab signs in as someone else it reloads; when the session ends some other way than this tab's own Sign out (another tab, a revoked session, Sign out everywhere) it reloads a hidden tab and refreshes a visible one, so the server components render signed out; it does nothing while this tab's own Sign out is on its way to afterSignOutUrl.

tsx
import "@evo-auth/react/styles.css";

import { publicConfig } from "@evo-auth/core";
import { AuthProvider, AuthRefresh } from "@evo-auth/nextjs/client";
import type { ReactNode } from "react";

import { evo } from "../lib/auth";
import { authConfig } from "../lib/auth-config";

export default async function RootLayout({ children }: { readonly children: ReactNode }): Promise<ReactNode> {
  const auth = await evo.getAuth();
  const browserConfig = publicConfig(authConfig);
  return (
    <html lang="en">
      <body>
        <AuthProvider initialState={auth} publicConfig={browserConfig}>
          <AuthRefresh publicConfig={browserConfig} />
          {children}
        </AuthProvider>
      </body>
    </html>
  );
}

With cacheComponents. create-next-app turns cacheComponents on in next.config.ts, and Next.js then wants each page to have a static shell it can prerender, with request data read inside <Suspense>. Three things change:

  • Add export const instant = false; to this layout. It reads the session for every request, so every page is rendered for its request, and the line tells Next.js that is intended. Don't move the read behind <Suspense> to get a static shell instead: the proxy gives each page a fresh nonce in its Content-Security-Policy, and a shell prerendered at build time has none, so the browser would block its scripts. Leave the line out without cacheComponents: Next.js then refuses it.
  • Add the same line to a page that calls requireAuth() at its top level, such as the protected page below, so its redirect stays a real 307.
  • Read a page's searchParams in a child component inside <Suspense>, as the sign-in and sign-up pages evo-auth init --stack writes do.

getAuth() waits for Next.js's connection() before it reads, so the session is read only for a real request, never into a prerendered or prefetched page. For the same reason, don't call it inside a 'use cache: private' function: Next.js refuses connection() there.

A protected page ​

requireAuth() returns the signed-in session. Signed out, it sends the browser to the sign-in page with redirect set to this page; with an expired token, through the handshake once.

tsx
import { SignedIn } from "@evo-auth/nextjs/client";
import type { ReactNode } from "react";

import { evo } from "../../lib/auth";
import { ExportButton } from "./export-button";

export default async function ProtectedPage(): Promise<ReactNode> {
  const auth = await evo.requireAuth();
  return (
    <SignedIn>
      <h1>Protected</h1>
      <p>Signed in as {auth.user.name}.</p>
      <ExportButton />
    </SignedIn>
  );
}

A page that requireAuth() protects doesn't need RedirectToSignIn: the server already sends a signed-out visitor away. SignedIn hides the page at once when the session ends in place, and AuthRefresh's refresh then sends the browser to sign in.

The admin page ​

List the user ids of your admins in admins.userIds in the shared config, restart the Evo Auth server, and render AdminPanel from @evo-auth/nextjs/admin. That entry is a client module, so a server page can use it; @evo-auth/react/admin is not, and a server page cannot import it.

tsx
import { AdminPanel } from "@evo-auth/nextjs/admin";
import type { ReactNode } from "react";

export default function AdminPage(): ReactNode {
  return <AdminPanel />;
}

The page needs no requireAuth(): the server checks every admin call, and the panel shows only "Not available" to anyone who is signed out or not listed, so a redirect would add nothing.

A server action and its caller ​

Next.js replaces the message of an error a server action throws in production, so requireAuthForAction() never throws or redirects: it answers { ok: false, error: "unauthenticated" } when the session cookie is missing or expired. useFreshSession calls the action, and on that answer refreshes the token once and calls it once more.

ts
"use server";

import { evo } from "../../lib/auth";

export async function whoAmI(): Promise<{ readonly ok: true; readonly name: string } | { readonly ok: false; readonly error: "unauthenticated" }> {
  const session = await evo.requireAuthForAction();
  if (!session.ok) return session;
  return { ok: true, name: session.auth.user.name };
}
tsx
"use client";

import { useFreshSession } from "@evo-auth/nextjs/client";
import { type ReactNode, useState } from "react";

import { whoAmI } from "./actions";

export function ExportButton(): ReactNode {
  const call = useFreshSession(whoAmI);
  const [answer, setAnswer] = useState("");
  const run = async (): Promise<void> => {
    const result = await call();
    setAnswer(result.ok ? `The server says: ${result.name}` : "Signed out.");
  };
  return (
    <p>
      <button type="button" onClick={() => void run()}>
        Ask the server
      </button>{" "}
      {answer}
    </p>
  );
}

The server's settings ​

The server package reads evo-auth.server.mjs in the folder it is started in. The settings live beside the app's own TypeScript, so the server uses the same config object as the app:

ts
import { authConfig } from "../lib/auth-config";

export const config = authConfig;

// The loopback address only: the app is the one client.
export const listen = { host: "127.0.0.1", port: 3011 } as const;
js
// evo-auth.server.mjs
import { mkdirSync } from "node:fs";

import "./server/resolve-ts.mjs";

mkdirSync(new URL("data", import.meta.url), { recursive: true });
const { config, listen } = await import("./server/settings.ts");

export default { config, database: { path: "data/evo-auth.sqlite" }, listen };

Node runs the TypeScript itself, but the app's imports have no extension, as Next.js writes them: copy server/resolve-ts.mjs from the example, a resolve hook that retries such an import as .ts. The server's secrets go in its own environment; the server guide lists them, and examples/nextjs-server/README.md shows the commands that make them. The app's environment needs EVO_AUTH_PUBLIC_KEYS and EVO_AUTH_PROXY_SECRET, the same values as the server's.

Next.js with Convex ​

This section is for an app whose auth side is Convex, set up as in the Convex guide, in place of the standalone server. The working reference is examples/nextjs-convex/, which runs against the local Convex backend on 127.0.0.1, with no Convex account. Every file above is the same except the ones named here: there is no Evo Auth server and no server/settings.ts, and the example has a convex/ folder, the app of the Convex guide, whose HTTP actions are the auth endpoints.

Two addresses, two variables. A Convex deployment has an API address, which the browser's Convex client uses, and an HTTP actions address, which serves the auth endpoints. The app's /auth route relays to the second. NEXT_PUBLIC_CONVEX_URL is the first and CONVEX_SITE_URL the second; each is an origin, https or http on a loopback host. Never derive the relay target from publicUrl. Next.js writes NEXT_PUBLIC_CONVEX_URL into the build, so a build needs it. CONVEX_SITE_URL is read when lib/auth.ts (under the Content-Security-Policy, below) loads, which next build does when it collects page data, so a build needs that too; neither is a secret. EVO_AUTH_PUBLIC_KEYS and EVO_AUTH_PROXY_SECRET are read on first use as before.

checkedOrigin (lib/env.ts in the example) refuses a value that is not an origin on https or on a loopback host, naming the variable and never its value:

ts
// lib/env.ts
const LOOPBACK_V4 = /^127\.\d{1,3}\.\d{1,3}\.\d{1,3}$/;

function isLoopback(hostname: string): boolean {
  return hostname === "localhost" || hostname === "[::1]" || LOOPBACK_V4.test(hostname);
}

/** value as an origin, or a thrown error naming the variable. */
export function checkedOrigin(name: string, value: string | undefined): string {
  if (value === undefined || value === "") throw new Error(`${name} is not set`);
  let url: URL;
  try {
    url = new URL(value);
  } catch {
    throw new Error(`${name} is not a URL`);
  }
  const allowed = url.protocol === "https:" || (url.protocol === "http:" && isLoopback(url.hostname));
  if (!allowed || url.origin !== value) {
    throw new Error(`${name} must be an origin with nothing after it: https, or http on a loopback host`);
  }
  return value;
}

Both bundlers resolve the modules' relative imports without an extension, which is how the example writes them.

The provider. ConvexProviderWithEvoAuth and the Convex client are browser code, so they live in a client component that the server layout renders inside AuthProvider:

tsx
// components/convex-provider.tsx
"use client";

import { ConvexProviderWithEvoAuth } from "@evo-auth/react/convex";
import { ConvexReactClient } from "convex/react";
import type { ReactNode } from "react";

import { checkedOrigin } from "../lib/env";

// The variable is named in full so that Next.js can write its value into the build.
const convex = new ConvexReactClient(checkedOrigin("NEXT_PUBLIC_CONVEX_URL", process.env.NEXT_PUBLIC_CONVEX_URL));

export function ConvexClientProvider({ children }: { readonly children: ReactNode }): ReactNode {
  return <ConvexProviderWithEvoAuth client={convex}>{children}</ConvexProviderWithEvoAuth>;
}
tsx
// app/layout.tsx: the layout above, with the provider inside AuthProvider.
<AuthProvider initialState={auth} publicConfig={browserConfig}>
  <ConvexClientProvider>
    <AuthRefresh publicConfig={browserConfig} />
    {children}
  </ConvexClientProvider>
</AuthProvider>

A client component then reads Convex with useQuery, skipped until useConvexAuth() says Convex has accepted the token. The example's protected page does it with whoami, a query that answers getEvoIdentity(ctx, authConfig): the page shows who the app server says you are, from requireAuth(), and below it who Convex says you are, from the same token.

The Content-Security-Policy. The policy the proxy makes allows connect-src 'self' alone, and the Convex client also sends requests and opens a WebSocket to the deployment. lib/auth.ts passes the deployment's two origins to createEvoAuth in policy.connectSrc, and proxy.ts stays export const proxy = evo.proxy; with the matcher above:

ts
// lib/auth.ts for Convex: the target is the deployment's HTTP actions origin, and the page policy names the deployment.
import "server-only";

import { createEvoAuth } from "@evo-auth/nextjs";

import { authConfig } from "../shared/auth-config";
import { clientAddress } from "./client-address";
import { convexOrigins } from "./csp";
import { checkedOrigin } from "./env";

export const evo = createEvoAuth(authConfig, {
  target: checkedOrigin("CONVEX_SITE_URL", process.env.CONVEX_SITE_URL),
  clientAddress,
  policy: { connectSrc: convexOrigins(process.env.NEXT_PUBLIC_CONVEX_URL) },
});
ts
// lib/csp.ts
import { checkedOrigin } from "./env";

/** The deployment's http(s) origin, as the browser's Convex client names it, and its ws(s) origin. */
export function convexOrigins(convexUrl: string | undefined): readonly [string, string] {
  const http = checkedOrigin("NEXT_PUBLIC_CONVEX_URL", convexUrl);
  const url = new URL(http);
  return [http, `${url.protocol === "https:" ? "wss:" : "ws:"}//${url.host}`];
}

Each connectSrc entry must be one exact http, https, ws or wss origin as new URL(...).origin writes it (lower case, no default port, no path, no user), and createEvoAuth throws a TypeError naming the entry's position for anything else, wildcards, keywords such as 'self' and scheme-only sources included, so a bad source fails next build and start-up. The package puts the same policy on the request, where Next.js reads the nonce, and on the response, each source after 'self' and every other directive unchanged.

Don't edit the Content-Security-Policy header in proxy.ts; pass the origins to createEvoAuth.

Server actions. A server action is not a Convex function: it reads the session with requireAuthForAction() and is called through useFreshSession, exactly as above, on Convex too. A Convex query or mutation checks the identity of the token the browser's client sends, with getEvoIdentity and requireMembership, as the Convex guide shows; the app's two checks of one token are independent, so a function that needs the person must make its own.

The development mailbox. The example's sender (convex/devMailbox.ts) keeps each message in a table of the deployment and the /mailbox page reads it live. It works only on a local backend, in the development cookie mode, and the page answers not found in a production build. An app that sends real email gives email.sender its own action.

The client address ​

The auth endpoints rate-limit sign-in, email codes and resets by the client's address, so clientAddress must return an address a client cannot choose. No recipe here reads a forwarded-for header a client can set, and none takes the leftmost X-Forwarded-For entry: that entry is whatever the client sent, and a new forged value per request would put every request in a fresh rate-limit bucket.

  1. Behind a proxy or a hosting platform: read a header the edge overwrites on every request (for nginx, proxy_set_header X-Real-IP $remote_addr;), or the entry a proxy you run appended to X-Forwarded-For, counted from the right. Never derive it from a header a client can send unchanged through your edge. This is the recipe for a deployment:
ts
// lib/client-address.ts behind an edge: the address your edge vouches for. nginx's `proxy_set_header X-Real-IP
// $remote_addr;` overwrites X-Real-IP with the peer's address on every request. On a hosting platform, read the header
// the host documents as overwritten.
export function clientAddress(request: Request): string {
  return request.headers.get("x-real-ip") ?? "";
}
  1. With nothing in front of the app: run Next.js behind a custom server that overwrites X-Forwarded-For with the socket's address before Next.js sees the request, and read the whole header with no split, as lib/client-address.ts above does. This is what the example does, in production and in development, and what a first run on your own machine uses:
js
// server.mjs: `node server.mjs` instead of `next start`, `node server.mjs --dev` instead of `next dev`.
import { createServer } from "node:http";

import next from "next";

const dev = process.argv.includes("--dev");
process.env.NODE_ENV ??= dev ? "development" : "production";
const app = next({ dev, hostname: "localhost", port: 3000 });
await app.prepare();
const handle = app.getRequestHandler();
createServer((req, res) => {
  req.headers["x-forwarded-for"] = req.socket.remoteAddress ?? "";
  return handle(req, res);
}).listen(3000, "127.0.0.1");

Copied behind a real proxy, the second recipe puts every client in one bucket, which is too strict but cannot be got round.

Bare next start gives no trustworthy address. Next.js 16.4.6 fills X-Forwarded-For only when the request has none (node_modules/next/dist/server/base-server.js, line 604: req.headers['x-forwarded-for'] ??= …socket.remoteAddress), so it keeps whatever a client sent. Measured on 16.4.6: under bare next start, a forged single address reached the route handler and was taken as the client's; a forged list of two was refused by the proxy with 403, since it is not one address. Behind the custom server, the auth side was given the socket's address whatever the client sent; the example's unit tests and a browser case check that.

What was measured and what was not: the custom server and bare next start were measured on 16.4.6. The first recipe, a real reverse proxy, hosted platforms, and whether common hosts overwrite X-Forwarded-For were not.

Request headers the proxy sets ​

On every request it handles, the proxy overwrites three request headers before your server components see them: x-evo-url (the request's path and query), x-nonce (this response's nonce) and content-security-policy. A value a client sent under those names never survives. They are trusted only as that: x-evo-url as a path and query, used to send the browser back to the page it asked for, and x-nonce for the requester's own response. Never treat either as an origin or as anything about another request.

The nonce and static pages ​

The proxy gives every response a fresh nonce and a Content-Security-Policy that allows scripts carrying it (evo.nonce() reads it in a server component). Next.js puts the nonce on the inline scripts it renders, which needs the page rendered per request. The layout above reads the session, so every page is rendered per request. A page you want built once as a static page cannot carry a per-response nonce: leave it out of the matcher, and serve it with a fixed policy of your own from headers() in next.config.js. An app that calls another origin from the browser lists it in policy.connectSrc, as the Convex section does.

Development notes ​

  • The handshake may run twice under next dev. The development server can send the handshake request twice for one expired page. Both are answered with fresh cookies: the second is a match within the refresh grace, recorded as refresh_grace_reuse in the auth events, not a reuse, and the page lands signed in. A production build sends it once.
  • Next.js's telemetry. Next.js sends anonymous usage data unless it is turned off. Either set NEXT_TELEMETRY_DISABLED=1 in the environment of every next command, or run next telemetry disable once. The example's scripts set the variable; @evo-auth/nextjs never sets it for your app.

Troubleshooting ​

  • Every /auth request is refused with proxy_refused: the client address is empty. Check which client-address recipe is in use: the edge recipe reads a header that nothing sets when no edge stands in front of the app, as on a bare localhost.

What stays out ​

  • The Pages Router: a different data model (getServerSideProps). The App Router has been Next.js's default since 13.
  • Next.js 15: the file is middleware.ts there, and its Node runtime was stable only from 15.5. A 15 recipe can be added if asked.
  • The Edge runtime: the rest of Evo Auth is tested on Node.
  • Calling the auth side directly, without /auth/* on the app: the cookies would become third-party.
  • Partial Prerendering with the nonce policy: Next.js's CSP guide calls them incompatible.
  • React Router: its framework mode has loaders, actions and middleware with different cookie and redirect rules, so it is separate work.

What the tests prove, and what they do not ​

The browser cases of nextjs-signin.spec.ts, nextjs-session.spec.ts and nextjs-actions.spec.ts run against both examples, the standalone server's and the Convex one (examples/nextjs-convex, on the local Convex backend); the server-action cases show that an action called after the token expired answers unauthenticated as data, that useFreshSession refreshes once and calls once more and never loops, and what Next.js sends the client for that answer in a production build. The example's browser cases (tests/acceptance/app/nextjs-signin.spec.ts and nextjs-session.spec.ts) are written for Chromium, Firefox and WebKit: Sign out landing on afterSignOutUrl, sign-in by password, passkey, provider and with the second step, reverification, an expired token on a full load and during a client-side navigation, a server action after expiry, sign-out in another tab with Back, a click racing the provider's own refresh, the handshake under the development server, a forged X-Forwarded-For, a prefetch kept out of the proxy, and the client entry in each of six ways of running the app (next dev and next dev --webpack, next start on each bundler's build, and the custom server in production and in development). A hidden tab in those cases is simulated; a really hidden tab is checked by hand, in a browser on a VM's desktop, because Playwright leaves a background tab visible in every engine.

Not measured: a real reverse proxy and hosted platforms (the first client-address recipe), whether common hosts overwrite X-Forwarded-For, Partial Prerendering, the Edge runtime, how Turbopack treats export * in a client entry (the package names every export instead), and whether vercel/next.js issue 75904 is fixed in 16.
