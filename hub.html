The shared sign-in server ​

A shared sign-in server (a "hub") is one Evo Auth deployment that your other Evo Auth apps sign in through. The hub holds the sign-in provider registrations (a GitHub OAuth app, later a Google one), and each app lists the hub as its provider with one line of config. A person signs in to the hub once; every other app that uses the hub then signs them in without asking GitHub again.

Use one when you run several apps of your own and want one place to register sign-in providers and one account per person across them. You do not need one for a single app: an app with its own github() works as before.

The hub is a small OpenID Connect provider. An app sends the person to the hub, the hub sends back a one-time code, and the app's server swaps the code for an id_token that says who the person is. The app then makes its own user, session and cookies, exactly as it does for GitHub. Nothing of the hub's session reaches the app, and no cookie is shared between sites.

Running a hub ​

A hub is an ordinary Evo Auth app (the same Start app and Convex deployment as in the TanStack Start guide) with hub mode switched on. Three settings make it one:

ts
import { github, validateConfig } from "@evo-auth/core";

export default validateConfig({
  publicUrl: "https://auth.example.com/auth",
  appId: "my-hub",
  providers: [github()],
  hub: { enabled: true, allowedClients: ["https://*.example.com/auth/evo/callback", "http://localhost/auth/evo/callback"] },
});
  • hub.enabled: true switches hub mode on. Three routes appear under basePath: GET /oidc/authorize, where an app sends the person; POST /oidc/token, which the app's server calls; and GET /.well-known/openid-configuration, the discovery document. The hub's existing /.well-known/jwks.json publishes the key that signs its id_tokens. With hub mode off these paths do not exist.
  • appId must be a name, such as my-hub, and never a URL origin. It is the audience of the hub's own access tokens; the id_tokens the hub gives apps carry the app's origin instead, and keeping appId off every origin stops the two kinds of token from ever being mistaken for each other. The hub refuses to start with an origin as its appId.
  • hub.allowedClients is the list of sites that may sign in through the hub. It is empty by default, which refuses every site. See the next section.

A hub may list more than one sign-in provider; a person then picks one on the hub's sign-in page (below). The host of publicUrl must not end in a dot.

The hub's pages must never be shown inside another site's frame. Its three routes send Content-Security-Policy: frame-ancestors 'none' themselves, and the hub's own pages need the same: the example app's policy (src/lib/csp.server.ts) already sends frame-ancestors 'none' on every page, so a hub built from the example has it. Keep that directive if you change the policy.

Set the hub's variables as for any app (Variables), including its provider's client id and secret. Register the provider's callback URL for the hub, such as https://auth.example.com/auth/github/callback; the apps register nothing.

The sites that may use the hub ​

An app's client id is its own origin (scheme, host and port), it has no client secret, and it must use PKCE. The hub lists each app by the exact callback address it sends the app's code to: the app's publicUrl followed by /{provider id}/callback, which for an app using evoHub() with its default id is {publicUrl}/evo/callback, such as https://notes.example.org/auth/evo/callback. evo-auth check on the app prints it. The entries of hub.allowedClients are each one of:

  • an exact callback address, such as https://notes.example.org/auth/evo/callback, written as a browser writes it back (lower-case host, no default port, a path, no query, fragment or dot at the end of the host). It must be https unless its host is localhost or 127.0.0.1, where a port may be written, such as http://localhost:3000/auth/evo/callback;
  • http://localhost/<path> or http://127.0.0.1/<path> with no port, which match that host on any port with that exact path, for apps you run on your own machine;
  • a wildcard address over the hub's own parent domain only: for a hub at https://auth.example.com, https://*.example.com/auth/evo/callback matches https://notes.example.com/auth/evo/callback and https://todo.example.com/auth/evo/callback, but not https://example.com or https://a.b.example.com, and not another path. A wildcard over any other domain (https://*.com/..., https://*.co.uk/..., https://*.convex.site/...) stops the hub from starting.

An entry that is an origin alone, such as https://notes.example.org, stops the hub from starting with a message naming the form needed. The hub sends a code only to a redirect_uri that equals a matching entry exactly, character for character, with a wildcard's host or a loopback entry's port taken from the app's origin: another path on the same site, an added query, a trailing slash, a default port written out or the same path spelled another way (letter case, percent-encoding, . segments) is refused on the refused-site page. So a page on an allowed site that leaks its own address cannot be made to receive a signed-in person's code.

Whatever the list says, the hub never accepts its own origin as a client, nor a client whose host ends in a dot.

Use a wildcard only for a domain you own. The rule cannot tell a domain you own from a shared hosting name. A hub at https://my-hub.vercel.app has the parent vercel.app, so it may list https://*.vercel.app/auth/evo/callback, and then every app anyone hosts on vercel.app can sign people in through your hub and receive who they are. A hub at https://myhub.co.uk listing https://*.co.uk/auth/evo/callback is the same case. If your hub runs on a hosting provider's name, list each app by its exact callback address. evo-auth check prints a warning for every wildcard, naming the domain it covers.

A sign-in request from a site the list does not name is refused on the hub's refused-site page, with the error code invalid_request. The person stays on the hub, the page quotes nothing of the request, and nothing is sent back to the site that asked.

The hub's sign-in page ​

A person who arrives from an app with no session at the hub signs in at the hub first. With one way in the hub sends them straight to it. With more than one, the hub shows its own sign-in page: "Sign in to continue to", the requesting site's origin (such as https://notes.example.com, or http://localhost:3000 marked "This computer"), one button per provider in the order of providers, and a Cancel link. A person already signed in to the hub never sees it: the app gets a code at once.

With passkeys.enabled on the hub, a passkey counts as a way in, so the page shows even for a hub with one provider, and it ends with "Sign in with a passkey". That link opens the hub's own signInUrl with the app's sign-in request as its redirect, the same value the provider buttons carry. The hub's sign-in page (SignIn from the React package) runs the passkey sign-in there and returns to that address, where the hub checks the request again from the start and sends the app its code. This is how someone whose only way in is a passkey signs in to an app through the hub. The link appears only when signInUrl is a page on the hub's own origin.

The page names only the site's origin, the one the hub checked against hub.allowedClients in the same request. It shows no name, logo or text the site sent, because a site could send anything there; the origin is the one thing about the site the hub has verified. There is no consent screen: only the sites you list can use the hub.

Cancel returns the person to the app's callback with error=access_denied and the app's state, and no session is made. A request the hub refuses before it has checked the site (a site not on the list, a malformed client_id or redirect_uri, or a redirect_uri that is not exactly a callback address listed for the site) shows the refused-site page instead, in the same look, with the error code invalid_request, no button and no link back. Any other mistake in the request goes back to the site with error=invalid_request, except a request object: a request that carries request goes back with error=request_not_supported, and one that carries request_uri with error=request_uri_not_supported. The hub never reads either value and never fetches a request_uri.

The hub asks for a fresh sign-in when the request has prompt=login, max_age=0, or a max_age smaller than the whole seconds since the person last signed in at the hub (the time the id_token gives as auth_time). An app that asks with prompt=none never sees the page: a person with no hub session, or one who would need to sign in again, max_age included, sends the app error=login_required. With a fresh sign-in asked for and no hub session, the page shows and any sign-in on it, passkey included, satisfies the request: the address the buttons return to leaves out prompt and max_age, so the person is not asked again. With a fresh sign-in asked for and a hub session, the hub sends the person to the provider of their primary account, the one they linked first, shows no page and never offers another provider. A fresh sign-in at any provider linked to the same user satisfies the rerun, as it would on a first sign-in, so a rerun completed through another linked provider is only as fresh as that provider can make it (an oauth2() provider cannot force a new login). Nothing becomes weaker: the person still needs that user's hub session in that browser, and could reach the same provider on a first sign-in. A person with two-step sign-in is the exception (see Two-step sign-in at the hub).

A person with no account at any provider the hub lists (one who signs in only with a passkey, or whose accounts are all at providers since removed) confirms with their passkey instead, when passkeys.enabled is on. The hub sends them to its signInUrl with intent=reverify and the same redirect. The hub's sign-in page asks for their passkey and returns to that address, where the hub issues the code, with auth_time set to when they confirmed. If they cancel, or come back without confirming, the app receives error=login_required; the hub does not send them to the sign-in page a second time. With passkeys off such a person is refused on the hub with oauth_failed, as before.

The hub's sign-in page needs no wiring for either link: SignIn reads redirect and intent from the page's own address after it loads. It takes redirect only as a single relative path the redirect rule accepts, and ignores anything else, an absolute address included, as if it were not there. After a passkey sign-in it goes to that path with a full page load. With intent=reverify it never signs anyone in: for a signed-in person it shows "Confirm it's you", asks the browser for their passkey at once, and goes back when that succeeds; if they cancel the browser's prompt, or the hub refuses the passkey, it stays with "Try again" and "Cancel", and Cancel goes back unconfirmed, so the app receives login_required. With nobody signed in it goes back at once and the hub decides again. The page must render SignIn while someone is signed in, not only inside SignedOut: the example's src/routes/sign-in.tsx does, and hides its own signed-in text while intent=reverify is in the address.

The core library renders both pages as plain HTML with no script. They are sent with a policy that allows nothing but their own stylesheet and their icon, which is written into the page: default-src 'none', the stylesheet's hash, img-src data:, base-uri 'none', form-action 'none' and frame-ancestors 'none'.

Pointing an app at the hub ​

One line, and no provider variable:

ts
import { evoHub, validateConfig } from "@evo-auth/core";

export default validateConfig({
  publicUrl: "https://notes.example.com/auth",
  providers: [evoHub({ url: "https://auth.example.com/auth" })],
});

url is the hub's publicUrl: its origin followed by its basePath. The button reads "Sign in with Evo"; pass label to change it. For a new app, evo-auth init --hub https://auth.example.com/auth writes this config, and an .env.example with no provider variable. In an app, evo-auth check compares the hub's discovery document with what evoHub() expects, prints the exact callback address the hub must list in hub.allowedClients (here https://notes.example.com/auth/evo/callback), and says no client secret is needed. A hub that does not answer is reported as a problem. More detail: evoHub().

Browsers keep cookies by host, not by port, so two apps on one host and different ports (such as localhost:3000 and localhost:3002) share cookies: give each its own cookies.prefix.

What an app receives about a person ​

The id_token tells the app:

  • sub, the hub's id for the person. It is the same in every app, so the app's account for the hub has that id as its providerUserId.
  • name, preferred_username, picture, and email with email_verified, from the hub's user and the account they first signed in with. preferred_username is the person's username on the hub when they hold one and the hub has usernames.enabled on, and otherwise that account's login.

The app stores these as it stores any provider's profile. They are for display: the app finds its user by the hub's id, never by email.

Moving existing users over ​

An app's existing users are keyed by the provider they signed in with, so a person's first sign-in through the hub makes a new user in the app, even if an existing user has the same email. Nothing links users by email.

To keep their user, a person links the hub account to it:

  1. List the hub beside the app's own provider, so the sign-in page shows both buttons: providers: [evoHub({ url }), github()].
  2. The person signs in the old way, opens their profile (UserProfile) and connects the Evo account. The hub signs them in if needed and the app links its account to their user.
  3. From then on either button signs them in as the same user. Once everyone who needs it has linked, you can remove the old provider from the config.

Fallback ​

Fallback is configuration only. An app either runs on its own with its own providers, or lists evoHub() beside one of its own, which shows two buttons. If the hub stops, the app's own button still signs people in.

What a person sees when the hub is down depends on when it stops. If the hub cannot be reached when they click its button, the browser cannot open the hub's page, because the button sends the browser straight to the hub: most browsers show their own error page, and some stay on the sign-in page; if the hub stops after it has sent them back to the app, the app's sign-in page shows "Sign-in did not finish" (oauth_failed). In both cases no session is made, and they can use the app's own button.

There is no automatic failover, no health check, no switching providers while running, no copy of the hub's users in the app, and no syncing users between the hub and an app.

Two-step sign-in at the hub ​

The hub and each app are separate deployments, and each applies its own secondFactor setting to its own sign-ins:

  • At the hub, the hub's setting decides. A person who signs in there with a password, an emailed code or a provider meets the hub's second step, if it applies to them, on the hub's own sign-in page. The hub issues its code to the app only after that step. The app does nothing and sees nothing of it.
  • At the app, the app's setting decides. A sign-in through evoHub() is a first factor like any provider's, so an app with secondFactor on asks for its own second step after it.
  • An app that relies on the hub's second step should leave its own secondFactor off. Otherwise the person is asked twice.
  • A passkey sign-in at the hub is a first factor with no second step, as anywhere.

Signing in again is a fresh sign-in for a person with two-step sign-in. A prompt=login, a max_age=0 or a max_age older than the person's last sign-in at the hub normally reruns the sign-in at the person's provider. For a person with a confirmed authenticator a provider rerun alone would skip the second factor they turned on. So the hub sends them to a fresh sign-in at the hub instead, with its own second step, and the app receives a code with a newer auth_time. The way back carries no prompt or max_age, so it does not loop. A request with prompt=none still gets login_required. See Two-step sign-in.

Signing out, bans and deletion ​

  • Signing out of an app ends only that app's session.
  • Signing out on the hub ends only the hub's session. Every app stays signed in; nothing tells an app. The next sign-in through the hub asks the hub's provider again.
  • A code the hub issued just before a hub sign-out can still be used by the app for up to 60 seconds. Codes are single use and bound to the app's PKCE secret.
  • A person banned on the hub cannot sign in to any app through the hub. Their sessions in apps they are already signed in to are not ended; ban them in each app too if they must lose access now.

What this version does not do ​

  • Per-app subjects: every app receives the same sub for a person.
  • Back-channel logout: signing out on the hub does not sign anyone out of an app.
  • Propagated deletion: deleting a user on the hub does not delete them in any app.
  • A consent screen: only the sites you list can use the hub.
  • Certification. The hub is a small OpenID provider for your own apps, not a certified one. It was run against the OpenID Foundation's conformance suite, test plan oidcc-test-plan (code flow, public client, static client, discovery), and departs from OpenID Connect Core 1.0 in these known ways:
    • id_tokens are signed with ES256 only. Core section 15.1 requires RS256.
    • nonce is required on every request. Core section 3.1.2.1 makes it optional in the code flow.
    • There is no user-info endpoint. Core section 5.4 returns the profile and email claims from it when an access token is issued; the hub puts name and preferred_username in every id_token, with picture, email and email_verified when it has them, and its access token opens nothing.
    • There is no refresh token. Core section 12 and RFC 6749 section 1.5 make one optional; an app signs in through the hub again instead.
    • The scopes are openid, profile and email only. Core section 5.4 also defines address and phone.
    • There is no acr claim, and acr_values is ignored. Core section 15.1 asks a provider to support acr_values.
    • Request objects (request and request_uri) are not supported, and the discovery document says so (request_parameter_supported and request_uri_parameter_supported are both false).

The hub's security properties (single-use codes, the checks at the token endpoint, the limits on refused requests) are in Security model.
