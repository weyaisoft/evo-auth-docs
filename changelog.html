Changelog ​

All notable changes to this project are listed here, in the form of Keep a Changelog. The project follows semantic versioning from 0.1.0. Before 1.0.0 a minor version may contain breaking changes, and each one is listed under its version with the steps to upgrade.

[Unreleased] ​

[0.1.1] - 2026-11-22 ​

Added ​

  • A documentation address: each package's homepage and the links at the end of its README now point to the docs site at https://weyaisoft.github.io/evo-auth-docs/, so the npm pages link the guides and the changelog.

Changed ​

  • The README, docs/server.md and the three quickstarts install from the npm registry (@evo-auth/*@0.1.1) and no longer say Evo Auth is not on npm or must be installed from tarballs. evo-auth init already printed the registry install line; --from still prints the tarball form.
  • The docs site builds for the path of the documentation address (/evo-auth-docs/), so pnpm --filter site build needs no --base flag.

No breaking changes.

[0.1.0] - 2026-11-17 ​

Added ​

The first release has six packages, all at 0.1.0 and all under the MIT licence.

  • @evo-auth/core: the sign-in protocol (GitHub sign-in, sessions with rotating refresh tokens, short-lived signed access tokens), the cryptography, the configuration and its validation, and the evo-auth command line (init, keys generate, keys rotate, keys activate, check). It has no runtime dependency and uses only Web-standard globals.
  • @evo-auth/convex: a Convex component named evoauth that stores users, accounts, sessions, rate-limit counters and auth events, with registerRoutes, createAuthApi, authConfigProvider and getEvoIdentity for the app that installs it.
  • @evo-auth/react: AuthProvider, the useAuth, useUser and useSessions hooks, the signed-in and signed-out controls, and the SignIn, UserButton and UserProfile components, with a stylesheet.
  • @evo-auth/nextjs: the Next.js App Router integration for @evo-auth/core and @evo-auth/react: createEvoAuth with its server, ./client and ./admin entry points.
  • @evo-auth/react-router: the React Router framework-mode integration for @evo-auth/core and @evo-auth/react, with its ./client entry point.
  • @evo-auth/server: Evo Auth without Convex, on one Node process (>=26.3 <27) and one SQLite file. It is a storage adapter that passes core's contract suite, schema versions with migrate and a copy beside the file before a migration, stored jobs with a lease so that one server runs per file, createServer (its handler, start(), listen() and close()), and the evo-auth-server command (start, migrate, backup, check, users ban|unban|delete, webhooks failed|redeliver). evo-auth init --server writes its options file. The guide is docs/server.md.
  • Signed webhooks for an app whose database is elsewhere: user.created, user.updated and user.deleted in the Standard Webhooks format, delivered at least once with retries and written in the same transaction as the change. verifyWebhook and WebhookError in @evo-auth/core check a delivery in any backend.
  • A second example app, examples/tanstack-server: TanStack Start on the server, with its own users table fed by webhooks.
  • Replacing EVO_AUTH_SECOND_FACTOR_KEY without anyone setting two-step sign-in up again: EVO_AUTH_SECOND_FACTOR_KEY_PREVIOUS holds the old key while authenticator and backup codes open under either key, each step a person passes moves them to the new key, and a reseal moves everyone else: evo-auth-server second-factor reseal on the standalone server, and the app's own action from createSecondFactorReseal on Convex (resealSecondFactors in core). evo-auth check and evo-auth-server check warn while the previous key is set. Backup codes are stored as seals of each code's SHA-256 under the second-factor key, so they move with it. See Rotating secrets.
  • devConsoleSender() in @evo-auth/core, the development sender evo-auth init --stack sets: it prints each message's code and link in the auth side's terminal instead of sending it. validateConfig refuses it without cookies.devMode, and each send is refused, logged as email.send_failed, unless the host says the auth side is local: evo-auth-server once listen() has bound a loopback address, and the Convex adapter when the deployment's CONVEX_CLOUD_URL is on a loopback host. A host says so through the optional localAuthSide member of auth.handler's and auth.sendEmailChallenge's context, and a sender reads it from its second argument.
