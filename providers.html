Sign-in providers ​

A provider is the object in providers that knows how to talk to one sign-in service. github() makes one for GitHub. oauth2() makes one from configuration for any service that speaks OAuth 2 with PKCE and has a user-info endpoint: see oauth2(). oidc() makes one for any OpenID Connect service, and checks the signed id_token it returns: see oidc(). google() makes one for Google: see google(). Ten more named providers are listed in The twelve named providers. evoHub() makes one for the shared sign-in server, an EVO_AUTH deployment that several of your apps sign in through: see evoHub(). For anything else you can write your own and list it beside them. This page says what the object holds, what EVO_AUTH does around it, and where its client id and secret go.

oauth2() ​

oauth2() takes the service's three endpoints and a map from its user-info answer to the profile, and needs no code of yours.

ts
import { oauth2, validateConfig } from "@evo-auth/core";

export const acme = oauth2({
  id: "acme",
  label: "Acme",
  authorizationEndpoint: "https://id.acme.example/oauth/authorize",
  tokenEndpoint: "https://id.acme.example/oauth/token",
  userinfoEndpoint: "https://id.acme.example/oauth/userinfo",
  scopes: ["profile"],
  profile: { providerUserId: "sub", login: "preferred_username", name: "name", avatarUrl: "picture" },
});

export default validateConfig({
  publicUrl: "https://app.example.com/auth",
  providers: [acme],
});

Set its two variables, EVO_AUTH_ACME_CLIENT_ID and EVO_AUTH_ACME_CLIENT_SECRET, where the auth endpoints run (see The client id and secret), and register https://app.example.com/auth/acme/callback with the service.

OptionRequiredWhat it is
idyesSee The id.
labelyesThe text on the sign-in button.
authorizationEndpoint, tokenEndpoint, userinfoEndpointyesThe service's three URLs, written out. Nothing is looked up at run time.
scopesnoA list of scope names, sent joined by spaces. Default: none, and then no scope parameter is sent.
tokenAuthnoHow the client id and secret reach the token endpoint: "client_secret_basic" (the default), in an HTTP Basic header, or "client_secret_post", in the request body. Only that one way is used.
profileyesWhere each profile field is in the user-info answer.
authorizationParamsnoFixed extra parameters for every authorize request, as names to text, such as { permissions: "0" }. See Extra authorize parameters.

Each field of profile is a claim path: names joined by dots, such as sub or data.user.id, each name a letter or _ followed by letters, digits or _. providerUserId is required. Its claim may be text of 1 to 255 characters, used as it is, or a whole number, written as decimal text; anything else ends the sign-in with oauth_failed. login, name, avatarUrl, email and emailVerified are optional, and a claim that is missing, empty or not text is left out. emailVerified counts only when its claim is the boolean true; the text "true", 1 and anything else are false. It must be a claim path: emailVerified: true, a promise that every email is verified, is refused.

login, name and avatarUrl can instead be built from several claims with a template, { template: "..." }, in which each {claim.path} is replaced by that claim. A service that gives an avatar as an id and a hash needs this:

ts
import { oauth2 } from "@evo-auth/core";

export const chat = oauth2({
  id: "chat",
  label: "Chat",
  authorizationEndpoint: "https://chat.example/oauth2/authorize",
  tokenEndpoint: "https://chat.example/api/oauth2/token",
  userinfoEndpoint: "https://chat.example/api/users/@me",
  scopes: ["identify"],
  tokenAuth: "client_secret_post",
  profile: {
    providerUserId: "id",
    login: "username",
    name: "global_name",
    avatarUrl: { template: "https://cdn.chat.example/avatars/{id}/{avatar}.png" },
  },
});

A claim counts when it is non-empty text or a whole number. When any claim the template names is missing, the field is left out, so a user with no avatar gets none rather than a broken address. In avatarUrl each value is percent-encoded, so a value holding / or ? stays one piece of the address; in login and name it goes in as it is. A template must hold at least one {claim.path}, no other brace and no control character, and be at most 512 characters. providerUserId, email and emailVerified are always single claims: an account id or an email is never put together.

Email is display data only. EVO_AUTH stores it on the account and shows the primary account's email as the user's, and no sign-in, link or deduplication reads it: a user is found by the provider's id and providerUserId alone, so two provider accounts that give the same verified email are two users. An email longer than 254 characters, or holding a control character, is dropped and the sign-in goes on without it.

oauth2() checks its options when it is called, and throws a TypeError that names the option and never its value for:

  • an id outside the id grammar, or an empty label or one with a control character;
  • an endpoint that is not an absolute https: URL, or http: on a loopback host (localhost, 127.0.0.0/8 or [::1]), or one with a user name, password, query string or fragment;
  • a scope that is empty or holds a space, a quote or a backslash;
  • a claim path that is not names joined by dots, such as a..b, or no providerUserId path;
  • a template that breaks the rule above, or a template for providerUserId, email or emailVerified;
  • an extra authorize parameter that breaks its rule;
  • a tokenAuth other than the two above, or an option that does not exist.

A loopback http: endpoint is for local development: validateConfig refuses it unless cookies.devMode is on.

The authorize request carries response_type=code, client_id, redirect_uri, the scopes, state and the S256 code challenge. The token request is a form POST with grant_type=authorization_code, the code, redirect_uri and the code verifier, and accepts only a JSON answer with an access_token and a token_type of bearer. The user-info request is a GET with that token. Every request refuses redirects and is cut off after 10 seconds, and any failure, of the service or of the network, ends the sign-in with oauth_failed and nothing the service said.

oauth2() sends no reauthentication prompt. Plain OAuth 2 has no standard parameter that makes the user sign in again, so when a user confirms who they are before a sensitive action, a service that remembers them sends them straight back. That reverification proves the user still controls their session at the service, not that they signed in again just now. See the security model.

oidc() ​

oidc() takes an OpenID Connect service's issuer and endpoints, written out. The account id is always the sub of the id_token the service signs, and nothing else.

ts
import { oidc, validateConfig } from "@evo-auth/core";

export const acme = oidc({
  id: "acme",
  label: "Acme ID",
  issuer: "https://id.acme.example",
  authorizationEndpoint: "https://id.acme.example/oauth/authorize",
  tokenEndpoint: "https://id.acme.example/oauth/token",
  jwksUri: "https://id.acme.example/oauth/jwks",
  userinfoEndpoint: "https://id.acme.example/oauth/userinfo",
});

export default validateConfig({
  publicUrl: "https://app.example.com/auth",
  providers: [acme],
});

As with oauth2(), set EVO_AUTH_ACME_CLIENT_ID and EVO_AUTH_ACME_CLIENT_SECRET where the auth endpoints run, and register https://app.example.com/auth/acme/callback with the service. The values to copy are in the service's discovery document, at {issuer}/.well-known/openid-configuration; evo-auth check reads that document and tells you when the config differs from it (see below).

OptionRequiredWhat it is
idyesSee The id.
labelyesThe text on the sign-in button.
issueryesThe issuer exactly as the service writes it in its id_tokens' iss.
authorizationEndpoint, tokenEndpoint, jwksUriyesThe service's URLs. Nothing is looked up at run time.
userinfoEndpointnoWhen set, the profile is read from it as well, and its fields win over the id_token's.
scopesnoA list of scope names, sent joined by spaces. It must include openid. Default: openid, profile and email.
profilenoWhere login, name, avatarUrl, email and emailVerified are read, as claim paths. Defaults: preferred_username, name, picture, email and email_verified.
tokenAuthnoHow the client id and secret reach the token endpoint: "basic", the default, in an HTTP Basic header (client_secret_basic), or "post", in the request body (client_secret_post), for a service that takes only that. Only that one way is used.
authorizationParamsnoFixed extra parameters for every authorize request, as names to text, such as a claims request. See Extra authorize parameters.

oidc() checks its options when it is called, as oauth2() does, and throws a TypeError that names the option and never its value. It also refuses a scopes list without openid, a profile entry for providerUserId, which is always sub, and emailVerified: true in place of a claim path. It refuses a tokenAuth other than "basic" or "post", and in particular tokenAuth: "none", a token exchange without a client secret: only evoHub() makes a provider that exchanges that way, and only with the shared sign-in server.

Extra authorize parameters ​

Some services need a parameter on the authorize request that EVO_AUTH does not send itself, such as a claims request asking for the email in the id_token. authorizationParams adds fixed ones, the same on every sign-in:

ts
import { oidc } from "@evo-auth/core";

export const stream = oidc({
  id: "stream",
  label: "Stream",
  issuer: "https://id.stream.example",
  authorizationEndpoint: "https://id.stream.example/oauth2/authorize",
  tokenEndpoint: "https://id.stream.example/oauth2/token",
  jwksUri: "https://id.stream.example/oauth2/keys",
  tokenAuth: "post",
  authorizationParams: { claims: JSON.stringify({ id_token: { email: null, email_verified: null } }) },
});

Each name is a letter followed by letters, digits, _, . or -, at most 64 characters, and each value is non-empty text of at most 2,048 characters with no control character. A parameter EVO_AUTH sets or rules on itself is refused, whatever its letter case, so an extra one can only add to the request: response_type, client_id, redirect_uri, scope, state, code_challenge, code_challenge_method, nonce, prompt, max_age, hd and response_mode. request and request_uri are refused too, because a request object's values would take the place of the state, the redirect and the PKCE challenge. oauth2() takes the same option with the same rule.

The authorize request is the one oauth2() sends, plus a nonce: 32 random bytes EVO_AUTH makes for each sign-in and seals in the sign-in cookie beside the state. The token answer must carry an id_token, and EVO_AUTH checks it before it reads anything in it: the algorithm (RS256 or ES256 only), the signature against the service's JWKS (fetched at every sign-in, never kept), the issuer, the audience, the times and the nonce. The security model lists every check. Any failure ends the sign-in with oauth_failed, no session and nothing the token or the service said. When userinfoEndpoint is set, its sub must equal the id_token's. The email and its verified flag are read from the same answer: the user-info answer when it has an email, the id_token otherwise. As with oauth2(), the email is display data only and never finds or links a user.

When a user confirms who they are before a sensitive action, oidc() sends prompt=login and max_age=0. If the id_token carries auth_time, it must be no earlier than the moment the confirmation started, less clockSkewSeconds, or the confirmation is refused. A service may leave auth_time out. Then the round trip proves that the user still controls their session at the service, as with oauth2(), not that they signed in again just now.

What evo-auth check compares ​

For each oidc() provider, evo-auth check reads {issuer}/.well-known/openid-configuration and compares its issuer, authorization_endpoint, token_endpoint, jwks_uri and, when you set one, userinfo_endpoint with your config. Each one that differs or is missing is a problem that names the member and your option. A token_endpoint_auth_methods_supported list that does not include client_secret_basic is a problem too, because sign-in through oidc() cannot work with that service; a document without the list passes, since client_secret_basic is the default. With tokenAuth: "post" the list must be there and include client_secret_post. A document that cannot be read is a problem. A provider made by oidc() whose settings evo-auth check cannot read, which happens when your config imports another copy of @evo-auth/core than the one running the command, is a problem too: check names it and says its discovery document was not compared. A provider you wrote yourself is not compared and not reported, whatever its kind, and neither is an oidc() provider whose fetchProfile you replaced, because check then treats it as your own. For microsoft(), whose document gives the issuer as https://login.microsoftonline.com/{tenantid}/v2.0 or with one tenant's id in it, check accepts either form. An evoHub() provider is compared the same way; what differs for it is under evoHub(). See the command line.

What a named provider can add ​

A named provider made inside EVO_AUTH, such as google(), is oidc() with its service's settings written out, plus rules only such a provider can set. They are not options of oidc(), because each one either accepts something a plain oidc() refuses or runs code at sign-in, and each is written for one service's documented behaviour. Beside Google's (a second issuer form, its account chooser and its hosted-domain check), there are four:

  • An issuer with the tenant put in. The id_token's iss may also equal a template with one of the token's own claims put in, such as https://login.microsoftonline.com/{tid}/v2.0 with the token's tid. The claim counts only when it is 1 to 128 letters, digits, _ or -, so it cannot change the address around it. Every other id_token check is unchanged.
  • A client secret made for each sign-in. The secret sent to the token endpoint is computed when the code is exchanged, from the provider's credentials and the current time, such as a short-lived JWT signed with ES256. It is sent the way the provider's tokenAuth says and is never kept.
  • An answer by form POST. The authorize request asks for response_mode=form_post, and the service's page then sends the browser back with a POST to the callback instead of a GET. For such a provider only, EVO_AUTH answers POST {basePath}/{id}/callback with a 303 to the GET callback carrying the posted code and state, and the GET callback does everything it does for any other provider: it checks the state against the sign-in cookie, exchanges the code with the PKCE verifier and checks the id_token and its nonce. The POST reads no cookie and changes nothing stored, so a POST another site makes leads only to that GET, which is refused unless the state is the one sealed in the browser's own sign-in cookie. It is the one POST that does not need an allowed Origin, because the service's page is on the service's origin. Every other provider's callback stays GET only.
  • A name from the posted user field. Some services send the user's name only once, in a user field beside the code. The POST callback seals that field, with the provider and the posted state, into a cookie of its own (__Host-evo_formuser with the default prefix) that lasts 60 seconds. The GET callback uses it only when its provider and state are those of the sign-in it completes, takes from it only a display name and only when the id_token gave none, and clears it whatever happens. The field is not signed, so nothing else is read from it.

Your own provider object can do the second and the fourth in its own code. exchangeCode gets the current time as nowSeconds, and fetchProfile's context carries the posted field as postedUser, but only a provider made inside EVO_AUTH with the form POST rule gets the POST callback that fills it.

google() ​

google() signs people in with their Google account. It is an oidc() provider with Google's settings written out, so every id_token check of oidc() applies.

ts
import { github, google, validateConfig } from "@evo-auth/core";

export default validateConfig({
  publicUrl: "https://app.example.com/auth",
  providers: [github(), google()],
});

To get a client id and secret, open the Google Cloud console, choose a project, and under Google Auth Platform set up the consent screen (the app name and a support address). Then under Clients create an OAuth client of type Web application, and add https://app.example.com/auth/google/callback (your publicUrl followed by /google/callback) as an authorized redirect URI. Put the client id in EVO_AUTH_GOOGLE_CLIENT_ID and the secret in EVO_AUTH_GOOGLE_CLIENT_SECRET where the auth endpoints run (see The client id and secret). Google requires the secret even though the sign-in also uses PKCE. List google() in the config itself rather than only when its client id is set: on Convex, a config that reads the variable to decide is refused at push when the variable is not set (see Convex). In examples/tanstack-convex, shared/providers.ts says how to add it.

The id is google and the button reads Google. The issuer is https://accounts.google.com, and the authorize, token and JWKS addresses are the ones in Google's discovery document; nothing is looked up at run time, and evo-auth check compares them with that document as for any oidc() provider. The scopes are openid, profile and email, and the profile comes from the id_token, with no user-info request. It differs from a plain oidc() provider in four ways:

  • Reverification asks which account, not for a fresh login. Google does not offer prompt=login or max_age, so a reverification sends prompt=select_account, as github() does, whatever selectAccount says. It confirms which Google account the user holds; it does not make them sign in to Google again. Passkey reverification is the strong one.
  • Two issuer forms. Google writes iss as https://accounts.google.com or accounts.google.com, and both are accepted. A provider made with oidc() accepts only its issuer.
  • The login is the email. Google sends no preferred_username, so the account's login is its email address. Like every login it is shown, never used to find or link a user.
  • hostedDomain, to admit one organisation. google({ hostedDomain: "example.com" }) sends hd=example.com, which only steers Google's account chooser, and refuses with oauth_failed any id_token whose hd claim is not exactly example.com, a missing one included. Google sets hd only for accounts of a Google Workspace or Cloud organisation. The email's domain is never read for this: a personal account can carry any address.

google() takes hostedDomain and selectAccount (see Which account) and nothing else, and throws a TypeError naming the option, never its value, for any other option, for a hostedDomain that is not a domain name in lower case, or for a selectAccount that is not true or false.

More named providers ​

Six more providers are built the same way as google(): each is oidc() with its service's issuer and endpoints written out, nothing is looked up at run time, and evo-auth check compares them with the service's discovery document. Each one's callback address is your publicUrl followed by /{id}/callback, such as https://app.example.com/auth/microsoft/callback, and that is the address to register at the service. Every one finds a user's account by the service's sub only, never by email.

ts
import { apple, gitlab, linkedin, microsoft, slack, twitch, validateConfig } from "@evo-auth/core";

export default validateConfig({
  publicUrl: "https://app.example.com/auth",
  providers: [
    microsoft({ tenant: "common" }),
    apple({ teamId: "ABCDE12345", keyId: "FGHIJ67890" }),
    gitlab(),
    slack(),
    twitch(),
    linkedin(),
  ],
});

microsoft() ​

Signs people in with a Microsoft account. In the Microsoft Entra admin center, under App registrations, register an application, choose the supported account types that match the tenant you give, and add the callback address as a Web redirect URI. Under Certificates & secrets, add a client secret. Set EVO_AUTH_MICROSOFT_CLIENT_ID to the application (client) id and EVO_AUTH_MICROSOFT_CLIENT_SECRET to the secret's value.

tenant is common by default (work, school and personal accounts), organizations (work and school accounts only), consumers (personal accounts only) or one organisation's tenant id, a GUID in lower case. The id_token's iss must be https://login.microsoftonline.com/{tid}/v2.0 with the token's own tid, which must itself be a tenant id, and the tid must fit the option:

tenantThe id_token's tid must be
commonany tenant id
organizationsany tenant id except the personal-account tenant
consumersthe personal-account tenant, 9188040d-6c67-4c5b-b112-36a304b66dad
a tenant idthat tenant id

Any other token is refused with oauth_failed. Microsoft does not verify the email it sends, so the email is always stored as not verified. The login is preferred_username.

apple() ​

Signs people in with their Apple Account. It needs a paid Apple Developer membership. In Certificates, Identifiers & Profiles, create a Services ID with Sign in with Apple turned on, and give it your domain and the callback address; Apple accepts only an https address on a domain name, not localhost. Then create a key with Sign in with Apple turned on and download its .p8 file, which Apple gives only once. Set EVO_AUTH_APPLE_CLIENT_ID to the Services ID and EVO_AUTH_APPLE_PRIVATE_KEY to the text of the .p8 file (its line breaks may be written as \n). There is no EVO_AUTH_APPLE_CLIENT_SECRET: each sign-in signs a short-lived client secret with that key. Your Team ID and the key's Key ID are options, teamId and keyId, not variables: each is 10 upper-case letters or digits, apple() refuses a config without both, and neither is secret. The client id and the private key are the two variables, set where the auth endpoints run.

Apple sends the user's name only the first time they sign in to your app, so that first sign-in stores it, and later sign-ins keep it. This holds for every provider: a sign-in that brings no name leaves the stored name as it is, and only a new user with no name gets the login as their name. The login is the email, which may be a private relay address. Apple answers with a form POST to the callback, which EVO_AUTH hands over to the usual callback (see What a named provider can add).

gitlab() ​

Signs people in with GitLab.com, or with a self-managed GitLab when you pass its address: gitlab({ issuer: "https://gitlab.example.com" }). In GitLab, under Edit profile and then Applications (or an instance-wide application in the Admin area), add an application with the callback address as its redirect URI, keep it Confidential, and tick the openid, profile and email scopes. Set EVO_AUTH_GITLAB_CLIENT_ID to the application id and EVO_AUTH_GITLAB_CLIENT_SECRET to its secret. The login is the GitLab username.

slack() ​

Signs people in with Sign in with Slack. At api.slack.com/apps, create an app; under OAuth & Permissions add the callback address as a redirect URL and add the user token scopes openid, profile and email. Set EVO_AUTH_SLACK_CLIENT_ID and EVO_AUTH_SLACK_CLIENT_SECRET to the client id and secret under Basic Information. The picture comes from Slack's user-info answer, and the login is the email.

The account is found by Slack's sub alone. Slack's users.identity page says: "User IDs are now globally unique. Unless you are in an Enterprise organization, the same user on two unrelated workspaces will have different user IDs." The team id is not part of the key, because Slack says it may change, and a key that changes would cut a user off from their account. In an Enterprise organisation one person keeps the same id across its workspaces, so they have one account.

twitch() ​

Signs people in with Twitch. In the Twitch Developer Console, register an application with the callback address as its OAuth redirect URL and the client type Confidential, then create a new secret. Set EVO_AUTH_TWITCH_CLIENT_ID and EVO_AUTH_TWITCH_CLIENT_SECRET. Twitch's discovery document lists only client_secret_post, so twitch() sends the secret in the form body. The sign-in asks for the user:read:email scope and the email, picture and display name in the id_token. Twitch has no separate name, so the display name and the login are both the Twitch display name.

linkedin() ​

Signs people in with Sign In with LinkedIn using OpenID Connect. In the LinkedIn Developer Portal, create an app, add the product Sign In with LinkedIn using OpenID Connect, and on the Auth tab add the callback address as an authorized redirect URL. Set EVO_AUTH_LINKEDIN_CLIENT_ID and EVO_AUTH_LINKEDIN_CLIENT_SECRET. LinkedIn's discovery document names no token authentication method; its documentation sends the client id and secret in the form body, so linkedin() does that, and evo-auth check accepts the missing list for it with a line saying why. A provider you make with oidc() gets no such allowance: a missing list means HTTP Basic only. The profile comes from LinkedIn's user-info answer, and the login is the email.

Where each preset's settings come from ​

Nothing is discovered at run time. Each address, scope and profile field is written in code from the page named below, so a service that changes them needs a new release of @evo-auth/core. For the seven OpenID Connect presets (google() and the six above), evo-auth check compares the addresses with the service's discovery document on your machine and tells you when they differ. The four oauth2() presets below have no discovery document, so check does not compare them.

Where a discovery document was silent, the preset follows the service's own documentation:

ProviderSettled from the service's own pages
microsoft()The personal-account tenant id, and that the email claim is not guaranteed to be correct, from Microsoft's ID token claims reference (learn.microsoft.com/en-us/entra/identity-platform/id-token-claims-reference).
apple()The client secret's format and the form POST answer, from Apple's pages on creating a client secret and on Sign in with Apple for other platforms; the logo-only artwork, from Apple's Human Interface Guidelines.
slack()The discovery document lists only sub, auth_time and iss as claims. The name, picture, email and verified flag come from Slack's openid.connect.userInfo answer.
linkedin()The discovery document names no token authentication method. LinkedIn's authorization-code-flow page sends the client id and secret in the form body, so linkedin() does.
twitch()The id_token carries only standard claims unless the authorize request asks for more, so a fixed claims parameter asks for the email, its verified flag, the picture and the display name.
discord()Every address, scope and profile field, from Discord's OAuth2 and User object pages. Discord's pages do not say whether the authorize endpoint takes a PKCE challenge; oauth2() always sends one.
facebook()Every address, scope and profile field, from Meta's manual-flow and Graph API pages, at version v27.0. Meta documents the token exchange as a GET with the secret in the query; facebook() POSTs the form instead, so the secret never lands in a URL. Its pages do not say that endpoint accepts a POST.
x()Every address, scope and profile field, from X's authorization-code and get-my-user pages. X's pages do not say whether the code exchange accepts an S256 challenge, which oauth2() always sends.
spotify()Every address, scope and profile field, from Spotify's code-flow and current-user's-profile pages. Spotify's pages document the client secret and the PKCE challenge as separate flows; oauth2() sends both.

Which account: selectAccount ​

github() and google() ask which account on every sign-in: each authorize request sends prompt=select_account, so GitHub shows its account picker and Google its account chooser, even when the browser is already signed in there. Without it, a browser signed in to GitHub or Google as one account signs the user in as that account with no question, which is easy to miss when someone has two accounts or shares a browser.

To let sign-in go straight through for a user already signed in at the provider, pass selectAccount: false:

ts
import { github, google, validateConfig } from "@evo-auth/core";

export default validateConfig({
  publicUrl: "https://app.example.com/auth",
  providers: [github({ selectAccount: false }), google({ selectAccount: false })],
});

Reverification and linking a second account still send prompt=select_account with selectAccount: false. githubForTesting() takes the same option beside its two origins. oidc(), oauth2() and evoHub() have no such option and send no prompt on a sign-in. A shared sign-in server's own github() or google() follows the same default, so a person signing in through it is asked there.

evoHub(): the shared sign-in server ​

evoHub() points an app at the shared sign-in server: an EVO_AUTH deployment, run once for all your apps, that holds the GitHub and Google registrations so the apps do not. The app's config needs one line and no provider variable.

ts
import { evoHub, validateConfig } from "@evo-auth/core";

export default validateConfig({
  publicUrl: "https://app.example.com/auth",
  providers: [evoHub({ url: "https://auth.example.com/auth" })],
});

url is the server's own publicUrl: its origin followed by its basePath. There is no client id or secret to register or set. The app's client id is its own origin, here https://app.example.com. The server lists the app by its exact callback address, {publicUrl}/{id}/callback, here https://app.example.com/auth/evo/callback, in its hub.allowedClients; evo-auth check prints it. The server sends codes to that address only: no other path, query or trailing slash. evo-auth init --hub https://auth.example.com/auth writes a config with this line and an .env.example with no provider variable.

OptionRequiredWhat it is
urlyesThe server's publicUrl. An absolute https: URL, or http: on a loopback host for development, written as a URL parser writes it back, with a path (its basePath), no trailing slash, and no user name, query string or fragment.
idnoSee The id. Default: evo.
labelnoThe text on the sign-in button. Default: Evo, so the button reads "Sign in with Evo".

It is oidc() over the server: the issuer is url, and the endpoints are {url}/oidc/authorize, {url}/oidc/token and {url}/.well-known/jwks.json, with no user-info endpoint. The scopes are openid, profile and email, and the authorize request carries PKCE with S256 and the nonce, as for oidc(). Nothing is looked up when it is made or when it runs. The token request is a public client's: client_id in the body, no client secret and no Authorization header. Every id_token check of oidc() applies unchanged, with the audience being the app's origin. evoHub() throws a TypeError naming the option, never its value, for a url that breaks the rule above, an id or label oidc() would refuse, or an option it does not take.

For an evoHub() provider, evo-auth check compares the server's discovery document as for any oidc() provider, except that token_endpoint_auth_methods_supported must list none, the method evoHub() uses. It asks no EVO_AUTH_EVO_* variable, prints the exact callback address the server must list in hub.allowedClients, and says no client secret is needed. A server that does not answer is a problem, as for any oidc() provider, whether or not another provider is listed beside it.

Fallback beside the server ​

Fallback is configuration only. List evoHub() beside a provider of the app's own, and the sign-in page shows two buttons:

ts
import { evoHub, github, validateConfig } from "@evo-auth/core";

export default validateConfig({
  publicUrl: "https://app.example.com/auth",
  providers: [evoHub({ url: "https://auth.example.com/auth" }), github()],
});

github() here needs its own two variables, as always. When the server cannot be reached, the browser cannot open its sign-in address and no session is made; when it fails during the exchange, the sign-in ends with oauth_failed. Either way the GitHub button still works. Nothing switches between them on its own: there is no health check, no automatic failover and no copy of the server's users in the app.

Moving existing users over ​

A user who signs in through the server for the first time is a new user in the app, even when an existing user has the same email: users are found by provider account, never by email. To move an existing user over, they sign in the old way, then Connect the server's account in UserProfile (see Linking a second provider to a user). From then on, signing in through the server reaches the same user, and once every user who needs it has linked, the old provider can be removed from the config.

The icon on the button ​

Each provider's button, and its tile wherever a provider is named (the profile's linked accounts, the confirm-identity dialog, the admin panel and the shared sign-in server's page), shows the provider's icon when it has one, and the first letter of its label on a coloured square when it has none.

github() and google() carry their official marks: the GitHub mark, black on a light page and white on a dark one, and Google's full-colour G on its sign-in square, the light square on a light page and the dark one on a dark page. microsoft() carries Microsoft's four-square logo, apple() Apple's logo-only Sign in with Apple square (the black logo on white, in light and dark, drawn with the tile's rounded corners and outline) and twitch() Twitch's purple Glitch. gitlab() carries GitLab's tanuki, slack() Slack's hash mark, discord() Discord's mark and spotify() Spotify's icon, all the owners' files unchanged. linkedin() carries LinkedIn's [in] logo, facebook() Facebook's "f" and x() X's logo (black on a light page, white on a dark one): the owners' official PNGs, resampled to 64 px on the longest side with nothing else changed, except X's white SVG, which is X's own file unmodified. They are trademarks, not covered by the MIT licence: see TRADEMARKS.md, which ships in @evo-auth/core and records each source file and how the resampled ones were made. oauth2(), oidc() and evoHub() carry none, so their buttons show the letter.

To give any provider an icon, add the member:

ts
import { oidc, validateConfig } from "@evo-auth/core";

const acmeLogo = `data:image/svg+xml,${encodeURIComponent('<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 16 16"><circle cx="8" cy="8" r="7" fill="#0f7a70"/></svg>')}`;

const acme = {
  ...oidc({
    id: "acme",
    label: "Acme",
    issuer: "https://id.acme.example",
    authorizationEndpoint: "https://id.acme.example/authorize",
    tokenEndpoint: "https://id.acme.example/token",
    jwksUri: "https://id.acme.example/jwks",
  }),
  icon: { light: acmeLogo },
};

export const config = validateConfig({ publicUrl: "https://app.example.com/auth", providers: [acme] });

light is drawn on a light page and dark, when you give it, on a dark one; without dark, light is drawn on both. Each value must be a data:image/svg+xml or data:image/png URI of at most 8192 characters, the whole URI counted, written with no space, control or non-ASCII character: percent-encode SVG markup with encodeURIComponent, or use base64. validateConfig refuses anything else, an https: address included, naming the provider and what is wrong. A data URI keeps the picture inside the page: the shared sign-in server's page allows images only from data: addresses, and no sign-in page asks the network for a picture. Setting icon: undefined on a spread of github() or google() drops its mark.

The icon is only ever the source of an <img> with an empty alternative text, beside the provider's name: it is never written into the page as markup, so an SVG cannot run script. Every provider's tile weighs the same, and the icon's shape says how it is drawn, whatever the picture's format. It takes one of three values:

  • "mark", the default when you leave shape out: a small mark, as GitHub's is, drawn at the size of a tile's letter and centred on a plain tile with an outline. Draw it square with little or no margin.
  • "square": artwork that brings its own square inside a margin of 6/56 of its width on each side, as Apple's logo-only files do. The tile draws the picture so that the square fills the tile and the margin falls outside it, with the tile's rounded corners and outline. apple() and gitlab() use it: GitLab's file draws the tanuki in the middle of a canvas with about a quarter of its width as margin on each side, which as a mark would come out a few pixels wide.
  • "full": the picture is the whole tile, as Google's sign-in square is, drawn edge to edge exactly as it is, with no rounding, inset or outline added. Draw it square with its own margin, corners and border. google() uses it.

validateConfig refuses any other value. A picture that is a whole tile needs shape: "full", a PNG included: without it, it is drawn as a mark, shrunk to the size of a letter on a plain outlined tile.

discord(), facebook(), x() and spotify() ​

Four more named providers, each oauth2() with the service's settings written out: its three addresses, its scopes and its profile map are fixed in code, so a config cannot point sign-in elsewhere. None takes an option. Nothing is looked up when one is made or when it runs. Each finds the account by the service's own user id alone; an email is shown, never used to find or link a user.

ts
import { discord, facebook, spotify, validateConfig, x } from "@evo-auth/core";

export default validateConfig({
  publicUrl: "https://app.example.com/auth",
  providers: [discord(), facebook(), x(), spotify()],
});

For each, register an app with the service, add https://app.example.com/auth/{id}/callback (your publicUrl followed by /{id}/callback) as its redirect address, and set the two variables where the auth endpoints run (see The client id and secret). Each shows its brand's official mark (see TRADEMARKS.md).

discord() ​

Create an application in the Discord developer portal, and under OAuth2 add the redirect address with id discord. Variables: EVO_AUTH_DISCORD_CLIENT_ID and EVO_AUTH_DISCORD_CLIENT_SECRET. It asks for the scopes identify and email, and reads /users/@me: the id, the username as the login, the display name when set, the email and its verified flag. The avatar address is built from the id and the avatar hash, https://cdn.discordapp.com/avatars/{id}/{avatar}.png, and left out for an account with no avatar.

facebook() ​

Create an app in Meta for Developers, add Facebook Login, and add the redirect address with id facebook under its valid OAuth redirect URIs. Variables: EVO_AUTH_FACEBOOK_CLIENT_ID (the app id) and EVO_AUTH_FACEBOOK_CLIENT_SECRET (the app secret). It asks for the email permission beside the always-granted public profile, and reads Graph /me?fields=id,name,email,picture at the version written in its addresses, v27.0. The id is the app-scoped id. Facebook sends no email for an account without a valid address, and has no login name or verified flag, so those are left out. The picture address expires.

x() ​

Create a project and app in the X developer console, turn on OAuth 2.0 user authentication for a web app (confidential client), and add the redirect address with id twitter. The function is x() and the button reads X, but its provider id is twitter (an id is at least two characters), so the redirect address to register at X is {publicUrl}/twitter/callback, and the variable prefix is EVO_AUTH_TWITTER. Variables: EVO_AUTH_TWITTER_CLIENT_ID and EVO_AUTH_TWITTER_CLIENT_SECRET. It asks for users.read and tweet.read, authenticates the token request with HTTP Basic as X requires of a confidential client, and reads /2/users/me with user.fields=profile_image_url: the id, the handle as the login, the name and the picture. It asks for no email.

spotify() ​

Create an app in the Spotify developer dashboard and add the redirect address with id spotify. Variables: EVO_AUTH_SPOTIFY_CLIENT_ID and EVO_AUTH_SPOTIFY_CLIENT_SECRET. It asks for user-read-email and reads /v1/me. The account is found by account_id, which Spotify gives as the immutable identifier and says to use for linking (its id is not for that); the id is kept as the login, for display only. A profile without account_id is refused as any failed sign-in is. The display name when set and the email are read too; Spotify says the email is unverified, so it is stored as not verified. No avatar is read.

What a provider object is ​

A provider is a plain object with six members, and two optional ones, endpoints and icon. Its type is Provider, exported from @evo-auth/core.

MemberTypeWhat it is
idtextThe provider's name in URLs and variable names. See The id.
kind"oauth2" or "oidc"The protocol family.
labeltextThe text on the sign-in button, such as Acme. Not empty, no control characters.
authorizationUrl(input) => stringBuilds the URL the browser is sent to at the provider. Synchronous.
exchangeCode(input) => Promise<result>Swaps the code from the callback for an access token.
fetchProfile(tokens, context) => Promise<result>Reads who signed in, with the tokens exchangeCode returned.
endpointslist of URL text, optionalThe URLs the provider talks to. oauth2() sets it to its three endpoints, oidc() to its issuer and endpoints.
icon{ light, dark? }, optionalThe picture on the provider's sign-in tile, in place of its first letter. See The icon on the button.

validateConfig checks every provider, whichever way it was made: the id, the label, that kind is one of the two values, that the three functions are functions, that no two providers share an id, and, when endpoints is there, that each one is an absolute https: URL, or http: on a loopback host only with cookies.devMode, with no user name, password, query string or fragment. When icon is there, it checks it as The icon on the button says. Each refusal names the provider by its place in the list, and by its id once the id is valid. The object must be a plain object whose members are its own data properties: a class instance, a getter or any other member is refused. validateConfig copies the members into a new frozen object, so changing your object afterwards changes nothing.

The three functions ​

authorizationUrl receives { clientId, state, codeChallenge, redirectUri, nonce, reauthenticate } and returns the authorize URL as absolute URL text. Put state, codeChallenge with code_challenge_method=S256, and redirectUri on it. nonce is the attempt's OpenID Connect nonce: an OpenID Connect provider sends it, and any other ignores it. reauthenticate is true when the user is confirming who they are before a sensitive action, such as deleting their account. Turn it into your provider's way of asking again, if it has one: github() and google() add prompt=select_account (which they also send on every sign-in unless selectAccount is false), oidc() adds prompt=login and max_age=0. If it has none, ignore it, as oauth2() does; the round trip then proves the user still controls the provider account, not that they typed a password just now.

exchangeCode receives { code, codeVerifier, redirectUri, credentials, nowSeconds }, where credentials is { clientId, clientSecret }, your provider's own pair, and nowSeconds the current time in seconds, for a service whose client secret is made for each exchange. Send redirectUri and codeVerifier to the token endpoint. Return { ok: true, tokens: { accessToken } }, with idToken beside accessToken when the service gave one, or { ok: false, error } with error set to new AuthError("oauth_failed").

fetchProfile receives those tokens and a context, { clientId, nonce, nowSeconds, clockSkewSeconds, reauthenticatedAfter }: what an OpenID Connect provider needs to check the id_token. nonce is the one sealed at the start, nowSeconds the current time in seconds, and reauthenticatedAfter the time in seconds the confirmation before a sensitive action started, or null for a plain sign-in. For a provider that answers by form POST, the context also holds postedUser, the text of the posted user field, when the POST belonged to this sign-in (see What a named provider can add). A provider that is not OpenID Connect ignores the context. Return { ok: true, profile } or the same failure. profile is:

FieldRequiredWhat it is
providerUserIdyesThe provider's stable id for the account, as text of 1 to 255 characters. Sign-in finds the user by this id and the provider's id, never by email.
loginnoThe account's handle.
namenoThe display name.
avatarUrlnoA picture URL.
emailnoThe account's email address, for display only. Nothing that decides who a user is or what they may do reads it.
emailVerifiednotrue when the service says it verified email. Anything other than the boolean true is stored as false.

login, name and avatarUrl are cut and filtered by the same rules as the access token's claims before anything is stored. email is kept only when it is text of at most 254 characters with no control character; any other value is dropped, and the sign-in goes on without it.

What EVO_AUTH keeps to itself ​

Your provider is your code, and it is trusted for its own logic. It gets the inputs above and its own credentials, and nothing else: no storage, cookie, session, master secret or other provider's credentials. EVO_AUTH makes the state, the PKCE verifier and the nonce, seals the attempt into the sign-in cookie, checks the state when the browser comes back, completes the sign-in and makes the session, whatever the provider does.

A provider function that throws, returns a promise that rejects, or returns anything other than the shapes above ends the sign-in with oauth_failed. No session is made, and one log line names the event, oauth.provider_failed, and nothing the provider said. Only the documented members of a result are read. EVO_AUTH does not time your provider's requests out, so give each one its own timeout, as the example below does with AbortSignal.timeout. Refuse redirects on any request that carries the client secret or the access token (redirect: "error"), so neither is sent on to another address.

The id ​

An id is a lower-case letter followed by 1 to 31 lower-case letters or digits: github and acme are ids, Acme, a, acme-id and a 33-character name are not. The id is used in two places:

  • The callback URL, {publicUrl}/{id}/callback. Register exactly this URL with the provider. evo-auth check prints it.
  • The names of the two variables below.

The client id and secret ​

Each provider's credentials are two environment variables, named from its id in upper case:

VariableHolds
EVO_AUTH_{ID}_CLIENT_IDThe client id the provider gave you.
EVO_AUTH_{ID}_CLIENT_SECRETThe client secret.

github() reads EVO_AUTH_GITHUB_CLIENT_ID and EVO_AUTH_GITHUB_CLIENT_SECRET, and google() reads EVO_AUTH_GOOGLE_CLIENT_ID and EVO_AUTH_GOOGLE_CLIENT_SECRET. A provider with id acme reads EVO_AUTH_ACME_CLIENT_ID and EVO_AUTH_ACME_CLIENT_SECRET.

Set both where the auth endpoints run, and nowhere else. On Convex that is the deployment's environment (see Variables); on another host it is the environment of the process that calls createAuth. The app server's render and proxy roles never read them. Locally, keep them in .env.local, which evo-auth init makes sure git ignores.

An evoHub() provider has no variables: its client id is the origin of the app's publicUrl, and it has no secret. Neither createAuth nor evo-auth check asks for EVO_AUTH_EVO_*. That holds only for a provider evoHub() made: a provider you write yourself with the id evo, or an oidc() provider given the server's addresses, reads its two variables like any other.

Only the auth role reads them: fromEnv(env, "auth") gives an object whose providerCredentials(id) reads the two variables the first time it is asked for that id. createAuth asks for every provider in providers and refuses to start when both variables of one are missing, naming both, or when only one is set or one is empty, naming that one. No value is ever printed. evo-auth init writes both variables, empty, into .env.example for each provider of the config it writes, and evo-auth check reports any that is missing by name.

Example of your own provider ​

A provider written by hand, for a service that speaks OAuth 2 with PKCE and has a user-info endpoint. oauth2() covers this case without code; the example shows the shape a provider of your own takes. It sends the client credentials in the token request body, as this service asks.

ts
import { AuthError, validateConfig, type Provider } from "@evo-auth/core";

const AUTHORIZE_URL = "https://id.acme.example/oauth/authorize";
const TOKEN_URL = "https://id.acme.example/oauth/token";
const USERINFO_URL = "https://id.acme.example/oauth/userinfo";

const failed = { ok: false, error: new AuthError("oauth_failed") } as const;

/** One request that must answer 200 with a JSON object; null for anything else, a timeout included. */
async function jsonObject(url: string, init: RequestInit): Promise<Record<string, unknown> | null> {
  try {
    const response = await fetch(url, { ...init, redirect: "error", signal: AbortSignal.timeout(10_000) });
    if (response.status !== 200) return null;
    const body: unknown = await response.json();
    return body !== null && typeof body === "object" && !Array.isArray(body) ? (body as Record<string, unknown>) : null;
  } catch {
    return null;
  }
}

export const acme: Provider = {
  id: "acme",
  kind: "oauth2",
  label: "Acme",
  authorizationUrl({ clientId, state, codeChallenge, redirectUri, reauthenticate }) {
    const url = new URL(AUTHORIZE_URL);
    url.searchParams.set("response_type", "code");
    url.searchParams.set("client_id", clientId);
    url.searchParams.set("redirect_uri", redirectUri);
    url.searchParams.set("scope", "profile");
    url.searchParams.set("state", state);
    url.searchParams.set("code_challenge", codeChallenge);
    url.searchParams.set("code_challenge_method", "S256");
    if (reauthenticate) url.searchParams.set("prompt", "login");
    return url.href;
  },
  async exchangeCode({ code, codeVerifier, redirectUri, credentials }) {
    const body = await jsonObject(TOKEN_URL, {
      method: "POST",
      headers: { Accept: "application/json", "Content-Type": "application/x-www-form-urlencoded" },
      body: new URLSearchParams({
        grant_type: "authorization_code",
        code,
        redirect_uri: redirectUri,
        code_verifier: codeVerifier,
        client_id: credentials.clientId,
        client_secret: credentials.clientSecret,
      }),
    });
    const accessToken = body?.["access_token"];
    return typeof accessToken === "string" && accessToken !== "" ? { ok: true, tokens: { accessToken } } : failed;
  },
  async fetchProfile({ accessToken }) {
    const body = await jsonObject(USERINFO_URL, { headers: { Authorization: `Bearer ${accessToken}`, Accept: "application/json" } });
    const id = body?.["sub"];
    const name = body?.["name"];
    if (typeof id !== "string" || id === "" || id.length > 255) return failed;
    return { ok: true, profile: { providerUserId: id, ...(typeof name === "string" ? { name } : {}) } };
  },
};

export default validateConfig({
  publicUrl: "https://app.example.com/auth",
  providers: [acme],
});

With this config, set EVO_AUTH_ACME_CLIENT_ID and EVO_AUTH_ACME_CLIENT_SECRET on the auth side, and register https://app.example.com/auth/acme/callback with the service.

Linking a second provider to a user ​

A sign-in through a provider account that no user holds makes a new user, even when another user has the same email. A signed-in user adds another provider's account to their own user with Connect in UserProfile (see React components); after that, signing in through either account reaches the same user. Each user can hold one account per provider.

The link starts with POST {basePath}/{provider}/link, which needs the access token, passes the Origin check and needs a recent confirmation with the provider. It answers 200 { "url": "..." }, the provider's authorize address, and sets the sign-in cookie with the link sealed in it. The provider is asked to reauthenticate as for a reverification: oidc() sends prompt=login and max_age=0, github() and google() ask the user to choose the account, and oauth2() sends nothing, so with an oauth2() provider the account linked is whichever one is signed in at the provider in that browser. The callback links the account only when the session that started the link is still live and its confirmation still recent, and refuses with oauth_failed, changing nothing, when another user holds the account or the user already holds an account at that provider. A completed link writes the account row and an account_linked event, changes no session, sets no session cookie, and returns to the page with evo_linked=1.

POST {basePath}/account/unlink with { "provider": "...", "providerUserId": "..." } removes one of the user's accounts while another remains and records account_unlinked.
