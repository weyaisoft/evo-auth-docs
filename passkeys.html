Passkeys ​

This page is for a developer turning on passkeys in an app that uses @evo-auth/react. A passkey lets a signed-in user sign in later with their fingerprint, face or screen lock (Windows Hello, iCloud Keychain, Google Password Manager or a security key) instead of a provider, and confirm their identity with it before a sensitive action.

With passkeys on, a signed-in user adds a passkey from their profile. With passkeys.signUp on as well, a new person can also sign up with an email address and a passkey and no password.

Turning them on ​

Set passkeys.enabled to true in the server config:

ts
export const authConfig = validateConfig({
  publicUrl: "https://example.com/auth",
  providers,
  passkeys: { enabled: true },
});

publicConfig then carries passkeys: true, and the components show passkeys with no change to your React code. Both examples in this repository run with passkeys on.

rpId. A passkey is bound to its relying party id, a host name. Leave passkeys.rpId out and it is publicUrl's host name, which is right for almost every app. Set it only when several hosts under one parent domain must share passkeys, and then to that parent: for a publicUrl at https://auth.example.com/auth, rpId: "example.com" lets the same passkeys work on app.example.com. At start-up it must equal publicUrl's host name or be a parent domain of it with at least two labels, and it cannot be set when the host is an IP address. There is no public-suffix check, so a value such as co.uk passes start-up; it still fails safe, because the browser refuses any ceremony whose rpId is not the page's host or a registrable parent of it, and the user sees a refusal line. Changing rpId later makes every passkey already added unusable. Browsers accept localhost over plain http, which is how the examples run.

With passkeys off, nothing on any screen changes and the passkey routes do not exist.

Trying it ​

In either example (examples/tanstack-convex or examples/tanstack-server, each with its own README steps), sign in with GitHub, open Profile and choose "Add a passkey". The browser asks you to confirm with GitHub first if your last confirmation is not recent, then to name the passkey, then shows its own prompt (Windows Hello, Touch ID, a phone or a security key). Sign out, and "Sign in with a passkey" on the sign-in page signs you back in with the passkey alone.

Signing up with a passkey ​

Set passkeys.signUp to true and a new person can make an account from an email address and a passkey. The address is proved first, by a code or a link sent to it, and the account exists only once the passkey is made.

ts
export const authConfig = validateConfig({
  publicUrl: "https://example.com/auth",
  providers,
  email: { sender },
  emailAuth: { code: true, link: true, signUp: true },
  passkeys: { enabled: true, signUp: true },
});

validateConfig refuses passkeys.signUp unless passkeys.enabled and emailAuth.signUp are on, email.sender is set, and at least one of emailAuth.code, emailAuth.link and emailAuth.password is on, so a person who signs up with a passkey always has a way back in by email. On Convex, registerRoutes needs its emailJob while it is on, as it does for the email methods (Convex). publicConfig carries passkeySignUp: true.

What the person sees. SignUp, and the sign-in card's "Create an account", show while (emailAuth.password || passkeySignUp) && emailAuth.signUp. With passkeySignUp on, the card opens on the passkey:

  1. The address and "Continue with a passkey". With passwords on too, "Use a password instead" opens the password form, and the password form offers "Use a passkey instead"; the address is kept either way.
  2. "Check your email": the six-digit code, with "Send a new code" and "Use a different address". The email is the sign_up message. While emailAuth.link is on it also holds a link; opened in the browser that asked, the sign-in page shows "Finish creating your account" and Continue goes on to the next step.
  3. "Create your passkey": a name, filled with "Passkey on {system}", then "Create passkey" and the browser's own prompt. The name is checked before anything is sent, and fresh options are fetched right before every prompt, so the step does not run out while the person reads it.
  4. The person is signed in and goes to the redirect. There is no extra screen.

An address that already has an account gets the existing_account_notice email instead of a code, and the card answers exactly as for a new address. A closed prompt goes back to step 3 quietly. The other refusals each have their own line: a wrong or expired code, too many tries, a wait after too many requests, an address that got an account meanwhile ("Sign in instead"), and a sign-up that has expired ("Start again").

Routes. Three POST routes under {basePath}/passkeys/sign-up exist only while the setting is on; otherwise they answer the generic 404.

RouteBodyAnswer
/start{ email }200 { sent: true } for every address the server takes, with the email cookie that ties the code and the link to this browser. 400 email_address, or 429 with Retry-After.
/options{ code }, { token } (a link's) or {}200 with the registration options. The first code or link proves the address; after that {} gives fresh options for 5 minutes, and a code or link sent again counts as {}. 400 with wrong_code, too_many_attempts, challenge_expired or email_other_browser (a link opened in another browser, which counts nothing), or the generic 404 without the email cookie.
/verify{ name, credential }200 { accessToken, expiresAt } with the session cookies: the user, the verified email account and the passkey are made together, and the session starts at once, with no second step. 400 with passkey_name, passkey_failed, address_taken or passkey_exists, or challenge_expired.

The registration options carry the account's user handle, 16 random bytes as 22 base64url characters, not the user's id; a passkey added later from the profile carries the same handle. The rules behind each step are in the security model.

Limits and events. /start counts email_sign_up for the client address first, then email_send and email_recipient, as a password sign-up does. A sign-up allows 5 wrong codes; a failed registration counts toward the same 5. /verify records sign_up, passkey_added and sign_in, and runs onUserCreated; user.created is the only webhook event. /start and /options record nothing.

At a shared sign-in server ​

With passkeys on at a hub, its chooser counts the passkey as a way in and links to the hub's own sign-in page, so a person whose only way in is a passkey can sign in to an app through the hub, and confirm their identity when an app asks for a fresh sign-in. The apps themselves need nothing new. See Passkeys at the hub.

What the user sees ​

  • SignIn ends its list with "Sign in with a passkey", when the browser can use one. While the browser shows its own prompt, the button waits and the provider buttons are held. After a successful sign-in the browser goes to the redirect prop, or to the page the user is on, exactly as after a provider sign-in, and the provider reads the new session there.
  • Autofill on the email field. Clicking the sign-in card's email field can show the person's saved passkeys in the browser's own autofill list; picking one signs them in with no button and no typing. See Autofill.
  • UserProfile has a Passkeys section. Each passkey shows its name, when it was added, when it was last used, and "Synced" or "This device only". The user can add, rename and remove passkeys.
  • Adding asks for a recent confirmation of identity first: "Use a passkey" when the user already has one this browser can use, otherwise the provider. Then a row names the new passkey, filled with "Passkey on Windows" (or the system the browser reports), or "Passkey" when the system cannot be read, and the user can change it before the browser's prompt.
  • Every confirmed action in the profile (deleting the account, connecting or disconnecting an account, adding or removing a passkey) and on the admin page (ban, unban, delete) offers "Use a passkey" beside the provider when the user has a passkey this browser can use. A passkey confirms in place, with no trip to the provider.
  • AdminPanel lists a user's passkeys on their page, each with a remove control behind a confirmation. The removal is recorded with the admin as the actor. Only the user can add or rename their passkeys.

The last way to sign in, accounts and passkeys counted together, cannot be removed, by the user or by an admin. An admin who wants to stop a user signing in bans or deletes them instead.

Removing a passkey ends the user's other sessions: the user's own removal signs out every other device, and its confirmation says so; an admin's removal signs the user out everywhere. See Revocation.

Autofill ​

Autofill has no setting. It runs on SignIn's email field whenever publicConfig.passkeys is true, the card shows that field (an email sign-in method is on: emailAuth.code, emailAuth.link or emailAuth.password) and the browser answers PublicKeyCredential.isConditionalMediationAvailable() with true. Nothing is added to the card: the field's autocomplete is "email webauthn", and the browser draws the list.

  • The request. When the field appears, the card posts POST {basePath}/passkeys/signin/options with { "conditional": true } and asks the browser with navigator.credentials.get({ mediation: "conditional" }). The browser shows nothing until the person clicks the field, and then offers the site's passkeys beside any saved addresses. Picking one posts it to /passkeys/signin/verify, with the same limits and refusals as the button, and lands where the button lands.
  • A pending second step stays as it is. For { "conditional": true } the options route always answers the ordinary sign-in options and leaves a pending second step's cookie alone, so reloading the sign-in page during a second step, or opening it in another tab, cancels nothing. See Two-step sign-in in the security model.
  • One request at a time. "Sign in with a passkey", a provider's button, the address's Continue and "Create an account" each stop autofill before they send anything. While the card shows a second step, or any step that replaces the email field, autofill is not running.
  • Keeping it fresh. The challenge lasts 120 seconds, so the card asks again every 110 seconds, but only while the tab is visible and the field does not have focus, so an open list is never closed under the person. It also asks again when the tab becomes visible, when the field gains focus with a request older than about 90 seconds, and after a refusal. Each refresh is one options request; it writes nothing and counts no limit.
  • A refusal shows "Couldn't sign you in with a passkey. Try again, or use another way to sign in.", and the list is offered again.
  • Where it is not. The sign-up card has nothing to fill. The shared sign-in server's chooser page has no script, so it has no autofill; the hub's own sign-in page, which is SignIn, has it.
  • The browser decides. Whether a browser offers passkeys in a field marked "email webauthn", and how its list looks, is the browser's. A browser that answers false, or has no isConditionalMediationAvailable, shows the card exactly as before.

Your own screens ​

usePasskeys() gives the same list and actions for a screen of your own. The package converts every byte string by hand and never calls PublicKeyCredential.parseCreationOptionsFromJSON, parseRequestOptionsFromJSON or toJSON, which WebKit lacks.

What the tests prove, and what only a real device does ​

The three-browser suite (tests/acceptance/app/passkeys.spec.ts, hub-passkeys.spec.ts and, for signing up, passkey-sign-up.spec.ts and server-passkey-sign-up.spec.ts) runs the examples in headless Chromium, Firefox and WebKit with Playwright's virtual authenticator, which stands in for navigator.credentials in the page. It proves, in all three:

  • adding a passkey from the profile, signing out, and signing in with the passkey alone;
  • confirming identity with it before removing a passkey and before deleting the account; renaming; removing, after which the server refuses that passkey at sign-in;
  • refusal of a passkey made for another rpId, of a signature counter that went backwards, and of a banned or deleted user;
  • at a hub, a person whose only way in is a passkey signing in to an app through the chooser, and confirming their identity for an app with a fresh auth_time, or cancelling and the app receiving login_required;
  • signing up with an address and a passkey on both examples, signing back in with it, a second passkey from another browser joining the same account, the notice to an address that already has one, a closed prompt, and the emailed link in the browser that asked and in another;
  • autofill (passkey-autofill.spec.ts and server-passkey-autofill.spec.ts): a passkey made at sign-up signing in when the sign-in page opens, the button still signing in beside autofill, and a second step pending in another tab left as it was.

The virtual authenticator always makes ES256 keys, always reports the user present and verified, never reports a backed-up (synced) passkey, and shows no account chooser. It answers a conditional request at once with the first passkey it holds, with no list and no person, and ignores the abort signal, so the suite proves autofill's requests and what follows a pick, not the browser's list or that stopping autofill closes it. The hook's rules for starting, refreshing, restarting and stopping are proved against a stand-in for navigator.credentials with a test clock. So these need a real device: Windows Hello, iCloud Keychain, Google Password Manager and security keys, signing in with a phone by QR code, the real user-verification prompts, the browser's autofill list and its closing when autofill stops, an RS256 passkey (Windows Hello on many machines; the server's RS256 check is tested in core), the "Synced" label, and the refusal of a response without user verification (tested in core).

Limits ​

  • The server enforces its own rules; see Passkeys in the security model for the checks, the counter rule and what an attacker would need.
  • Attestation (knowing which make of authenticator the user has) is not offered.
  • Someone at an unattended browser on the "Create your passkey" step could finish the sign-up with their own passkey, as with any sign-up left open. That step lives 5 minutes after the address is proved.
  • Removing a passkey here does not remove it from the user's device or password manager, which may still list it until the user deletes it there.
