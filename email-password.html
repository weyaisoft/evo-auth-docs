Email and password ​

People sign up and sign in with an email address and a password. Evo Auth checks the password rules, stores only a salted and peppered hash, throttles guessing, and sends the reset, sign-up and address-change codes by email.

Switch it on ​

Passwords are off until you turn them on. Every emailAuth setting defaults to false.

ts
import { type EmailSender, validateConfig } from "@evo-auth/core";

declare const send: EmailSender;

export default validateConfig({
  publicUrl: "https://app.example.com/auth",
  email: { sender: send },
  emailAuth: { password: true, signUp: true },
  password: { minLength: 15, breachCheck: true },
});
SettingDefaultWhat it does
emailAuth.passwordfalseSign-in with an address and a password, the reset by email, setting or changing a password, and adding or changing an address. Needs email.sender and EVO_AUTH_PASSWORD_PEPPER.
emailAuth.signUpfalseWith emailAuth.password on, adds POST {basePath}/email/sign-up. Also lets an emailed code or link make an account (see Email).
password.minLength15The fewest characters a password may have, from 8 to 128.
password.breachChecktrueRefuses a new password found in Have I Been Pwned's Pwned Passwords list.

The two password settings apply only while emailAuth.password is true. The reference has the limits.

Then set EVO_AUTH_PASSWORD_PEPPER where the auth endpoints run (see The pepper), and, on Convex, emailJob (see Email). createAuth refuses to start while emailAuth.password is on and the pepper is missing. evo-auth check names it too.

The password rules ​

  • At least password.minLength characters, each Unicode code point counting as one. The default is 15, which is what NIST SP 800-63B-4 asks for when the password is the only factor. It allows 8 when the password is one of several factors. The setting accepts 8 to 128. The minimum does not drop by itself. password.minLength already goes down to 8, and NIST's 8 applies only when a second factor is required (secondFactor.required, see Two-step sign-in). Turning two-step sign-in on, or even requiring it, leaves the minimum where you set it. The app chooses:

    ts
    import { type EmailSender, validateConfig } from "@evo-auth/core";

declare const send: EmailSender;

export default validateConfig({
  publicUrl: "https://app.example.com/auth",
  email: { sender: send },
  emailAuth: { password: true },
  secondFactor: { enabled: true, required: true },
  password: { minLength: 8 },
});

  • At most 128 characters. This is fixed.

  • No composition rules, so no demand for capitals, digits or symbols, and no periodic expiry.

  • With password.breachCheck on, a new password found in the Pwned Passwords list is refused. Only the first 5 hexadecimal characters of the password's SHA-1 leave the server, with padding asked for, and the service needs no account. When the service cannot be reached, answers with anything but 200 or takes longer than 10 seconds, the check is skipped, the password is accepted and password.breach_check_unavailable is logged.

A refusal says why, as NIST asks: 400 invalid_request with the reason password_too_short, password_too_long or password_breached. A sign-up, a reset and a change all use these rules. The browser learns them from publicConfig, which carries password: { minLength, breachCheck } only while emailAuth.password is on. Neither value is secret.

How a password is stored ​

A password is hashed with PBKDF2-HMAC-SHA256 at 600,000 iterations and a random 16-byte salt. An HMAC-SHA256 keyed by the pepper is then taken over the result. The stored value names its own scheme, $evo-pbkdf2-sha256$i=….

The iteration count is fixed by core, and only a release raises it. It is never a setting. A stored hash whose count is above 2,000,000 is refused before anything is derived, so an imported or altered value cannot make the server burn CPU. A person who signs in with a hash made at an older, lower count has it replaced by a current one in the same operation.

Hashing runs in the HTTP action or the server's handler and never in a storage operation: only the finished string reaches storage. The password-hashing spike timed 600,000 iterations at about 46 ms in a Convex HTTP action, 71 ms in a Node-runtime action and 58 ms on Node 26.3, on the machine that ran it. Convex's default runtime refuses a count above a figure between 2 and 3 million, and the 2,000,000 limit sits below it.

The pepper ​

EVO_AUTH_PASSWORD_PEPPER is its own variable, not derived from EVO_AUTH_SECRET, because that secret can be replaced and this one must not be. Its rule is the same as the master secret's: base64url text that decodes to at least 32 bytes, and different from EVO_AUTH_SECRET. evo-auth init writes one into the env file with the master secret. A project that ran init before passwords existed has none: make one as Rotating secrets shows. With the pepper kept apart from the database, a copy of the database alone is no use for guessing passwords.

Replacing the pepper makes every user reset their password. Every stored hash was made with the old one, so none verifies. Until a person resets, their right password is refused as if it were wrong, and each try counts as a failed sign-in (see Throttling). Replace it only if it leaked. Steps are in Rotating secrets.

Signing up ​

With emailAuth.password and emailAuth.signUp on, POST {basePath}/email/sign-up takes { "email", "password" }, and with usernames on an optional "username" too (see Choosing one at sign-up). It checks the address, the buckets and the password rules, hashes the password, and records a challenge that holds the hash. The answer is 200 { "sent": true } and a cookie that names the browser. Nothing exists yet. The person types the emailed code at POST {basePath}/email/verify, or opens the link while emailAuth.link is on, and only then are the user, their email account and their password made and the browser signed in.

The route is mounted only while both settings are on. It hashes the password for every address before it inserts anything, so an address with an account takes as long as one without. For an address that already has an account the code is not sent: the person gets the existing_account_notice message instead, and the answer is the same. The sign_up message always carries a code, and a link only while emailAuth.link is on.

With passkeys.signUp on as well, SignUp opens on signing up with a passkey and no password, with "Use a password instead" for this form, which then offers "Use a passkey instead". Both kinds of sign-up count in the same email_sign_up bucket. With emailAuth.password off and passkeys.signUp on, the card offers only the passkey.

Signing in ​

POST {basePath}/email/sign-in/password takes { "email", "password" }. A right password signs in, and the answer is the one POST {basePath}/token gives. For a user who has a second factor, or under secondFactor.required, a right password signs nobody in yet: the answer is 200 { "secondFactor": { … } } and a pending sign-in cookie, and the session comes after the second step (see Two-step sign-in). Everything else is the same 400 invalid_request with the reason invalid_credentials: an unknown address, a wrong password, an address with no password and a password that has been turned off. Every refused sign-in does the same work for every address: the password is checked against a dummy hash when there is none to check, and one storage operation records the failure.

Usernames ​

With usernames.enabled on, a person can choose a username in the profile and then sign in with it and their password instead of their address. A username is another way to name the email account's password: it needs emailAuth.password on (validateConfig refuses it otherwise), and a user chooses one only while they have an email account.

SettingDefaultWhat it does
usernames.enabledfalseAdds POST {basePath}/username/sign-in and POST {basePath}/account/username, publicConfig.usernames, the sign-in card's "Email or username" field, and the sign-up card's "Username (optional)".
usernames.reserved[]Up to 200 more names nobody may choose, each following the rule below.

The rule. 3 to 30 characters of a to z, 0 to 9, ., _ and -, starting and ending with a letter or a digit, with no two of ., _ and - side by side, and not all digits. So a username never holds @, and a value with @ is always an address. ASCII capitals are read as lower case and nothing else is changed: the server trims nothing, and SignIn trims what was typed before it checks. A name is reserved when, lower-cased and with its dots, dashes and underscores removed, it matches a built-in name (admin, support, login, settings and others) or one in usernames.reserved treated the same way.

Signing in. POST {basePath}/username/sign-in takes { "username", "password" }. A name that fails the rule is answered 400 invalid_request with the reason invalid_credentials at once, with no hash and no storage call: the rule is public, so the quick answer gives nothing away. Otherwise the route is the address's: an unknown name, a wrong password, a name whose user has no password and a turned-off password all get that same answer after the same work, and a right password signs in to the email account's session, or answers with the second step (see Signing in).

Choosing, changing and removing one. POST {basePath}/account/username, with the access token, takes { "username": "<name>" } or { "username": null }, and answers 200 { "username" } with the name now held, or null.

  • The first name needs no confirmation of identity. Changing or removing a held name needs a recent one (reverification.maxAgeSeconds), and answers 403 reverification_required without it. A change or a removal uses the confirmation up, so a second one straight after asks again.
  • A name another user holds is refused with the reason username_taken, a name that fails the rule with username_invalid, and a reserved one with username_reserved, each on 400 invalid_request. One storage operation checks that a name is free and writes it, so two people asking for one name together cannot both get it.
  • A user with no email account gets no_email_account for a name, but can still remove one they hold.
  • Setting the name already held, or removing when none is held, changes nothing and records no event. Every other change records the username_changed auth event.
  • Every request with a well-formed body counts in the username_change bucket: 10 for each user a day.

GET {basePath}/me carries user.username, the name or null. Deleting a user frees their name at once, in the same write that starts the deletion.

Admins, your server code and other systems. An admin can clear a person's name from the admin page, behind a recent confirmation of the admin's identity, and can find people by the start of a name; an admin cannot set one (the admin routes). Your server code reads the name as AuthApiUser's username and sets, changes or removes it with setUsername, which follows the rule but not the reserved list. Webhook payloads carry it, and a shared sign-in server sends it to apps as preferred_username while the setting is on. Turning usernames.enabled off keeps the names stored, and evo-auth-server check warns while any are held; adding a held name to usernames.reserved does not take it away, and check names it.

Choosing one at sign-up ​

POST {basePath}/email/sign-up takes an optional "username" beside the address and the password. SignUp's password form shows it as "Username (optional)" and sends nothing for a blank field. The passkey form, and a sign-up by code or link, have no username: those people add one from the profile.

  • The checks run in this order: the body, the address, the username's rule (reason username_invalid) and the reserved list (reason username_reserved), then the buckets, the password rules and the hash. The two username refusals depend only on what was typed, so they come before anything is counted.
  • While usernames.enabled is off, a body that carries "username" is refused with 400 invalid_request, and nothing is written.
  • The challenge holds the lower-cased name until the code is typed or the link is opened. No answer before then says whether a name is taken. A taken name and a free one get the same 200 { "sent": true }, the same storage calls, the same work and the same email: the route never looks the name up.
  • At completion, POST {basePath}/email/verify or POST {basePath}/email/verify-link, one storage operation makes the user and sets the name if nobody holds it. If somebody does, the account is made without it, the person is signed in all the same, and the answer carries "usernameTaken": true: beside accessToken and expiresAt, or inside secondFactor when a second step comes first. Only someone who has just proved the mailbox sees it. Two people completing with one name at the same moment end with one holder, and the other is told.
  • On usernameTaken, SignUp's code step, SignIn's link page and the second step show "Choose another username" before following the redirect. Save sends POST {basePath}/account/username, which needs no confirmation for a first name; Skip goes on with no name. The flag lives in the page only, so a reload during a second step loses it, and the person can add a name from the profile.
  • If usernames are turned off between the start and the completion, the pending name is dropped.

What a username does not hide. Usernames are public: anyone willing to make an account can learn which names are taken, so nothing may rely on a name being hard to find out. And anyone who knows a username can switch that person's password off by failing it 100 times (see Throttling), at most 10 tries every 15 minutes, until the person resets it by email. They can no longer hold up sign-in by the address while doing it, since the address and the name each have their own account bucket.

Resetting a password ​

POST {basePath}/email/reset/request takes { "email" } and answers 200 { "sent": true } for every address. The reset_password message, with a code, goes only to an address that has an email account whose user may sign in. POST {basePath}/email/reset/complete takes { "code", "password" } in the browser that asked. A right code and an acceptable password set the password, clear any failed count and any turned-off state, end every other session of the user with the reason credential_changed and sign this browser in. A wrong code, a used or expired one, or a missing cookie is the generic 400 invalid_request, and the password rules and the hash are not run. A reset also gives a first password to a person who had only signed in by code. When a second step applies to the user, the reset still saves the new password and ends the other sessions, but it does not sign this browser in: the answer is 200 { "secondFactor": { … } }, and the person signs in after the second step.

Changing a password, and the address ​

A user has one email address. These routes need a signed-in person who has confirmed their identity recently (see Confirming identity).

  • POST {basePath}/email/password/change takes { "password" }. It sets a password or changes it, ends the user's other sessions with the reason credential_changed and keeps the caller's. A user with no email account gets 400 invalid_request with the reason no_email_account.
  • POST {basePath}/email/add takes { "email" } and sends a verify_address code. POST {basePath}/email/add/verify takes { "code" } in the session that started it. For a user with no email account this adds one. For a user who has one, it is a change of address: the password moves to the new address, the old email account is removed and the user's other sessions end. When another user holds the address, the answer is 400 invalid_request with the reason email_taken. The answer to /email/add says nothing about who holds an address, because that is said only after the code proves the mailbox.

Confirming identity ​

Adding or changing an address, and setting or changing a password, first need a recent confirmation, and answer 403 reverification_required without one. A person who signs in only by email confirms in one of two ways:

  • POST {basePath}/email/reverify/password takes { "password" }. It never accepts a password that is turned off, and a wrong one counts as a failed sign-in.
  • POST {basePath}/email/reverify/code takes {} and sends a reverify code to the person's own address. POST {basePath}/email/reverify/verify takes { "code" } in the session that asked, with five tries.

While secondFactor.enabled is on, a person with a confirmed authenticator is the exception: the password, a provider and an emailed code are refused for them, and they confirm with a passkey, an authenticator code or a backup code (see Two-step sign-in).

The dialog in UserProfile offers what the person has, in this order: a passkey, their password, a provider, an emailed code. One confirmation covers one change. It is used up when the change starts, so of two changes sent together on one confirmation the second answers reverification_required, and a new /email/add voids the user's earlier verify_address challenges. Removing a passkey or unlinking an account does not use it up: removals keep using the recent window (reverification.maxAgeSeconds).

Throttling and turning a password off ​

Only failed passwords count. A success never does. Three buckets apply, each a rateLimits setting (see the reference):

BucketDefaultCounts
password_sign_in_account10 in 15 minutesFailed passwords for one address, or with usernames on for one username, whichever client tries. An address and a username each have their own.
password_sign_in_address30 in 15 minutesFailed passwords from one client address, across every address tried.
email_sign_up10 an hourSign-ups from one client address, counted before anything is written or sent.

A full bucket answers 429 rate_limited with Retry-After. The email_send and email_recipient buckets of Email apply to every message these routes send.

The 100th failed password in a row for one account turns that password off, counting the tries by address and by username together, and Evo Auth emails the person a password_disabled notice. A right password resets the count. While a password is off, sign-in with it is refused with the same generic invalid_credentials as any other failure, so nobody learns that it is off. Only a reset by email, or a password change by a signed-in person who has just confirmed their identity, turns it back on. No admin can: the admin page shows whether a user has a password and whether it is turned off, and nothing there sets, clears or turns one on.

The routes ​

All are POST under {basePath}/email, with everything in the JSON body.

PathMounted while
/sign-in/password, /reset/request, /reset/complete, /password/change, /reverify/passwordemailAuth.password is on
/sign-upemailAuth.password and emailAuth.signUp are both on
/add, /add/verify, /reverify/code, /reverify/verifyany of emailAuth.code, emailAuth.link or emailAuth.password is on

With usernames.enabled on, POST {basePath}/username/sign-in and POST {basePath}/account/username are mounted too, and /sign-up takes an optional username whose completion can answer usernameTaken (see Usernames).

/add and its three neighbours hash nothing, so they run without the pepper while only a code or a link is on. The code, link and /verify routes are in Email.

What stays out ​

  • Linking by email: an email account is never joined to another account because the address matches. A GitHub user and an email user with the same address are two users.
  • Composition rules and periodic expiry.
  • Security questions.
  • Lockout without a reset route.
  • Plain-text or reversible storage.
  • Bot checks.
