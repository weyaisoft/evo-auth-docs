Configuration reference ​

Settings ​

Every setting appears once, in the order the definition lists it.

publicUrl ​

  • Type: string
  • Default: none; the setting is required
  • Limits: an absolute http or https URL in its normal form (lower-case scheme and host, no default port, no dot segments) with no query, fragment or user name, whose path equals basePath; http needs cookies.devMode; at most 256 characters
  • Description: The absolute URL the browser uses for the auth endpoints: the origin plus basePath, for example https://app.example.com/auth. Used exactly as the token issuer (iss), the base of each provider callback ({publicUrl}/{id}/callback) and the JWKS location ({publicUrl}/.well-known/jwks.json), so it must be written exactly as a URL parser would write it back: the origin followed by the path and nothing else.

basePath ​

  • Type: string
  • Default: /auth
  • Limits: one or more /segments of letters, digits and . _ ~ - (the pattern ^(/[A-Za-z0-9._~-]+)+$), with no trailing /, no percent-encoding and no . or .. segment
  • Description: The path under which the auth endpoints are served; the refresh cookie's Path. Only unreserved URL characters are allowed, so the value can be written into the cookie's Path attribute unchanged and cannot add another attribute such as Domain or SameSite.

appId ​

  • Type: string
  • Default: the origin of publicUrl
  • Limits: a non-empty string of at most 256 characters with no control characters
  • Description: The audience (aud) written into and checked on every access token.

appName ​

  • Type: string
  • Default: none (the host name of publicUrl is shown)
  • Limits: text of 1 to 64 characters with no control character
  • Description: The app's name as people see it: in the header, heading, subject and button of every email Evo Auth sends, and in the title of the page a sign-in link opens ("Sign in to {appName}"). The browser receives it in publicConfig. While it is unset the host name of publicUrl is shown instead, such as app.example.com.

cookies ​

cookies.prefix ​

  • Type: string
  • Default: evo
  • Limits: lower-case letters and digits, at least one
  • Description: The prefix of every cookie name, for example __Host-evo_session.

cookies.devMode ​

  • Type: boolean
  • Default: false
  • Limits: true only when publicUrl is http on a loopback host (localhost, 127.0.0.0/8 or [::1])
  • Description: Development cookie mode: drops the __Host- and __Secure- prefixes and the Secure flag so cookies work on http://localhost. Never for production.

allowedOrigins ​

  • Type: string[]
  • Default: [the origin of publicUrl]
  • Limits: exact http or https origins (scheme, host and port only), no wildcards
  • Description: Origins whose POST requests are accepted; the CSRF check. Separate from allowedRedirectOrigins.

allowedRedirectOrigins ​

  • Type: string[]
  • Default: [the origin of publicUrl]
  • Limits: exact http or https origins (scheme, host and port only), no wildcards or patterns
  • Description: Origins an absolute redirect may point to after sign-in. Any other redirect falls back to afterSignInUrl.

afterSignInUrl ​

  • Type: string
  • Default: /
  • Limits: a relative path starting with exactly one / (not // or /\), with no backslash, only visible ASCII characters (U+0021 to U+007E; percent-encode any other character) and no . or .. segment before any ? or #, plain or written with %2e or %2E, or an absolute http or https URL with no user name or password, written exactly as a URL parser writes it back (lower-case scheme and host, the host in its ASCII (xn--) form, no default port, no dot segments, a / before any ? or #, and non-ASCII characters in the path, query and fragment percent-encoded; a bare origin may leave out the final /), whose origin is in allowedRedirectOrigins; no spaces, other whitespace or control characters; at most 2,048 characters
  • Description: Where the browser goes after sign-in when no valid redirect was given.

afterSignOutUrl ​

  • Type: string
  • Default: /
  • Limits: a relative path starting with exactly one / (not // or /\), with no backslash, only visible ASCII characters (U+0021 to U+007E; percent-encode any other character) and no . or .. segment before any ? or #, plain or written with %2e or %2E, or an absolute http or https URL with no user name or password, written exactly as a URL parser writes it back (lower-case scheme and host, the host in its ASCII (xn--) form, no default port, no dot segments, a / before any ? or #, and non-ASCII characters in the path, query and fragment percent-encoded; a bare origin may leave out the final /), whose origin is in allowedRedirectOrigins; no spaces, other whitespace or control characters; at most 2,048 characters
  • Description: Where the browser goes after sign-out.

signInUrl ​

  • Type: string
  • Default: /sign-in
  • Limits: a relative path starting with exactly one / (not // or /\), with no backslash, only visible ASCII characters (U+0021 to U+007E; percent-encode any other character) and no . or .. segment before any ? or #, plain or written with %2e or %2E, or an absolute http or https URL with no user name or password, written exactly as a URL parser writes it back (lower-case scheme and host, the host in its ASCII (xn--) form, no default port, no dot segments, a / before any ? or #, and non-ASCII characters in the path, query and fragment percent-encoded; a bare origin may leave out the final /), whose origin is in allowedRedirectOrigins; no spaces, other whitespace or control characters; at most 2,048 characters
  • Description: The app's sign-in page. Failed navigation requests redirect here with error=<code>.

session ​

session.lifetimeSeconds ​

  • Type: integer
  • Default: 2592000 (30 days)
  • Limits: a whole number from 3600 to 34560000 (1 hour to 400 days, the browsers' cookie limit)
  • Description: How long a session lasts from sign-in; the refresh cookie's lifetime.

accessToken ​

accessToken.lifetimeSeconds ​

  • Type: integer
  • Default: 300 (5 minutes)
  • Limits: a whole number from 60 to 900 (1 to 15 minutes)
  • Description: How long an access token (JWT) is valid.

clockSkewSeconds ​

  • Type: integer
  • Default: 5
  • Limits: a whole number from 0 to 60
  • Description: Clock skew allowed when checking a token's exp and nbf.

refresh ​

refresh.reuseGraceSeconds ​

  • Type: integer
  • Default: 30
  • Limits: a whole number from 0 to 60
  • Description: How long the immediately previous refresh token may be exchanged again, for concurrent reloads and lost responses. 0 turns the window off: then a lost response, a double reload or restored tabs each end the session and cost a sign-in.

reverification ​

reverification.maxAgeSeconds ​

  • Type: integer
  • Default: 600 (10 minutes)
  • Limits: a whole number from 60 to 3600 (1 minute to 1 hour)
  • Description: How recent the session's last provider confirmation must be for account deletion.

authEvents ​

authEvents.retentionSeconds ​

  • Type: integer
  • Default: 7776000 (90 days)
  • Limits: a whole number from 86400 to 34560000 (1 to 400 days)
  • Description: How long an auth event row is kept: each row's expiresAt is set when it is written, to its time plus this value, and a batched sweep removes expired rows. Changing the setting rewrites neither the auth event rows already written nor the purgeAt of session rows already written; they keep the values set when they were written.

admins ​

admins.userIds ​

  • Type: string[]
  • Default: [] (no admins: every admin route answers 404)
  • Limits: a list of user ids, each of 1 to 64 printable ASCII characters (U+0021 to U+007E)
  • Description: The user ids of the admins, checked on the server on every request to the admin routes under {basePath}/admin/. With the list empty those routes do not exist and answer 404 for every method; a user whose id is not listed gets the same 404. Admin status is never read from a token, and the list never reaches the browser. Changing it needs a deploy. A signed-in user can read their own id as user.id in the answer of GET {basePath}/me.

hub ​

hub.enabled ​

  • Type: boolean
  • Default: false
  • Limits: true or false; true needs an appId that is not a URL origin, such as my-hub, and a publicUrl whose host does not end in a dot
  • Description: Hub mode: this deployment also becomes a small OpenID provider that other Evo Auth apps sign in through, so each sign-in provider is set up once. Off by default, and with it off nothing changes. With it on, appId must be set to a name that is not a URL origin, so the hub's own access tokens and the id_tokens it gives apps never share an audience, and the host of publicUrl must not end in a dot, so the hub's own origin has one spelling. With more than one provider in providers, a person signing in at the hub picks one on the hub's sign-in page. It adds the routes GET {basePath}/oidc/authorize, POST {basePath}/oidc/token and GET {basePath}/.well-known/openid-configuration.

hub.allowedClients ​

  • Type: string[]
  • Default: [] (no site may use the hub)
  • Limits: a list of entries, each an exact callback address written as a URL parser writes it back, with a path other than / and no query, fragment, user information or dot at the end of the host: on an https origin or an http origin on localhost or 127.0.0.1; https://*.<parent>/<path> where <parent> is the host of publicUrl without its first label, publicUrl is https and <parent> has two labels or more, and the star stands for exactly one label (no port); or http://localhost/\<path> or http://127.0.0.1/\<path>, which match that host on any port. An origin alone is refused
  • Description: The sites that may sign in through the hub, by the exact callback address the hub sends each one's code to. An app's client id is its own origin and it has no secret; its entry here is its callback address, {publicUrl}/{provider id}/callback, such as https://notes.example.com/auth/evo/callback for an app using evoHub() with its default id, which evo-auth check on the app prints. The hub accepts a sign-in request only from a client an entry matches, sends its code only to that entry's address exactly (no other path, no added query, no trailing slash), and never accepts its own origin, whatever the list says. A wildcard may cover only the hub's own parent domain: for a hub at https://auth.example.com, https://*.example.com/auth/evo/callback is accepted and matches https://notes.example.com/auth/evo/callback, and every other site is listed exactly. Use a wildcard only for a domain you own: on a shared hosting name, such as a hub at https://my-hub.vercel.app listing https://*.vercel.app, it lets every app anyone hosts there sign in through the hub, and evo-auth check warns about every wildcard. Empty by default, which refuses every site: without the list any site could use the hub's provider apps to sign people in and receive their identity. Read only when hub.enabled is true.

passkeys ​

passkeys.enabled ​

  • Type: boolean
  • Default: false
  • Limits: true or false
  • Description: Passkeys: a signed-in user can add a passkey (WebAuthn) from their profile, then sign in or confirm their identity with it. Off by default, and with it off nothing changes. A passkey is added to an existing account after a recent confirmation, like linking a provider account, unless passkeys.signUp is on, when a new person can also sign up with an email address and a passkey. A user's accounts and passkeys count together as their ways to sign in, so the last one cannot be removed, by the user or by an admin.

passkeys.signUp ​

  • Type: boolean
  • Default: false
  • Limits: true or false
  • Description: Passkey sign-up: a new person can sign up with an email address and a passkey, and never sets a password. The address is proved first by an emailed code, or a link while emailAuth.link is on, and the account is created only in the step that stores the passkey, so a half-finished sign-up leaves no account behind. Adds POST {basePath}/passkeys/sign-up/start, /passkeys/sign-up/options and /passkeys/sign-up/verify. Needs passkeys.enabled, emailAuth.signUp (so one switch still stops every kind of sign-up), email.sender, and at least one of emailAuth.code, emailAuth.link and emailAuth.password, so a person who signed up this way has a way back by email if the passkey is lost. Off by default.

passkeys.rpId ​

  • Type: string
  • Default: the host name of publicUrl
  • Limits: a lower-case host name that equals the host name of publicUrl or is a parent domain of it (a suffix after a dot) with at least two labels; a parent domain only when the host of publicUrl is a name, not an IP address; at most 253 characters
  • Description: The relying party id passkeys are bound to. The browser lets a passkey be used only on this host name and the ones under it, so set it to a parent domain, such as example.com for a publicUrl at https://auth.example.com/auth, only when passkeys made here must also work on its other subdomains. Changing it later makes every passkey already added unusable. Checked at start-up whenever it is set, and used only when passkeys.enabled is true.

organizations ​

organizations.enabled ​

  • Type: boolean
  • Default: false
  • Limits: true or false; true needs organizations.invitationUrl
  • Description: Organisations: groups of the app's users, each member with a role from organizations.roles. Off by default, and with it off nothing changes. Every organisation keeps at least one member whose role holds org:memberships:manage, so a change of role, a removal or a leaving that would leave none is refused, whoever asks.

organizations.roles ​

  • Type: Record<string, Role>
  • Default: { admin: { label: "Admin", permissions: the five system permissions }, member: { label: "Member", permissions: ["org:memberships:read"] } }
  • Limits: an object mapping each role key (a lower-case letter, then lower-case letters, digits, - and _, at most 32 characters) to { label, permissions }: a label of 1 to 64 characters with no control character, and a list of at most 32 different permissions, each one of the five system permissions (org:profile:manage, org:profile:delete, org:memberships:read, org:memberships:manage, org:invitations:manage) or an app permission feature:action in lower-case letters, digits, - and _, each part starting with a letter, neither part org, at most 48 characters; at least one role
  • Description: The roles a member of an organisation can have and what each may do. Core checks the five system permissions; an app checks its own feature:action permissions. Roles live here, not in the database, so a change takes effect at the next deploy: a membership whose role is no longer listed holds no permissions until it is given another, and evo-auth-server check reports such memberships. Both evo-auth check and evo-auth-server check print a fingerprint of the roles, so two configs, such as the issuer's and a verifier's, can be compared by it. While organisations are on, each role's key and label reach the browser in publicConfig, so labels are public: a signed-out visitor can see them. Permissions are never sent there.

organizations.creatorRole ​

  • Type: string
  • Default: admin
  • Limits: a key of organizations.roles whose role holds org:memberships:manage
  • Description: The role the user who creates an organisation is given. It must hold org:memberships:manage, so every organisation starts with a member who can manage its members.

organizations.creation ​

  • Type: string
  • Default: anyone
  • Limits: anyone or admins
  • Description: Who may create an organisation: anyone signed in, or admins, the users in admins.userIds. The server API may create one for any user either way. Creations are counted per user in the organization_create rate-limit bucket.

organizations.invitationUrl ​

  • Type: string
  • Default: none (required while organizations.enabled is true)
  • Limits: a relative path starting with exactly one / (not // or /\), with no backslash, only visible ASCII characters (U+0021 to U+007E; percent-encode any other character) and no . or .. segment before any ? or #, plain or written with %2e or %2E, or an absolute http or https URL with no user name or password, written exactly as a URL parser writes it back (lower-case scheme and host, the host in its ASCII (xn--) form, no default port, no dot segments, a / before any ? or #, and non-ASCII characters in the path, query and fragment percent-encoded; a bare origin may leave out the final /), whose origin is in allowedRedirectOrigins; no spaces, other whitespace or control characters; at most 2,048 characters
  • Description: The page of the app where a person opens an invitation link to join an organisation: an invitation's link is this address with the invitation token added. Required while organizations.enabled is true.

email ​

email.sender ​

  • Type: EmailSender
  • Default: none (no email is sent)
  • Limits: a function (message, { signal, deadline }) => Promise<void>, or on Convex a reference to one of the app's actions, such as internal.email.send; required while any emailAuth setting is true
  • Description: Sends the email Evo Auth writes: sign-in codes and links, the codes of sign-up, password reset and adding an address, the note to an address that already has an account, and invitations sent to an address. Core never sends mail itself and holds no mail account or key: the sender keeps those in its own closure. On Convex give a reference to one of the app's actions, which is run with ctx.runAction and passed the message as its arguments. A code or link is sent by the email job after the route that asks for it, such as POST {basePath}/email/sign-in/code, has answered, never during the request, so how long the answer takes cannot tell which addresses have accounts: the job decides whether the address gets a message, saves the hashes of what it sends, then calls the sender. On the Node server the job runs in the server's job runner; on Convex it is the app's own action, set up with two lines: export const emailJob = createEmailJob(components.evoauth, { config }) in a file such as convex/auth.ts, and registerRoutes(http, components.evoauth, { config, emailJob: internal.auth.emailJob }). An invitation sent to an address is sent in the request, after the invitation is saved. An error the sender throws is logged as email.send_failed and is not retried, and the answer to the request does not change. A send is waited for at most 30 seconds: then the signal the sender was given is aborted and the send is logged as email.send_failed, with no retry, so a mail service that hangs holds up nothing behind it. A sender function is given signal, as on the Node server, and may pass it to its fetch. On Convex the app's sender action cannot be given a signal or be cancelled, so this is a limit of the Convex adapter: the action is passed deadline instead, the time in milliseconds since the epoch at which Evo Auth stops waiting, from which it can set its own request timeout. On Convex the email job runs at most once, so a storage failure inside it is not retried and that one message is lost; the person asks for a new code. The message holds type, to, subject, text, html, and code, url and expiresAt when it has them: the code and the link sign someone in, so the sender must not log them. The one sender that may is devConsoleSender(), for local development: it sends nothing and writes each message's code and link to the auth side's log, so a first sign-up needs no mail account. validateConfig refuses it unless cookies.devMode is on, and each send refuses unless the host says the auth side is local: evo-auth-server once listen() has bound a loopback address (never a handler the app mounts and serves with only start()), and the Convex adapter when the deployment's CONVEX_CLOUD_URL is on a loopback host (a local backend), since a cloud deployment made by npx convex dev runs the same config with devMode on. A host says so through the optional localAuthSide member of auth.handler's and auth.sendEmailChallenge's context. A refused send is logged as email.send_failed, with no code.

email.templates ​

  • Type: EmailTemplates
  • Default: none (the built-in templates)
  • Limits: an object whose keys are message types (sign_in, sign_up, verify_address, reset_password, existing_account_notice, password_disabled, reverify, invitation), each an object of up to three functions subject, text and html, each taking the message's details and returning text
  • Description: Replaces parts of the built-in messages: each function given replaces the part of the same name for that type and leaves the others. Every message keeps a plain-text part (empty text falls back to the built-in text) and the code never goes in the subject (a subject holding it falls back to the built-in subject). An html function must escape what it puts in the HTML.

emailAuth ​

emailAuth.code ​

  • Type: boolean
  • Default: false
  • Limits: true or false; true needs email.sender
  • Description: Sign-in by a 6-digit code sent by email, typed in the browser that asked for it. The code lasts 10 minutes, works once, and 5 wrong tries void it. Signing in by an emailed code is not NIST-grade (NIST SP 800-63B-4 does not allow email for out-of-band authentication); it is offered because most sign-in products offer it and anyone with the mailbox can already reset a password. Adds POST {basePath}/email/sign-in/code and POST {basePath}/email/verify.

emailAuth.link ​

  • Type: boolean
  • Default: false
  • Limits: true or false; true needs email.sender
  • Description: Sign-in by a link sent by email, to the app's signInUrl with ?evo_email_link= and a token. It completes only in the browser that asked for it, and only when the page's button is pressed, so a mail scanner that opens links cannot use it up. It lasts 10 minutes and works once; with emailAuth.code on, the same message carries both. Adds POST {basePath}/email/sign-in/code and POST {basePath}/email/verify-link.

emailAuth.signUp ​

  • Type: boolean
  • Default: false
  • Limits: true or false; true needs email.sender
  • Description: Whether an email code or link may make a new account. Off: only an address that already has an email account gets a message, and an unknown address gets the same answer and no email. On: the code or link for an unknown address makes the user and the email account when it is used. Either way no account exists until the address is proven, and an email account is never joined to another account because the address matches.

emailAuth.password ​

  • Type: boolean
  • Default: false
  • Limits: true or false; true needs email.sender and the EVO_AUTH_PASSWORD_PEPPER variable
  • Description: Sign-in by email address and password. Passwords are hashed with PBKDF2-HMAC-SHA256 at 600,000 iterations and a pepper, EVO_AUTH_PASSWORD_PEPPER, which evo-auth init writes, with or without --server; if the pepper leaks, replacing it means every user resets their password. Adds POST {basePath}/email/sign-in/password, the reset by email (POST {basePath}/email/reset/request and POST {basePath}/email/reset/complete), setting or changing the password of a signed-in user (POST {basePath}/email/password/change), adding an address to a signed-in user (POST {basePath}/email/add and POST {basePath}/email/add/verify), and, with emailAuth.signUp on, POST {basePath}/email/sign-up, which makes nothing until the emailed code is used. 10 failed sign-ins in 15 minutes stop sign-in for the address for a while, and 100 in a row turn the password off until it is reset by email.

password ​

password.minLength ​

  • Type: integer
  • Default: 15
  • Limits: a whole number from 8 to 128
  • Description: The fewest characters a password may have, each Unicode code point counting as one; the most is 128. NIST SP 800-63B-4 asks for 15 when the password is the only factor and allows 8 when it is one of several. There are no composition rules. Applies only while emailAuth.password is true.

password.breachCheck ​

  • Type: boolean
  • Default: true
  • Limits: true or false
  • Description: Refuses a new password that appears in Have I Been Pwned's Pwned Passwords list. Only the first 5 hex characters of the password's SHA-1 leave the server, with padding asked for, and the service needs no account. When it cannot be reached the check is skipped and password.breach_check_unavailable is logged. Applies only while emailAuth.password is true.

usernames ​

usernames.enabled ​

  • Type: boolean
  • Default: false
  • Limits: true or false; true needs emailAuth.password
  • Description: Sign-in by username: a person with an email account may choose a username on their account page and sign in with it and their password where they would type their address. A username is a second name for the email account's password, not a new secret: 3 to 30 letters, digits, dots, dashes or underscores, lower-cased, starting and ending with a letter or digit, never all digits and never holding @, so one sign-in field takes either an address or a username. Adds POST {basePath}/username/sign-in and POST {basePath}/account/username, and GET {basePath}/me carries the name. POST {basePath}/email/sign-up takes an optional username, set when the code or link is verified if no one holds it by then; no answer before that says whether it is taken. Usernames are public: anyone willing to make accounts can learn which names are taken, and anyone who sees a username can use up that person's password to its 100-failure ceiling, which a reset by email clears. Off: both routes answer the generic 404, a sign-up that carries username is refused, and names already chosen stay stored and come back into force when it is turned on again. Needs emailAuth.password.

usernames.reserved ​

  • Type: string[]
  • Default: [] (the built-in list only)
  • Limits: a list of at most 200 names, each passing the username rule
  • Description: Names no one may choose, added to the built-in list: admin, administrator, root, system, support, help, security, staff, moderator, owner, api, auth, login, signin, signup, logout, settings, account, www, mail, null and undefined. Names are compared lower-cased with dots, dashes and underscores removed, so ad.min is reserved too. The list applies to new choices only: a name someone already holds stays theirs.

secondFactor ​

secondFactor.enabled ​

  • Type: boolean
  • Default: false
  • Limits: true or false; true needs the EVO_AUTH_SECOND_FACTOR_KEY variable
  • Description: Two-step sign-in: a signed-in user may turn on a second step for themselves, a 6-digit code from an authenticator app, with ten single-use backup codes for when the app is lost. Adds POST {basePath}/second-factor/totp/start and /second-factor/totp/confirm (turn it on, or replace the authenticator), /second-factor/backup-codes/regenerate, /second-factor/remove, and, with admins listed, POST {basePath}/admin/user/second-factor/remove for a person who has lost both. At sign-in, a user who has one gets no session from the first factor: it answers the pending step (JSON routes answer secondFactor; a provider's callback goes to signInUrl with ?evo_step=second_factor) and GET {basePath}/signin/second-factor, POST {basePath}/signin/second-factor/verify (an authenticator code, a backup code or, with passkeys.enabled, a passkey) and POST {basePath}/signin/second-factor/cancel complete or end it within 10 minutes and 5 wrong attempts. A passkey sign-in is never asked for a second step. Each change needs a recent confirmation of identity, and a notice email goes to the user's email account when email.sender is set. The secrets are sealed under EVO_AUTH_SECOND_FACTOR_KEY. Off: the routes answer the generic 404 and a second factor already set up is not asked for; evo-auth-server check warns while users still have one.

secondFactor.required ​

  • Type: boolean
  • Default: false
  • Limits: true or false; true needs secondFactor.enabled
  • Description: Every user must have a second factor: one who has none is taken through setting up an authenticator during sign-in, before they get a session; a passkey also counts. A user may still turn their own second factor off, and is then taken through set-up at their next sign-in. NIST SP 800-63B-4 allows password.minLength 8 only when a second factor is required; the minimum does not change by itself.

providers ​

  • Type: Provider[]
  • Default: none; the setting is required
  • Limits: a list of plain provider objects whose own data members are a unique id (a lower-case letter, then 1 to 31 lower-case letters or digits), kind oauth2 or oidc, a label (non-empty text with no control character), the functions authorizationUrl, exchangeCode and fetchProfile, and optionally endpoints, a list of absolute https URLs with no user name, password, query or fragment (http on a loopback host needs cookies.devMode), and icon, { light, dark?, shape? }, light and dark each a data:image/svg+xml or data:image/png URI of at most 8192 characters and shape mark, square or full
  • Description: The enabled sign-in providers, for example [github()], or a provider object the app writes itself. Each provider's client id and secret are the variables EVO_AUTH_{ID}_CLIENT_ID and EVO_AUTH_{ID}_CLIENT_SECRET, with its id in upper case.

Environment variables ​

Every variable appears once, in the order the definition lists it.

EVO_AUTH_SECRET ​

  • Read by: auth (required)
  • Holds a secret: yes
  • Purpose: The master secret. Its decoded bytes are the HKDF input for every internal key: the client-address HMAC key, the sign-in cookie key and the refresh MAC key.
  • Strength rule: base64url text without padding that decodes to at least 32 bytes; generate 32 random bytes

EVO_AUTH_PROXY_SECRET ​

  • Read by: proxy (required), auth (not required)
  • Holds a secret: yes
  • Purpose: Shared by the auth deployment and the app's proxy only. When set on the auth side, every request must carry it in X-Evo-Proxy-Secret and the client address is read only from X-Evo-Client-IP. The proxy role requires it. The auth role reads it when it is set and does not refuse to start without it, but on Convex, outside the development cookie mode, every auth route answers unavailable until it is set.
  • Strength rule: base64url text without padding that decodes to at least 32 bytes, the rule of EVO_AUTH_SECRET, and it must differ from EVO_AUTH_SECRET; fromEnv refuses it otherwise

EVO_AUTH_PASSWORD_PEPPER ​

  • Read by: auth (not required)
  • Holds a secret: yes
  • Purpose: The pepper of every password hash: an HMAC-SHA256 over the PBKDF2 output is keyed by it, so a copy of the database alone cannot be used to guess passwords. Required while emailAuth.password is true; createAuth refuses to start without it. It is its own variable, not derived from EVO_AUTH_SECRET, which can be replaced. If it leaks, replacing it means every user resets their password.
  • Strength rule: base64url text without padding that decodes to at least 32 bytes, the rule of EVO_AUTH_SECRET, and it must differ from EVO_AUTH_SECRET; generate 32 random bytes

EVO_AUTH_SECOND_FACTOR_KEY ​

  • Read by: auth (not required)
  • Holds a secret: yes
  • Purpose: The key every authenticator secret and every backup code is sealed under, through an HKDF label of its own. Required while secondFactor.enabled is true; createAuth refuses to start without it, and with the setting off nothing reads it. It is its own variable, not derived from EVO_AUTH_SECRET, so replacing the master secret does not lock anyone out. To replace this key without locking anyone out, set EVO_AUTH_SECOND_FACTOR_KEY_PREVIOUS to its old value first and run the reseal (docs/rotating-secrets.md).
  • Strength rule: base64url text without padding that decodes to at least 32 bytes, the rule of EVO_AUTH_SECRET, and it must differ from EVO_AUTH_SECRET and from EVO_AUTH_PASSWORD_PEPPER; generate 32 random bytes

EVO_AUTH_SECOND_FACTOR_KEY_PREVIOUS ​

  • Read by: auth (not required)
  • Holds a secret: yes
  • Purpose: The second-factor key being replaced, set only while the key is rotated: authenticator secrets and backup codes sealed under it still open, each successful use moves that user's values to EVO_AUTH_SECOND_FACTOR_KEY, and the reseal moves the rest. Read only while secondFactor.enabled is true, and by the reseal whatever the setting. Remove it once the reseal reports 0 and 0; evo-auth check and evo-auth-server check warn while it is set.
  • Strength rule: the rule of EVO_AUTH_SECOND_FACTOR_KEY: base64url text without padding that decodes to at least 32 bytes, different from EVO_AUTH_SECRET and from EVO_AUTH_PASSWORD_PEPPER; it may equal EVO_AUTH_SECOND_FACTOR_KEY while the rotation starts

EVO_AUTH_SIGNING_KEY ​

  • Read by: auth (required)
  • Holds a secret: yes
  • Purpose: The active private signing key for access tokens. Its kid is recomputed as the RFC 7638 thumbprint.
  • Strength rule: an ES256 (P-256) private key as a JWK whose public part is in EVO_AUTH_PUBLIC_KEYS

EVO_AUTH_STAGED_SIGNING_KEY ​

  • Read by: no role
  • Holds a secret: yes
  • Purpose: The private key evo-auth keys rotate stages, until evo-auth keys activate <kid> makes it EVO_AUTH_SIGNING_KEY. After activation it holds the previous signing key, so the printed rollback command works until that key's removeAfter. No library role reads it, and it is never sent to a deployment.
  • Strength rule: none stated
  • Note: the command line writes this variable; it does not go in .env.example.

EVO_AUTH_PUBLIC_KEYS ​

  • Read by: render (required), auth (required)
  • Holds a secret: no
  • Purpose: The public key set: the active key plus any retiring ones, each retiring key with a removeAfter time. Published at {publicUrl}/.well-known/jwks.json.
  • Strength rule: a JSON list of ES256 (P-256) public JWKs that contains the active key

EVO_AUTH_{ID}_CLIENT_ID ​

  • Read by: auth (required); read only when the {id} provider is enabled
  • Holds a secret: no
  • Purpose: The client id of the OAuth app registered with one provider. {ID} is the provider's id in upper case, so github() reads EVO_AUTH_GITHUB_CLIENT_ID and a provider with id acme reads EVO_AUTH_ACME_CLIENT_ID. Required for each provider in providers, read only for those.
  • Strength rule: none stated

EVO_AUTH_{ID}_CLIENT_SECRET ​

  • Read by: auth (required); read only when the {id} provider is enabled
  • Holds a secret: yes
  • Purpose: The client secret of the OAuth app registered with one provider. {ID} is the provider's id in upper case, so github() reads EVO_AUTH_GITHUB_CLIENT_SECRET and a provider with id acme reads EVO_AUTH_ACME_CLIENT_SECRET. Required for each provider in providers, read only for those.
  • Strength rule: none stated
