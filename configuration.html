Configuration notes ​

This page is for a developer writing the config object. It explains how the config is made and shared, and records the rules that the generated tables cannot show. Every setting, its type, default and limits are on the generated configuration reference, and every error code is on the error reference. This page does not repeat them.

One config, made once ​

ts
import { github, validateConfig } from "@evo-auth/core";

export const authConfig = validateConfig({
  publicUrl: "https://app.example.com/auth",
  providers: [github()],
});

validateConfig checks the input, fills the defaults and returns the config. Only that returned object is accepted by createAuth, createAuthProxy, createGetAuth, registerRoutes, authConfigProvider, createAuthApi, getEvoIdentity and publicConfig. Anything else is refused. isValidatedConfig(value) tells you whether a value is one.

Put the config in one module that every part of your app imports. The proxy and the auth endpoints then agree on basePath, the cookie names and the development cookie mode, because they read them from the same object. The module must read no environment variable and hold no secret. Secrets are EVO_AUTH_* variables, read through fromEnv: see the variables and, for where each one is set, the Convex guide.

A bad config throws a ConfigError that names the setting and the rule, never a value. A bad or missing variable throws a SecretsError that names the variable.

publicUrl and basePath ​

publicUrl is the address the browser uses for the auth endpoints: your site's origin followed by basePath. It is used exactly as written as the token issuer, as the base of each provider callback ({publicUrl}/{id}/callback) and as the JWKS address ({publicUrl}/.well-known/jwks.json). It must equal what a URL parser would write back (lower-case scheme and host, no default port), and its path must equal basePath. appId defaults to the origin of publicUrl and is the token's audience.

appName is your app's name as people see it, such as "Fernhill": 1 to 64 characters, with no control character. Every email Evo Auth sends shows it in its header, heading, subject and button ("Your Fernhill sign-in code"), and the page a sign-in link opens is titled "Sign in to Fernhill". It is optional; while it is unset the host name of publicUrl stands in, such as app.example.com.

Lengths matter. publicUrl and appId are at most 256 characters each, and a user id is at most 64 ASCII characters. A storage adapter with longer ids fails the shared contract suite. These bounds keep the session cookie within 4,096 bytes.

cookies.prefix has no length limit, and the session cookie's 4,096-byte bound holds for the default prefix or a short one. If you choose a long prefix, you take on that check.

Changing basePath to a path nested under the old one signs each user out once: the browser then sends both refresh values and a valid old one counts as reuse.

Where the settings take effect ​

  • session.lifetimeSeconds: how long a session lasts from sign-in, and the refresh cookie's lifetime.
  • accessToken.lifetimeSeconds: how long a token is valid. A revoked session's tokens keep working in your Convex functions until they expire.
  • refresh.reuseGraceSeconds: the grace window. At 0 the window is off, and any lost response ends the session.
  • authEvents.retentionSeconds: changing it rewrites neither the auth event rows already written nor the purgeAt of session rows already written. They keep the values set when they were written.
  • rateLimits.*: per-bucket limits. callback_refusal and self_read count per client address, session_refresh, self_service, admin_read and admin_write per session, sign_in_account per provider account. The email buckets are email_send, password_sign_in_address and email_sign_up per client address, and email_recipient and password_sign_in_account per email address, kept only as a hash. They count only while an email setting is on (see Email and Email and password).
  • allowedOrigins guards POSTs (the CSRF check); allowedRedirectOrigins is a separate list for absolute redirects after sign-in.

The routes ​

Everything the auth endpoints answer is under basePath, matched exactly: no trailing slash, no doubled slash, no percent-encoded segment and no other letter case. A route that reads no query refuses a path that carries one. A provider route exists only for a provider id the config lists. Anything else is not_found.

Method and pathPurpose
GET {basePath}/{provider}/startStarts the sign-in. Reads redirect and intent.
GET {basePath}/{provider}/callbackThe provider's callback.
POST {basePath}/{provider}/callbackOnly for a provider whose service answers by form POST (response_mode=form_post): sends the browser on to the GET callback with the code and state. See Sign-in providers.
GET {basePath}/handshakeRotates the refresh token for a page request and redirects back once. Reads redirect.
POST {basePath}/tokenGives the browser a fresh access token.
POST {basePath}/signoutSigns out this session.
GET {basePath}/meThe signed-in user, with accounts.
GET {basePath}/sessionsThe user's live sessions.
POST {basePath}/sessions/revokeRevokes one of the user's sessions.
POST {basePath}/sessions/revoke-allEnds every session of the user, this one included.
POST {basePath}/account/deleteDeletes the account after a recent confirmation with the provider.
GET {basePath}/.well-known/jwks.jsonThe public keys.
POST {basePath}/email/...Sign-in by an emailed code or link, sign-up, password sign-in, reset, and changing a password or address. Each route exists only while the setting that adds it is on: see Email and Email and password.
POST {basePath}/passkeys/sign-up/start, /options, /verifySigning up with an address and a passkey. They exist only while passkeys.signUp is on: see Passkeys.
POST {basePath}/username/sign-in, POST {basePath}/account/usernameSigning in with a username and a password, and choosing, changing or removing one. They exist only while usernames.enabled is on: see Email and password.
{basePath}/second-factor/..., {basePath}/signin/second-factor/...Two-step sign-in: set-up, backup codes, turning it off, confirming identity with a code, and the second step at sign-in. They exist only while secondFactor.enabled is on: see Two-step sign-in.

HEAD and OPTIONS are not in any entry: there is no CORS, so they answer 405 with an Allow header. The JWKS body is fixed when createAuth runs, so a key past its removeAfter stays published until a host that builds createAuth once restarts.

Admins ​

admins.userIds lists the user ids of your admins. It is empty by default, and then the admin routes under {basePath}/admin/ do not exist: every method on them answers 404. Each entry is a user id of 1 to 64 printable ASCII characters. The list is read on the server on every admin request and never reaches the browser.

To make yourself an admin:

  1. Sign in to your app and open the page with UserProfile (or the profile in UserButton's menu). Your user id is under your name; copy it with the button beside it. It is also user.id in the answer of GET {basePath}/me.

  2. Add that id to admins.userIds in the module that builds your config, the one both your server and your Convex functions import, and deploy:

    ts
    export const authConfig = validateConfig({
  publicUrl: "https://app.example.com/auth",
  providers: [github()],
  admins: { userIds: ["<your user id>"] },
});

  3. Your requests to the admin routes now pass the admin check, and a page that mounts AdminPanel shows you the users. Anyone else still gets 404, and the page shows them only "Not available".

Removing an admin also needs a deploy, and an admin cannot ban, unban, delete or revoke the sessions of another listed admin, or their own. With secondFactor.enabled on, an admin can also remove a user's second factor, for someone locked out (Two-step sign-in). The routes are described in Server API and their protections in the security model.

publicConfig ​

publicConfig(config) gives the browser exactly thirteen fields: basePath, signInUrl, afterSignOutUrl, uatCookieName, loopGuardParam, providers (id, label and the tile picture when there is one), passkeys, passkeySignUp, organizations, emailAuth, usernames, emailDelivery and appName (null while it is unset), and two more that appear only while their setting is on. While emailAuth.password is true, password: { minLength, breachCheck } as configured, so the password field can say how long a password must be and whether it is checked for data breaches; without it the screens use 15 and show no breach line. While secondFactor.enabled is true, secondFactor: { enabled, required }; an absent member means two-step sign-in is off. Call it on the server and pass the result to AuthProvider as data. It refuses a config validateConfig did not return.

Email and passwords ​

Signing in by an emailed code or link, and by a password, is off until you turn it on. email.sender is the function that delivers every email Evo Auth writes, and the four emailAuth booleans (code, link, signUp and password) all default to false. Any that is on needs email.sender, and password also needs the EVO_AUTH_PASSWORD_PEPPER variable. password.minLength and password.breachCheck set the password rules. The guides are Email and Email and password; every setting's type and limits are on the reference.

Usernames ​

usernames.enabled, false by default, lets a person choose a username in the profile, or when signing up with a password, and sign in with it and their password instead of their address. validateConfig refuses it without emailAuth.password. usernames.reserved adds up to 200 names nobody may choose to the built-in ones; validateConfig refuses an entry that does not follow the username rule, naming its place in the list and never the value. See Email and password.

Passkeys ​

passkeys.enabled lets a signed-in user add passkeys, and passkeys.signUp lets a new person sign up with an address and a passkey. validateConfig refuses passkeys.signUp without passkeys.enabled, emailAuth.signUp and email.sender, and without at least one of emailAuth.code, emailAuth.link and emailAuth.password, naming the setting and what it needs. See Passkeys.

Two-step sign-in ​

secondFactor has two booleans, both false by default. secondFactor.enabled lets users turn on a second step for themselves: an authenticator app's 6-digit code, with ten backup codes. secondFactor.required makes every user have one, and validateConfig refuses it without enabled. While enabled is on, createAuth refuses to start without EVO_AUTH_SECOND_FACTOR_KEY. That variable is its own, not derived from EVO_AUTH_SECRET, and replacing it asks nothing of your users: the old value goes in EVO_AUTH_SECOND_FACTOR_KEY_PREVIOUS while a reseal moves everyone to the new key (Rotating secrets has the steps). evo-auth init writes it, and evo-auth check and evo-auth-server check report it by name (see The command line). The second step follows every first factor except a passkey. Two-step sign-in has the rest.

Providers ​

providers lists the enabled sign-in providers: any of the twelve named ones (github(), google(), microsoft(), apple(), gitlab(), slack(), twitch(), linkedin(), discord(), facebook(), x() and spotify(), with their options on The twelve named providers), or a provider object you write yourself (see Sign-in providers). validateConfig checks each one's shape, whichever way it was made, and refuses two with the same id.

A provider's id is a lower-case letter followed by 1 to 31 lower-case letters or digits, and its client id and secret are the variables EVO_AUTH_{ID}_CLIENT_ID and EVO_AUTH_{ID}_CLIENT_SECRET, with the id in upper case. So github() reads EVO_AUTH_GITHUB_CLIENT_ID and EVO_AUTH_GITHUB_CLIENT_SECRET, and a provider with id acme reads EVO_AUTH_ACME_CLIENT_ID and EVO_AUTH_ACME_CLIENT_SECRET. Two named providers differ from their function name: x() has the id twitter, so it reads EVO_AUTH_TWITTER_CLIENT_ID and EVO_AUTH_TWITTER_CLIENT_SECRET, and apple() reads EVO_AUTH_APPLE_CLIENT_ID and EVO_AUTH_APPLE_PRIVATE_KEY. Only the auth role reads them, the first time createAuth asks for that provider, and createAuth refuses to start while either is missing for a configured provider. See Register a GitHub OAuth app. The label on the sign-in button comes from the provider (GitHub); to change the text, use the React strings.

Hub mode ​

Hub mode makes one Evo Auth deployment a shared sign-in server: a small OpenID provider that your other Evo Auth apps sign in through, so each sign-in provider is set up once, at the hub. Two settings control it, and both are off or empty by default; with hub.enabled unset or false, nothing about a deployment changes.

  • hub.enabled switches hub mode on. While it is true, appId must be set to a name that is not a URL origin, such as my-hub. appId is the audience of the hub's own access tokens and defaults to the origin of publicUrl; the id_tokens the hub gives apps carry the app's origin as their audience, and refusing an origin as appId keeps the two audiences from ever meeting. The host of publicUrl must not end in a dot (https://auth.example.com./auth), so the hub's own origin has one spelling. With more than one provider in providers, a person signing in at the hub picks one on the hub's sign-in page; with one, the hub goes straight to it.

  • hub.allowedClients lists the sites that may sign in through the hub, each by the exact callback address the hub sends its code to. An app's client id is its own origin and it has no secret; its entry is its {publicUrl}/{provider id}/callback, such as https://app.example.com/auth/evo/callback for an app using evoHub() with its default id, which evo-auth check on the app prints. The list is empty by default, which refuses every site. Each entry is one of:

    • an exact callback address, such as https://app.example.com/auth/evo/callback, written as a URL parser writes it back (lower-case host, no default port, a path other than /, no query, fragment or user name, no dot at the end of the host); plain http only on localhost or 127.0.0.1, with its port written;
    • a wildcard address over the hub's own parent domain only: for a hub at https://auth.example.com, https://*.example.com/auth/evo/callback, where the star stands for exactly one label, so it matches https://notes.example.com/auth/evo/callback, and not https://example.com or https://a.b.example.com; it takes no port. A wildcard over any other domain is refused (https://*.com/..., https://*.co.uk/..., https://*.convex.site/...), and so is every wildcard for a hub that is not https, sits on an IP address or a single-label host, or whose parent would be a single label (a hub at example.com): list such sites exactly;
    • http://localhost/<path> or http://127.0.0.1/<path> with no port, which match that host over http on any port, with that exact path.

    An origin alone, such as https://app.example.com, is refused with a message naming the callback address form, and so is any other entry, at start-up, naming hub.allowedClients and its position. A redirect_uri must equal a matching entry exactly, with a wildcard's host or a loopback entry's port taken from the client id: another path, an added query, a trailing slash or another spelling of the same address is refused on the hub's refused-site page. Whatever the list says, the hub never accepts its own origin, the origin of publicUrl, as a client, nor a client id whose host ends in a dot.

    Use a wildcard only for a domain you own. The wildcard rule cannot tell auth.example.com from a hub on a shared hosting name: a hub at https://my-hub.vercel.app may list https://*.vercel.app, and then every app anyone hosts there can sign people in through your hub (myhub.co.uk with https://*.co.uk is the same case). evo-auth check prints a warning for every wildcard in the list, naming the domain it covers; it is a warning, not a problem, and does not change the exit code.

With hub mode on, three routes join the table, and with it off they are missing routes like any other path:

Method and pathPurpose
GET {basePath}/oidc/authorizeAn app sends the person here to sign in. A request from a site the list does not allow, or with a redirect_uri that is not exactly a callback address listed for that site, is refused on a page of the hub's own (error code invalid_request) that quotes nothing of the request and is never sent back to the site. With the site allowed, other mistakes go back to its redirect_uri with error=invalid_request, and a request object with error=request_not_supported (request) or error=request_uri_not_supported (request_uri), never read. A person not signed in to the hub signs in at the hub first: with one provider straight away, with more than one by picking a provider on the hub's sign-in page, which names only the requesting site's origin and has a Cancel link back to the site with error=access_denied. One already signed in gets a code at once. prompt=login, max_age=0, or a max_age older than their last sign-in at the hub makes them confirm again first with the provider of their primary account, the one they linked first; if that does not renew their sign-in at the hub, the site gets error=login_required instead of a code. With prompt=none the hub shows no page: a person not signed in, or who would need to sign in again, sends the site error=login_required.
POST {basePath}/oidc/tokenThe app's server exchanges the one-time code for an id_token. It is called without an Origin header; one that is not the app's own origin is refused. A malformed request is 400 invalid_request; a code that is unknown, used, expired, or presented with another client, redirect_uri or verifier is 400 invalid_grant.
GET {basePath}/.well-known/openid-configurationThe hub's discovery document, which evo-auth check in an app compares with evoHub().

Each refused request to the first two counts toward a bucket (rateLimits.authorize and rateLimits.token, 20 in 600 seconds by default); a sign-in that succeeds never counts. authorize is per client address. token is per app and client address: the address is the app server's, so a stranger whose code shares that outgoing address (common on shared hosting) can lock out only the app they name, and a request naming a site not on the list counts per address alone and locks out no listed app. Every answer on the three paths carries Content-Security-Policy: frame-ancestors 'none'.

ts
export const authConfig = validateConfig({
  publicUrl: "https://auth.example.com/auth",
  appId: "my-hub",
  providers: [github()],
  hub: { enabled: true, allowedClients: ["https://*.example.com/auth/evo/callback", "https://notes.example.org/auth/evo/callback", "http://localhost/auth/evo/callback"] },
});
