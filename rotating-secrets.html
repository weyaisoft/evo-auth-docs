Rotating secrets ​

This page is for the person who replaces EVO_AUTH_SECRET (the master secret), EVO_AUTH_PROXY_SECRET (the secret shared by the proxy and the auth endpoints), EVO_AUTH_PASSWORD_PEPPER (the pepper of password hashes) or EVO_AUTH_SECOND_FACTOR_KEY (the key of two-step sign-in). Signing keys are separate: see rotating the signing keys.

None of the four has a command that replaces it. You make a new value and set it where the old one is. The second-factor key also has a previous key and a reseal, so nobody has to set two-step sign-in up again.

Making a secret ​

All four have the same rule: base64url text without padding that decodes to at least 32 bytes. The proxy secret, the pepper and the second-factor key must also differ from the master secret, and the second-factor key from the pepper; start-up is refused otherwise. The proxy secret sits on the app server, and a reused value would put the master secret there.

Make 32 random bytes in base64url form:

node -e "process.stdout.write(require('node:crypto').randomBytes(32).toString('base64url'))"

Keep the value in a variable of your shell or a password manager. Do not write it into a file the repository tracks, a log or a chat.

Replacing EVO_AUTH_SECRET ​

Effect: it signs everyone out. Every key the product uses is derived from the master secret, so replacing it changes all of them at once:

  • Sign-in cookies stop opening. A sign-in in flight fails with the generic refusal, and the user starts again.
  • Client-address hashes change. The rate-limit rows start counting afresh.
  • The refresh MAC key changes. Every refresh token fails its MAC and is treated as junk, with no storage read and no revocation. Everyone is signed out and signs in again.
  • Signed access tokens are not affected until they expire, because the signing keys are separate. A user keeps working for up to accessToken.lifetimeSeconds (300 seconds by default), then finds the session gone.

Steps:

  1. Make the new value (above).
  2. Set EVO_AUTH_SECRET to it everywhere the auth endpoints read it. On Convex that is the deployment: npx convex env set EVO_AUTH_SECRET, with the value on standard input. If you keep a copy in .env.local, replace the value there too.
  3. If your auth endpoints run on a host that builds createAuth once, restart it. On Convex the next request uses the new value, with no push, because the environment is read on each auth request.
  4. Run pnpm exec evo-auth check.

Do not set it to the value of EVO_AUTH_PROXY_SECRET. evo-auth check reads the env file, not the running process, so keep the file in step with the deployments, or its report describes the old value.

Replacing EVO_AUTH_PROXY_SECRET ​

The auth deployment and the app's proxy must hold the same value. Replacing it means setting the same new value on both, and requests that arrive between the two changes are refused with proxy_refused.

Steps:

  1. Make the new value (above).
  2. Set it on the auth deployment: npx convex env set EVO_AUTH_PROXY_SECRET, value on standard input.
  3. Set it on the app server and restart the app server, which reads it when it starts.
  4. Run pnpm exec evo-auth check.

Do the two changes close together. Between them, every request through the proxy is refused, sign-ins, refreshes and the handshake included. The secret is not used to derive any session or token key, so replacing it changes no stored session.

The proxy secret stays on the app server and the auth deployment. Never put it in a client bundle, a VITE_ variable or a log.

Replacing EVO_AUTH_PASSWORD_PEPPER ​

Effect: every user must reset their password. Each stored password hash was made with the old pepper, so none of them verifies with the new one. Until a person resets, their right password is refused like a wrong one, and each try counts as a failed sign-in. Sessions that exist are not affected. Replace the pepper only if it has leaked; see Email and password.

Steps:

  1. Make the new value (above).
  2. Set EVO_AUTH_PASSWORD_PEPPER to it everywhere the auth endpoints read it. On Convex that is the deployment: npx convex env set EVO_AUTH_PASSWORD_PEPPER, with the value on standard input. Replace the copy in .env.local too.
  3. Restart a host that builds createAuth once. On Convex the next request uses the new value.
  4. Run pnpm exec evo-auth check.
  5. Tell your users to use "Forgot password?". The reset email needs your email.sender to work.

Replacing EVO_AUTH_SECOND_FACTOR_KEY ​

Effect: nobody has to do anything. For a while the auth endpoints hold two keys: the new one in EVO_AUTH_SECOND_FACTOR_KEY and the old one in EVO_AUTH_SECOND_FACTOR_KEY_PREVIOUS. They open a stored authenticator secret or backup code with the new key first and the old one second, so authenticator codes, backup codes and identity confirmations keep working. Each person who passes a step has their stored values sealed again under the new key, and new set-ups and new backup codes use the new key at once. The reseal moves everyone else.

EVO_AUTH_SECOND_FACTOR_KEY_PREVIOUS has the key's rule (above) and must also differ from the master secret and the pepper. Only the auth endpoints read it, and only while secondFactor.enabled is on. While it is set, evo-auth check and evo-auth-server check print a warning naming it.

Steps:

  1. Set EVO_AUTH_SECOND_FACTOR_KEY_PREVIOUS to the current value.
  2. Set EVO_AUTH_SECOND_FACTOR_KEY to a new value. Restart a host that builds createAuth once; restart all instances of a multi-instance server together.
  3. Run the reseal until it reports 0 and 0.
  4. Remove EVO_AUTH_SECOND_FACTOR_KEY_PREVIOUS: on Convex, from the deployment (npx convex env remove EVO_AUTH_SECOND_FACTOR_KEY_PREVIOUS) and from .env.local; on the standalone server, from its environment, then restart it. Then run evo-auth check, or evo-auth-server check.

The proof is the reseal command reporting 0 and 0 before the removal; the checks only confirm the variable is gone from what they read.

On Convex, step 1 is npx convex env set EVO_AUTH_SECOND_FACTOR_KEY_PREVIOUS and step 2 npx convex env set EVO_AUTH_SECOND_FACTOR_KEY, each with the value on standard input; the next request reads both. Set the previous key first: while it still equals the key, the endpoints accept it and the checks warn. Replace the copies in .env.local too. The app server reads neither.

The reseal ​

The reseal opens every stored value with both keys and seals again under the new key each person's values that are still under the old one. It writes each person's values only if nobody changed them since it read them, so it never undoes a backup code used or an authenticator replaced at the same moment; such a person is counted under the previous key, and the next run moves them. It prints three counts: the people resealed, the people still under the previous key, and the people with a value that opens under neither key.

On the standalone server, run it in the server's folder, with the server's environment, while the server runs:

evo-auth-server second-factor reseal

It exits 0 when it reports 0 and 0, and 1 otherwise. A person still under the previous key only needs another run. A person under neither key, or with backup codes in the old format, needs the step in its paragraph below first; another run alone never exits 0 while they are listed.

On Convex, the reseal is an action of your app, made in the same file as the email job and run with npx convex run. It runs inside the deployment, where the keys are:

ts
// convex/auth.ts
import { createEmailJob, createSecondFactorReseal } from "@evo-auth/convex";
import { authConfig } from "../shared/auth-config.js";
import { components } from "./_generated/api.js";

export const emailJob = createEmailJob(components.evoauth, { config: authConfig });
export const secondFactorReseal = createSecondFactorReseal(components.evoauth, { config: authConfig });
npx convex run auth:secondFactorReseal

It answers { resealed, stillPrevious, neither, oldFormat, next }. One run starts no new page after 200 seconds, so it answers before npx convex run stops waiting at 5 minutes; while next is not null, run it again from there with npx convex run auth:secondFactorReseal '{"after": "<next>"}', adding up the counts. A pass that started with no after and ended with next null, with stillPrevious 0 and neither and oldFormat empty in every run, is the 0 and 0 of step 3. Otherwise start another pass, after the step below for each person listed in neither or oldFormat: another pass alone never empties those lists. The page size and the time a run allows were measured on a local Convex backend, not on Convex's cloud or your deployment, and the time's margin is set against the 5 minutes npx convex run waits, so rerun with next whatever your timings are. If npx convex run prints 'Failed to run function … Error', run it again with {}.

Both refuse to run without EVO_AUTH_SECOND_FACTOR_KEY_PREVIOUS, naming it.

A person counted under neither key had values sealed under a third, older key, which neither key opens; their authenticator code answers 503 unavailable. The reseal lists their user ids. Remove each one's second factor (evo-auth-server users second-factor remove <id>, the admin page, or the server API's removeSecondFactor(userId)), and they set it up again. See Recovery.

A person with backup codes in the old format has codes stored before backup codes were sealed. No key opens them, so the reseal leaves that person's values as they are. The command prints Backup codes in the old format: N (the person makes new codes, or the factor is removed) with their user ids and exits 1, and the Convex action lists them in oldFormat. The person makes new backup codes from their profile, or you remove their second factor as above; then run the reseal again.

If you remove EVO_AUTH_SECOND_FACTOR_KEY_PREVIOUS before the reseal reports 0 and 0, the people still under the old key get 503 unavailable for an authenticator code and a backup code. Nothing is lost: set the previous key again and run the reseal.

After a leak ​

After a suspected leak, if the database may also have been copied, step 3 is followed by asking each two-step user to replace their authenticator and to make new backup codes. Whoever holds an old copy and the old key can open the secrets and search the backup codes offline. A replacement alone keeps the old backup codes.
