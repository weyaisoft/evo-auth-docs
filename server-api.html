Server API and hooks ​

This page is for a developer who needs to act on users from server code: read, list, ban, revoke sessions, edit metadata, delete. It also covers the hooks that run when a user is created, changed, deleted or signs in. The server API is for trusted code only: no HTTP route exposes it. The admin routes, for the users you list as admins, are a separate surface served by the auth handler; see The admin routes.

The entry points ​

WhatCallReturns
The auth endpointscreateAuth(config, secrets, { logger?, clock? }){ handler }
One requestauth.handler(request, { storage, connectionAddress? })Promise<Response>
The server API on a storage adaptercreateAuthApi(storage, config?)AuthApi
The server API on ConvexcreateAuthApi(components.evoauth, { config, hooks })(ctx: AuthApiCtx) => AuthApi

On Convex you do not call createAuth yourself: registerRoutes does it for each request. See the Convex guide.

On Convex, annotate the result as (ctx: AuthApiCtx) => AuthApi. The generated api names your module and your module names the generated api, and the annotation breaks that type cycle:

ts
const authApi: (ctx: AuthApiCtx) => AuthApi = createAuthApi(components.evoauth, { config: authConfig });

Then call it with the ctx of the function you are in: authApi(ctx).banUser(userId). getUser and listUsers run with any function's ctx. Every other method writes, so it needs a mutation's, an action's or an HTTP action's ctx.

The methods ​

MethodWhat it does
getUser(userId)The user, or null.
listUsers({ cursor?, limit? })One page, in creation order. limit is 1 to LIST_USERS_PAGE_LIMIT (100), which is also the default. Pass the last page's nextCursor as cursor; nextCursor is null after the last page.
banUser(userId)Ends every session of the user at once and refuses their sessions until unbanUser.
unbanUser(userId)Lifts a ban. Sessions from before the ban stay ended.
revokeSession(sessionId)Revokes one live session with the reason admin.
revokeAllSessions(userId)Ends every session the user has now.
setPublicMetadata(userId, metadata)Replaces publicMetadata.
setPrivateMetadata(userId, metadata)Replaces privateMetadata.
setUsername(userId, username)Sets, changes or removes (null) the user's username, lower-casing it first. The username rule applies and the reserved list does not; no confirmation is asked and no bucket is counted. It works whatever usernames.enabled says.
deleteUser(userId)Starts deleting the user: access ends at once and the rows are removed in batches. It asks for no reverification, because server code is trusted.

Each method is one storage operation, so its effect is atomic and the hooks run inside it. Revoking, banning and deleting are flag-first: access ends at once and cleanup follows.

Answers that are not failures come back as outcomes, never thrown: not_found for an unknown id, and already_ended from revokeSession for a session that had already ended (revoked, expired, or its user banned, deleted or signed out everywhere). That call writes nothing. A wrong argument is a TypeError.

setUsername answers { outcome, username } with set, changed, removed or unchanged and the name now held (null after a removal), or one of invalid (the name fails the rule), taken (another user holds it), no_email_account (a name for a user with no email account) and not_found (a missing or deleted user). unchanged writes nothing. Every other change records username_changed with no actorUserId and sends user.updated.

AuthApiUser has id, displayName, avatarUrl, createdAt, updatedAt, publicMetadata, privateMetadata, email, username (the user's username, or null), and bannedAt, deletedAt and revokedAllAt when set. Times are milliseconds since the epoch. PublicUser is the browser's view: the same without privateMetadata and email.

email is the email of the user's primary account, the earliest linked one, as its provider gave it, or null. It is display data only. EVO_AUTH never finds, links or merges users by email, so two users may show the same address, and a provider's word that it verified an address is stored but grants nothing. Do not use email to decide who a user is or what they may do; use id. GET {basePath}/me does not return it.

Organisations ​

With organizations.enabled set to true in the config, the server API also acts on organisations. On a storage adapter, pass the object validateConfig returned as the second argument, createAuthApi(storage, config); on Convex, createAuthApi(components.evoauth, { config }) already has it. Without the config, or while organizations.enabled is false, each organisation method rejects with a TypeError that names the setting, and the user methods work as before.

MethodWhat it does
createOrganization({ name, slug, imageUrl?, createdBy })Creates an organisation with createdBy as its first member, in organizations.creatorRole. It works for any user whatever organizations.creation says, and is not counted in the organization_create bucket. A slug another organisation has is slug_taken; a missing, banned or deleted user is user_not_found.
getOrganization(organizationId)The organisation, or null.
listOrganizations({ cursor?, limit? })One page of organisations in creation order, like listUsers.
updateOrganization(organizationId, { name?, slug?, imageUrl? })Changes the profile. A slug another organisation has is slug_taken.
deleteOrganization(organizationId)Deletes the organisation at once; its memberships and invitations are removed in batches.
addMember(organizationId, userId, role)Adds an existing user with a role from organizations.roles. A role that is not there is unknown_role; a missing, banned or deleted user is user_not_found; a member is already_member.
setMemberRole(organizationId, userId, role)Changes a member's role.
removeMember(organizationId, userId)Removes a member.
listMembers(organizationId, { cursor? })One page of up to 100 members, oldest first, each with the user's displayName and avatarUrl.
setOrganizationPublicMetadata(organizationId, metadata)Replaces the organisation's publicMetadata, under the rules for a user's.
setOrganizationPrivateMetadata(organizationId, metadata)Replaces the organisation's privateMetadata.
createInvitation({ organizationId, role, invitedBy, expiresInSeconds? })Creates an invitation to join with role, from invitedBy, an existing user who is neither banned nor deleted. It expires after expiresInSeconds: 604,800 (7 days) when left out, a whole number from 1 to 2,592,000 (30 days). Answers { outcome: "created", invitation, url }: url is the link, {organizations.invitationUrl}?evo_invitation={token}, returned here once and kept nowhere. A role that is not in organizations.roles is unknown_role, a missing organisation not_found, a missing, banned or deleted invitedBy user_not_found.
revokeInvitation(organizationId, invitationId)Deletes an open invitation, so its link no longer works. not_found for no such organisation or invitation of it.

The server API acts as the app, so it checks no organisation role. One rule holds for it as for everyone: every organisation keeps at least one member whose role holds org:memberships:manage. A role change or removal that would leave none is refused as last_manager, with nothing written. Deleting a user is not stopped by it: their memberships are removed with their other rows, and an organisation left with no such member is repaired with setMemberRole or addMember.

AuthApiOrganization has id, name, slug, imageUrl (an https URL or null), createdBy, createdAt, updatedAt, memberCount (the exact number of its memberships), publicMetadata and privateMetadata. A slug is 1 to 40 characters, each a to z, 0 to 9 or -; a name is 1 to 64 characters with no control character. Anything else is a TypeError that names the argument. AuthApiMembership, a row of listMembers, has organizationId, userId, role, createdAt (when the user joined), updatedAt, displayName and avatarUrl. A member whose role is no longer in organizations.roles keeps the role as stored and holds no permissions; evo-auth-server check reports such memberships.

AuthApiInvitation has id, organizationId, role, invitedBy, createdAt and expiresAt, never the token or its hash.

Creating, deleting, adding, removing and changing a role record the auth events organization_created, organization_deleted, member_added, member_removed and member_role_changed; creating, revoking and accepting an invitation record invitation_created, invitation_revoked and invitation_accepted. Each carries the organisation's id, and none carries an invitation's token or link. No webhook is sent for them yet.

Invitations ​

An invitation is a single-use link. Storage keeps only the SHA-256 of its token, so the link is shown once: in the answer that created it, and to onInvitationCreated, the hook an app uses to send it however it likes (an email of your own, a chat message). The server API's createInvitation runs no hook: it returns the link to you, to send yourself. Whoever opens the link while signed in joins with the invitation's role, and the link then stops working. It is never tied to an email address. A link made here keeps working whatever later happens to invitedBy, because it comes from your own backend; a link a member or an app admin made on the routes stops working once they may no longer grant its role. Expired invitations are removed by a sweep, at most 1,000 a run. Treat the link as a secret until it is accepted: do not log it. On Convex, deliver it from an action that called your mutation (ctx.runMutation returns the link to the action), and never pass it to ctx.scheduler: Convex keeps a scheduled function's arguments, so the token would be stored.

Metadata ​

Pass your two metadata shapes once, as the type arguments of createAuthApi:

ts
type PublicMeta = { plan: "free" | "pro" };
type PrivateMeta = { stripeCustomerId?: string };

const authApi = createAuthApi<PublicMeta, PrivateMeta>(components.evoauth, { config: authConfig });

Declare these types with type, not interface. A metadata value is a plain JSON object ({ readonly [key: string]: JsonValue }), and TypeScript does not treat an interface as assignable to that index-signature shape.

publicMetadata is returned to the signed-in user by GET {basePath}/me; privateMetadata never leaves the server. A metadata value must be a plain JSON object: own enumerable data properties holding only null, booleans, finite numbers, strings, arrays and plain objects, with no cycle. Anything else is a TypeError.

On Convex, a metadata key that starts with $ or holds a non-ASCII character is refused by Convex itself, with its own message, and nothing is written.

Hooks ​

The user hooks and onSignIn are your own internal mutations. The component calls each inside its own transaction, so a hook that throws discards every write of that operation, yours included.

HookReceives
onUserCreated{ user }
onUserUpdated{ user }
onUserDeleted{ user }
onSignIn{ user, sessionId }
onInvitationCreated{ organization, role, url, invitedBy }

Pass them to registerRoutes and createAuthApi as references: hooks: { onUserCreated: internal.hooks.onUserCreated }. Use internalMutation, so no client can call them.

onInvitationCreated is different: it is one of your internal actions (internalAction), and it runs after the invitation has been saved, in the HTTP action that answers a member's or an admin's request, so it can call a mail service directly. The link never reaches the component. If it throws, the invitation still exists, the inviter still gets the link to copy, and invitation.hook_failed is logged. You cannot record "invitation sent" in the same transaction as the invitation. Validate the arguments with the two validators @evo-auth/convex exports:

ts
import { evoSessionIdValidator, evoUserValidator } from "@evo-auth/convex";
import { internalMutation } from "./_generated/server.js";

export const onSignIn = internalMutation({
  args: { user: evoUserValidator, sessionId: evoSessionIdValidator },
  handler: async (ctx, { user }) => {
    await ctx.db.insert("hookLog", { hook: "onSignIn", userId: user._id });
  },
});

A hook receives the stored document, so the user's id is user._id. The server API returns the API's view of a user, whose id is user.id. They are the same value under two names.

evoUserValidator is the component's stored user document, and evoSessionIdValidator is a string. For onInvitationCreated, evoOrganizationValidator is the stored organisation document; role, url and invitedBy are strings (v.string()). url is the invitation's link, which grants membership: send it, and do not log it.

On the SQLite server, pass the same hooks as functions to createServer({ hooks }); onInvitationCreated receives { organization, role, url, invitedBy } there too, after the invitation's transaction has committed, with the same rule when it throws.

Two copies of core ​

instanceof AuthError and isValidatedConfig rely on one installed copy of @evo-auth/core. If your dependency tree holds two copies, an error from one is not an instance of the other's class, and a config from one is refused by the other. SecretsError and ConfigError are type-only exports: check them by shape, not with instanceof.

The routes your users call ​

The browser components call five self-service routes under basePath, all with a Bearer access token. They are listed in Configuration with the other routes.

  • GET {basePath}/me
  • GET {basePath}/sessions
  • POST {basePath}/sessions/revoke
  • POST {basePath}/sessions/revoke-all
  • POST {basePath}/account/delete

When GET /sessions is truncated, the components say "Showing your 100 most recent sessions" and offer sign-out everywhere, which is POST {basePath}/sessions/revoke-all. UserProfile always shows its "Sign out everywhere" button.

Organisation routes ​

With organizations.enabled set to true, the handler also serves these routes, with the same rules: a Bearer access token and a live session on every one, and the Origin check on every POST. With it false they do not exist. Every id goes in the JSON body, or in the query for a GET.

Method and pathInputAnswerNeeds
GET {basePath}/organizationsnone{ organizations, canCreate }
POST {basePath}/organizationsbody { name, slug, imageUrl? }{ organization, role }organizations.creation
GET {basePath}/organizations/detailquery organizationId{ organization, role, permissions }membership
POST {basePath}/organizations/updatebody { organizationId, name?, slug?, imageUrl? }{ organization }org:profile:manage
POST {basePath}/organizations/deletebody { organizationId }{ done: true }org:profile:delete and a recent confirmation
GET {basePath}/organizations/membersquery organizationId, cursor{ members, nextCursor }org:memberships:read

POST {basePath}/organizations/members/removebody { organizationId, userId }{ done: true }org:memberships:manage, none for yourself
POST {basePath}/organizations/leavebody { organizationId }{ done: true }membership
GET {basePath}/organizations/invitationsquery organizationId{ invitations, truncated }org:invitations:manage

POST {basePath}/invitations/previewbody { token }{ organizationName, role }no session

  • organizations lists the caller's own memberships, oldest first and at most 100, each { id, name, slug, imageUrl, memberCount, role }. canCreate is true when organizations.creation is "anyone", or when it is "admins" and the caller is in admins.userIds; creating still checks the rule itself.
  • An organization in an answer is { id, name, slug, imageUrl, createdAt, memberCount }. Metadata is not sent to members. permissions are those organizations.roles gives the caller's role now.
  • A member is { userId, displayName, avatarUrl, role, createdAt }, 100 a page; createdAt is when they joined.
  • Removing yourself is leaving. Deleting needs the session to have confirmed within reverification.maxAgeSeconds (403 reverification_required); the permission is checked first, so a member who may not delete is never asked to confirm.
  • Someone who is not a member of the organisation gets 404 not_found on every route about it, the same answer as for an organisation that does not exist.
  • The refusals a screen tells apart are 400 with { error: "invalid_request", reason }: forbidden (the caller's role lacks the permission), role_above_own (the role given, or the member's current role, holds a permission the caller's own role lacks), last_manager, unknown_role, not_member, already_member, slug_taken and creation_not_allowed. A full organization_create bucket is 429 rate_limited.
  • An invitation is { id, role, invitedBy, createdAt, expiresAt }, never its token or hash. url in the creation answer is the link, {organizations.invitationUrl}?evo_invitation={token}, given there once. expiresInSeconds is 604,800 (7 days) when left out, at most 2,592,000 (30 days). The list holds at most 100 open invitations, oldest first; truncated says more exist.
  • The invitation token is never in a request address: preview and accept take it in the JSON body, so it stays out of server logs and the Referer header. The preview needs no session and answers only the organisation's name and the role's key. A missing, expired, revoked or used link is the same 404 not_found, for the preview and the accept alike.
  • Accepting adds the caller with the invitation's role and deletes the invitation in one operation, so a link works once. A member already is already_member; a role no longer in organizations.roles is unknown_role.
  • Reads count in self_read per address, writes in self_service per session, and a creation also in organization_create. The preview counts self_read per address.

The admin routes ​

The auth handler also serves nine admin routes under {basePath}/admin/, beside the server API. They exist only when admins.userIds lists at least one user id (see Configuration); with the list empty every one of them answers 404. They are for the users you list, from the browser, with their own Bearer access token. The server API's banUser and the rest stay as they are, for your own server code.

Method and pathInputAnswer
GET {basePath}/admin/usersquery search with searchBy, banned=1, cursor, each optional{ users, nextCursor }, for a search too
GET {basePath}/admin/userquery userId{ user, accounts, isAdmin }
GET {basePath}/admin/user/sessionsquery userId{ sessions, truncated }
GET {basePath}/admin/eventsquery userId (optional), cursor{ events, users, nextCursor }
POST {basePath}/admin/user/banbody { userId }{ done: true }
POST {basePath}/admin/user/unbanbody { userId }{ done: true }
POST {basePath}/admin/user/deletebody { userId }{ done: true }
POST {basePath}/admin/sessions/revokebody { userId, sessionId }{ done: true }
POST {basePath}/admin/sessions/revoke-allbody { userId }{ done: true }
POST {basePath}/admin/user/usernamebody { userId }, only while usernames.enabled is on{ done: true }
  • The user list pages 100 users at a time in creation order; with banned=1 it lists banned users only. A search takes an id, a login, an email or a username, named by searchBy: id, login, email or username, the one field it matches. searchBy needs a search and a search needs searchBy; anything else is 400 invalid_request. searchBy=id matches the user whose id is exactly the search text: a part of an id matches nothing. searchBy=login and searchBy=email match the users of the accounts whose login or email starts with the text, in any letter case, so mar finds Mark and martha@example.com. Results come in the order of the lowercase login or email; a user whose several accounts match is listed once on a page. A deleted user is left out. The banned filter applies to a search's results too. A search by login or email pages like the list, 100 accounts' users at a time, with nextCursor for the next page of the same search; a search by id returns at most one user and nextCursor: null. A cursor from another search or from the list is 400 invalid_request. An account linked before this version is found by login or email from its user's next sign-in. searchBy=username matches the users whose username starts with the text, in any letter case, in the order of the name, 100 a page with nextCursor, whatever usernames.enabled says.
  • Each user is { id, displayName, avatarUrl, email?, createdAt, bannedAt, login?, username, providers, isAdmin }: username is the user's username or null; email is the user's email, left out when there is none; login is the login of the user's first linked account, left out when there is none; providers lists the provider ids of the user's accounts once each, in the order they were linked; isAdmin says whether the user is in admins.userIds. User detail adds publicMetadata, the linked accounts { provider, login, email?, emailVerified, linkedAt } and isAdmin. privateMetadata is never sent. An email is shown to the admin and decides nothing: every action names its user by id.
  • Sessions are the user's live ones only, at most 100, each { sessionId, createdAt, expiresAt, userAgent }.
  • Events are newest first, 100 a page, each { type, at, userId?, sessionId?, reason?, actorUserId? }. users names every user and admin on the page as { displayName, login? }; a deleted user is left out.
  • Ban, unban and delete need the admin's session to have confirmed with the provider within reverification.maxAgeSeconds, as account deletion does, and answer 403 reverification_required otherwise. Revoking sessions needs no confirmation.
  • Clearing a username is the only thing an admin does to one: there is no route to set or change it. It needs the same recent confirmation as ban and answers { done: true } also for a user who holds no name, writing nothing then. It frees the name at once, records username_changed with the admin as actorUserId and sends user.updated; the person can choose a new name from their profile. A missing or deleted user is 404 not_found.
  • A write on yourself or on another listed admin is 400 invalid_request. Use your own self-service routes, and remove an admin from the list with a deploy first.
  • Every admin write records the same event the action records anywhere else, with actorUserId, the admin who acted. Events written by the server API and the self-service routes carry no actorUserId.
  • GETs count in the admin_read bucket and POSTs in admin_write, per session.

With organizations.enabled also true, the admin acts on any organisation, whatever their own role in it:

Method and pathInputAnswer
GET {basePath}/admin/organizationsquery cursor{ organizations, nextCursor }
GET {basePath}/admin/organizationquery organizationId, cursor{ organization, members, nextCursor, invitations, invitationsTruncated }
POST {basePath}/admin/organization/updatebody { organizationId, name?, slug?, imageUrl? }{ done: true }
POST {basePath}/admin/organization/deletebody { organizationId }{ done: true }
POST {basePath}/admin/organization/members/addbody { organizationId, userId, role }{ done: true }
POST {basePath}/admin/organization/members/rolebody { organizationId, userId, role }{ done: true }
POST {basePath}/admin/organization/members/removebody { organizationId, userId }{ done: true }
POST {basePath}/admin/organization/invitations/createbody { organizationId, role, expiresInSeconds? }{ invitation, url }
POST {basePath}/admin/organization/invitations/revokebody { organizationId, invitationId }{ done: true }
  • The list pages 100 organisations in creation order, each { id, name, slug, imageUrl, createdAt, memberCount }. One organisation adds createdBy, updatedAt and publicMetadata, with a page of its members as on the member's route and up to 100 open invitations. privateMetadata is never sent, nor any invitation's token or hash.
  • An admin's invitation is from the admin (invitedBy), for any role, and its link is answered once, as on the member's route.
  • GET /admin/user adds memberships, each { organizationId, name, slug, imageUrl, role }.
  • The admin may give any role, but the last-manager rule holds for them too. An admin may add themselves or another admin to an organisation, to repair it.
  • Delete needs a recent confirmation, asked only once the organisation is known to exist.
  • A missing organisation or user is 404 not_found; slug_taken, unknown_role, already_member, not_member and last_manager are 400 with that reason, as on the member's routes.
  • Each write records its event with actorUserId, the admin.

The order of checks, what a non-admin sees and what the routes never send are on the security model.
