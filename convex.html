Convex guide ​

This page is for a developer who runs the auth endpoints on Convex. It covers installing the component, mounting the routes, the environment variables, reading the signed-in user in your own functions, banning a user from the command line, rotating the signing keys, and the safety rule about Convex credentials.

You also need an app server that proxies {basePath}/* to Convex, because Convex serves HTTP actions from another site and the cookies must be first-party. For TanStack Start see the TanStack Start guide; for the proxy itself see The proxy and the client address. The working reference is examples/tanstack-convex/convex/.

Install the three packages first: the install command is under evo-auth init.

1. Install the component ​

convex/convex.config.ts:

ts
import { defineApp } from "convex/server";
import evoauth from "@evo-auth/convex/convex.config";

const app = defineApp();
app.use(evoauth);
export default app;

The component keeps users, accounts, sessions, rate-limit counters, cleanup jobs and auth events in its own tables. Your app never reads them. Run npx convex dev once so Convex generates components.evoauth in convex/_generated/api.

2. Make one shared config ​

validateConfig returns the only object the Convex package and the app server accept. Put it in one module that both import. The example's is shared/auth-config.ts:

ts
import { validateConfig } from "@evo-auth/core";
import { providers } from "./providers.js";

export const authConfig = validateConfig({
  publicUrl: "http://localhost:3000/auth",
  cookies: { devMode: true },
  providers,
});

The module must read no environment variable. Convex requires every variable read anywhere in the import chain of auth.config.ts to be set, with no fallback, and refuses the push otherwise. That chain includes the provider list, so choose providers in code, not by whether a variable is set: the example's shared/providers.ts lists github() alone, and you add Google by adding google() to that list and setting EVO_AUTH_GOOGLE_CLIENT_ID and EVO_AUTH_GOOGLE_CLIENT_SECRET on the deployment. publicUrl is your site's origin plus basePath. Remove cookies.devMode for production: it is right only for http://localhost. See Configuration.

3. Mount the routes ​

convex/http.ts. registerRoutes mounts every auth route as an HTTP action of your own app, under basePath:

ts
import { httpRouter } from "convex/server";
import { github, validateConfig } from "@evo-auth/core";
import { registerRoutes } from "@evo-auth/convex";
import { components } from "./_generated/api.js";

const http = httpRouter();

registerRoutes(http, components.evoauth, {
  config: validateConfig({ publicUrl: "https://app.example.com/auth", providers: [github()] }),
});

export default http;

In your own app, import the shared config instead of calling validateConfig here, and pass the hooks if you use any (Server API and hooks):

ts
registerRoutes(http, components.evoauth, {
  config: authConfig,
  hooks: {
    onUserCreated: internal.hooks.onUserCreated,
    onUserUpdated: internal.hooks.onUserUpdated,
    onUserDeleted: internal.hooks.onUserDeleted,
    onSignIn: internal.hooks.onSignIn,
  },
});

registerRoutes reads no environment variable while http.ts loads. It checks its options and that the config is one validateConfig returned, and it throws, registering nothing, when the router already has a route on {basePath}/*. It mounts every method Convex routes to an HTTP action, so a method outside a path's table still reaches the handler and gets its 405 with Allow. An app route on an exact path under basePath, or a longer prefix, takes precedence over the handler without an error, so keep your own routes off that path.

4. Tell Convex to accept the tokens ​

convex/auth.config.ts:

ts
import { authConfigProvider } from "@evo-auth/convex";
import { authConfig } from "../shared/auth-config.js";

export default { providers: [authConfigProvider(authConfig)] };

authConfigProvider(config) returns the customJwt entry. Its issuer is publicUrl, its application id is appId, and its jwks is a data URI built from EVO_AUTH_PUBLIC_KEYS, so the deployment never fetches its own key set and there is no second copy of the keys. It reads EVO_AUTH_PUBLIC_KEYS when auth.config.ts loads, so the push fails, naming that variable, when it is missing.

Variables ​

Every name and rule is on the generated reference. This table says where each one is set.

VariableConvex deploymentApp server
EVO_AUTH_SECRETyesno
EVO_AUTH_SIGNING_KEYyesno
EVO_AUTH_PUBLIC_KEYSyes, before the first pushyes
EVO_AUTH_GITHUB_CLIENT_ID and EVO_AUTH_GITHUB_CLIENT_SECRET (for each enabled provider, the pair; apple() has EVO_AUTH_APPLE_CLIENT_ID and EVO_AUTH_APPLE_PRIVATE_KEY, and x() has the id twitter)yesno
EVO_AUTH_PROXY_SECRETyes, unless cookies.devMode is onyes
EVO_AUTH_PASSWORD_PEPPERyes, while emailAuth.password is on (the example has it on)no
EVO_AUTH_SECOND_FACTOR_KEYyes, while secondFactor.enabled is onno
EVO_AUTH_SECOND_FACTOR_KEY_PREVIOUSoptional: only during a rotation; see Rotating secretsno

Values come from evo-auth init (the master secret, the password pepper and the second-factor key) and evo-auth keys generate (the two key variables), both into .env.local. The proxy secret is not made by a command; see Rotating secrets.

Set a Convex variable with npx convex env set NAME and give the value on standard input, never as an argument, so it stays out of the process list and the shell history. evo-auth keys generate --convex and evo-auth keys rotate --convex do that for the key variables.

On a first Convex deploy the deployment must exist before EVO_AUTH_PUBLIC_KEYS can be set, so the first push fails until it is. Run npx convex dev, let it fail naming EVO_AUTH_PUBLIC_KEYS, set the variable, and push again.

What happens when a variable is missing ​

The environment is read on each auth request, never while http.ts loads. While it is incomplete, every auth route answers the handler's unavailable refusal (503, body {"error":"unavailable"}, Cache-Control: private, no-store, Vary: Cookie, no cookie), and the action writes one line to the deployment's log naming the variables at fault and no value:

[evo-auth] register_routes.setup_failed EVO_AUTH_PROXY_SECRET

This happens when EVO_AUTH_PROXY_SECRET is unset outside the development cookie mode, and when any other variable is missing or refused. The line is written on every refused request, so it repeats until the environment is fixed. Your app's other HTTP routes keep serving.

The operator's order:

  1. Set the variables.
  2. Push.
  3. Run evo-auth check.

A changed variable applies from the next request, with no push. Only a missing EVO_AUTH_PUBLIC_KEYS fails the push, because auth.config.ts reads it.

Reading the user in your own functions ​

getEvoIdentity(ctx, config) returns the signed-in user, or null:

ts
import { getEvoIdentity } from "@evo-auth/convex";
import { authConfig } from "../shared/auth-config.js";
import { query } from "./_generated/server.js";

export const whoami = query({
  args: {},
  handler: (ctx) => getEvoIdentity(ctx, authConfig),
});

It returns { userId, sessionId, name, picture, organization, verifiedAt }. verifiedAt is when the person last confirmed their identity, in milliseconds since the epoch, taken from the token's vat claim, and null for a session that was never confirmed (see Recent confirmation in your own functions). It returns null when the caller has no verified token and for an identity whose issuer is not exactly publicUrl, which suits an app with two auth providers. On the client, ConvexProviderWithEvoAuth from @evo-auth/react/convex sends the access token with every Convex call.

Convex checks a token's signature and claims, not the session behind it. A token issued before a revocation still works in your Convex functions until it expires (accessToken.lifetimeSeconds, 300 seconds by default). The auth routes themselves check the session on every request.

Organisations in your own functions ​

With organizations.enabled on, a person can pick an active organisation for their session (POST {basePath}/organizations/active with { "organizationId": "..." }, or null for none). Their access token then carries the organisation's id and slug and their role. getEvoIdentity gives it as organization: { id, slug, role, permissions }, with the permissions your config's organizations.roles gives that role, or null when there is none. A role your config does not list has no permissions.

hasPermission(identity, "docs:edit") answers from that object. It is quick, because it reads only the token, but the token can be up to one access-token lifetime old: a member removed or demoted a minute ago may still pass it.

For a function that must not trust a claim that old, requireMembership reads the component instead:

ts
import { requireMembership } from "@evo-auth/convex";
import { v } from "convex/values";
import { authConfig } from "../shared/auth-config.js";
import { components } from "./_generated/api.js";
import { mutation } from "./_generated/server.js";

export const deleteDocument = mutation({
  args: { organizationId: v.string(), documentId: v.id("documents") },
  handler: async (ctx, { organizationId, documentId }) => {
    await requireMembership(ctx, components.evoauth, organizationId, "docs:delete", authConfig);
    await ctx.db.delete(documentId);
  },
});

It returns the membership { organizationId, userId, role, permissions } as stored now. Otherwise it throws a ConvexError whose data is { code: "unauthenticated" } when the request has no Evo Auth identity, or { code: "forbidden" } when the caller is not a member, their role lacks the permission, or organisations are off. It never says which of those it was.

The issuer and your Convex functions must hold the same organizations.roles, because each works out the permissions from it.

Recent confirmation in your own functions ​

For a function that must run only soon after the person confirmed their identity, requireRecentVerification reads the identity's verifiedAt (the token's vat claim) and refuses when it is missing or too old:

ts
import { requireRecentVerification } from "@evo-auth/convex";
import { v } from "convex/values";
import { authConfig } from "../shared/auth-config.js";
import { mutation } from "./_generated/server.js";

export const deleteWorkspace = mutation({
  args: { workspaceId: v.id("workspaces") },
  handler: async (ctx, { workspaceId }) => {
    await requireRecentVerification(ctx, authConfig, { maxAgeSeconds: 300 });
    await ctx.db.delete(workspaceId);
  },
});

It returns when the confirmation is no more than maxAgeSeconds old. Otherwise it throws a ConvexError whose data is { code: "reverification_required", maxAgeSeconds }. A caller with no Evo Auth identity gets { code: "unauthenticated" } instead, as requireMembership gives: someone signed out is not shown the confirm-identity dialog. maxAgeSeconds is a whole number from 60 to 3600; another value, or a config validateConfig did not return, throws a TypeError. The helper writes nothing, so it never uses the confirmation up.

In the browser, useReverification catches that code, opens the confirm-identity dialog, and calls your function again once. The Node helper and the claim are described there.

A confirmation changes one claim of the token, so subscribed Convex queries run again once when it happens. That is a rare event, the same as switching organisation, and it cannot be hidden: requireRecentVerification needs vat in the identity.

Banning a user ​

The server API can ban, unban, revoke and delete users, and HTTP routes never expose it. Wrap it in an internalMutation so it is not in your public API and runs only for someone with deployment access. The example's convex/admin.ts:

ts
import { v } from "convex/values";
import type { AuthApi } from "@evo-auth/core";
import { createAuthApi, type AuthApiCtx } from "@evo-auth/convex";
import { authConfig } from "../shared/auth-config.js";
import { components, internal } from "./_generated/api.js";
import { internalMutation } from "./_generated/server.js";

// The annotation breaks a type cycle: the generated api names this module, and this module names the generated api.
const authApi: (ctx: AuthApiCtx) => AuthApi = createAuthApi(components.evoauth, {
  config: authConfig,
  hooks: {
    onUserCreated: internal.hooks.onUserCreated,
    onUserUpdated: internal.hooks.onUserUpdated,
    onUserDeleted: internal.hooks.onUserDeleted,
    onSignIn: internal.hooks.onSignIn,
  },
});

export const ban = internalMutation({
  args: { userId: v.string() },
  handler: (ctx, { userId }) => authApi(ctx).banUser(userId),
});

Run it with:

npx convex run admin:ban '{"userId":"<the user id>"}'

There is no ban command in evo-auth. More in Server API and hooks.

Never let a Convex admin or deploy key reach the browser ​

The Convex admin key and any deploy key must never reach the browser or a client bundle. With either one, every component function, including the refresh operations, can be called directly.

Keep them out of VITE_* variables, out of any file your build bundles for the client and out of logs. The component's refresh operations assume only your own HTTP actions call them.

Rotating the signing keys ​

Rotation has two steps so that no token is signed with a key a verifier does not have yet. evo-auth keys rotate adds a new key to the published set and stages it. evo-auth keys activate <kid> moves signing to it, once every verifier has the new set. The full commands and their output are on the command line page.

  1. Stage the key. Run pnpm exec evo-auth keys rotate --convex. It writes the new public key into EVO_AUTH_PUBLIC_KEYS and keeps the new private key as EVO_AUTH_STAGED_SIGNING_KEY in .env.local. EVO_AUTH_SIGNING_KEY is unchanged, so nothing signs with the new key yet. With --convex it also sets EVO_AUTH_PUBLIC_KEYS on the Convex deployment. Without --convex, set it yourself. Its last line gives the new key's id: Next: … run evo-auth keys activate <staged kid>.
  2. Give the new set to every verifier. Set the new EVO_AUTH_PUBLIC_KEYS on the app server and restart it. Your running app then publishes the new key at {publicUrl}/.well-known/jwks.json.
  3. Set the variable, then deploy. On Convex cloud, push after setting the variable and before keys activate. Whether a changed EVO_AUTH_PUBLIC_KEYS reaches auth.config.ts without a push is unverified on a cloud deployment. The local backend recorded a pushless pickup: a key added to the variable was accepted by ctx.auth with no push. No flag enforces this step, so do it.
  4. Check. Run pnpm exec evo-auth check --convex. In its Public key sets section, the line for the Convex deployment must say it lists the staged key: the Convex deployment's EVO_AUTH_PUBLIC_KEYS: lists the staged key (kid <staged kid>). keys activate --convex is refused until it does.
  5. Activate. Run pnpm exec evo-auth keys activate <staged kid> --convex. It shows the comparison of the key sets, asks you to type yes, writes the staged key as EVO_AUTH_SIGNING_KEY, and sets EVO_AUTH_SIGNING_KEY and EVO_AUTH_PUBLIC_KEYS on the deployment. There is no flag for a redeploy. It sets removeAfter on the retiring key to now plus the access-token lifetime, the clock-skew allowance and 300 seconds, so tokens that key signed keep verifying until they expire. It ends by printing the rollback command.

Rolling back ​

keys activate keeps the previous private key as the staged key. Its last line is the command to undo the activation:

To roll back: evo-auth keys activate <previous kid> (available until <time>)

<time> is an ISO 8601 date and time with its offset, in the time zone of the machine that ran the command. The window ends at the retiring key's removeAfter. After that, activate refuses that kid, and the next keys rotate removes the key and stages a new one. activate always takes a kid, and it must equal the staged key's, so a bare keys activate can never roll back by accident. Nothing about the staged key is sent to Convex: activation and rollback set only EVO_AUTH_SIGNING_KEY and EVO_AUTH_PUBLIC_KEYS, each on standard input. Running keys rotate while a rollback key is kept replaces it, says so, and closes the rollback window early.

A server whose key set lacks the active key's id sees new tokens as unknown_kid. getAuth then treats the page as the handshake state, and the loop guard ends it signed out, so the failure is visible and never a loop.

The JWKS body at {publicUrl}/.well-known/jwks.json is fixed when createAuth runs. On a host that builds createAuth once, a key past removeAfter stays published until restart.

Sending email ​

Signing in by an emailed code or link, and by a password, needs email.sender: a reference to one of your own actions, such as internal.email.send, which Evo Auth runs with ctx.runAction. It also needs the email job, an action of yours that sends the messages after a request has been answered. It is two lines. In a file such as convex/auth.ts:

ts
import { createEmailJob } from "@evo-auth/convex";
import { validateConfig } from "@evo-auth/core";
import { components } from "./_generated/api.js";

const config = validateConfig({ publicUrl: "https://app.example.com/auth" });

export const emailJob = createEmailJob(components.evoauth, { config });

In your app config is the shared config of section 2. Then give the job to the call in convex/http.ts:

ts
registerRoutes(http, components.evoauth, { config: authConfig, emailJob: internal.auth.emailJob });

registerRoutes refuses to run without emailJob while any of emailAuth.code, emailAuth.link, emailAuth.password or passkeys.signUp is on, even when only emailAuth.password is on. The error names emailJob and every one of those settings that is on. It is needed while secondFactor.enabled is on and email.sender is set too, because the second-factor notices are sent by it (see Two-step sign-in).

A scheduled action on Convex runs at most once, so a storage failure inside the email job loses that one message and the person presses "Send a new code". That is an accepted limit of this adapter. Your sender action cannot be cancelled: it is passed deadline, the time in milliseconds since the epoch at which Evo Auth stops waiting, to set its own request timeout. The sender, the messages and the rest of the limits are on Email.

The second-factor reseal is an action of yours too, exported beside the email job. It is run with npx convex run auth:secondFactorReseal only while EVO_AUTH_SECOND_FACTOR_KEY is being replaced; see Rotating secrets.

ts
import { createEmailJob, createSecondFactorReseal } from "@evo-auth/convex";
import { validateConfig } from "@evo-auth/core";
import { components } from "./_generated/api.js";

const config = validateConfig({ publicUrl: "https://app.example.com/auth" });

export const emailJob = createEmailJob(components.evoauth, { config });
export const secondFactorReseal = createSecondFactorReseal(components.evoauth, { config });

Signing in by email in the example ​

examples/tanstack-convex has email sign-in on, by a six-digit code, by a link and by a password, with sign-up at /sign-up and usernames on (usernames.enabled, see Email and password), so a person can choose one when signing up with a password, or add one in Profile, and sign in with it, where the card opens on signing up with a passkey (passkeys.signUp, see Passkeys). Its protected page has "Export my data", a query that uses requireRecentVerification (convex/account.ts), so the confirm-identity dialog can be seen opened by an app's own action. It sends no email: email.sender is internal.devMailbox.send (convex/devMailbox.ts), a development mailbox that keeps each message in a table, and the app's Mailbox page (http://localhost:3000/mailbox, in the header in development) shows them live. Each email is shown as it would arrive: the app's name (appName: "Example app" in shared/auth-config.ts) over a rule, a heading, the code in a box, a sign-in button and the link written out, with the plain-text part a click away.

The development mailbox works only when the app is reached on this machine: a local Convex backend, or the Node example opened at localhost. On a cloud dev deployment, or through a tunnel, it is switched off. To receive codes there, set email.sender to a real sender: an internal action of your own that calls your mail service (see Email).

Upgrading the component's tables ​

Release rules are on Upgrading. One upgrade step is specific to session rows written before the fields purgeAt and eventsUntil existed. No release has been cut, so no tool runs these steps. For a deployment holding such rows:

  1. Add purgeAt and eventsUntil as optional fields.
  2. Backfill every session row. R is authEvents.retentionSeconds.
    • eventsUntil = max(createdAt + R, the latest expiresAt of the stored events that name the session).
    • purgeAt = max(rule, eventsUntil), where rule is expiresAt + R, or min(expiresAt + R, revokedAt + R) for a revoked row.
    • Run the backfill so that it also starts the session sweep.
  3. Make both fields required.
