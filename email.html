Email: sending, and signing in by code or link ​

Evo Auth writes every email it sends, and your app delivers it. Core holds no mail account and no key: you give it one function, email.sender, and it calls that function with the finished message. Signing in with a password is on Email and password.

Signing in by an emailed code or link is not NIST-grade ​

NIST SP 800-63B-4 does not allow email for out-of-band authentication, so a code or a link sent to an address is not a NIST-grade way to sign in. It is offered because most sign-in products offer it, and because anyone who controls a mailbox can already reset a password there. If your app has to meet NIST, leave emailAuth.code and emailAuth.link off.

Switch it on ​

Every emailAuth setting defaults to false. A setting that is on needs email.sender, and validateConfig refuses the config without it.

SettingWhat it does
email.senderThe function that delivers a message. Required while any emailAuth setting is on.
email.templatesReplaces parts of the built-in messages. See Changing the words.
emailAuth.codeSign-in by a six-digit code typed in the browser that asked for it.
emailAuth.linkSign-in by a link that opens your signInUrl.
emailAuth.signUpLets a code or link make a new account.
emailAuth.passwordSign-in with a password. See Email and password.

The defaults, limits and wording of each are on the generated reference. On the Node server the sender is a function in the config:

ts
import { type EmailSender, validateConfig } from "@evo-auth/core";

// The mail service's key is read when a message is sent, not when this module loads.
const send: EmailSender = async (message, { signal }) => {
  const response = await fetch("https://mail.example.com/v1/send", {
    method: "POST",
    headers: { "Content-Type": "application/json", Authorization: `Bearer ${process.env["MAIL_API_KEY"] ?? ""}` },
    body: JSON.stringify({ to: message.to, subject: message.subject, text: message.text, html: message.html }),
    signal,
  });
  if (!response.ok) throw new Error("the mail service refused the message");
};

export default validateConfig({
  publicUrl: "https://app.example.com/auth",
  appName: "Fernhill",
  email: { sender: send },
  emailAuth: { code: true, link: true, signUp: true },
});

appName is how the emails name your app (see Configuration). Without it they show the host name of publicUrl.

On Convex ​

email.sender is a reference to one of your own actions, such as internal.email.send. Evo Auth runs it with ctx.runAction and passes the message as its arguments. The action also gets deadline, described under Limits on a send.

ts
import { v } from "convex/values";
import { internalAction } from "./_generated/server.js";

export const send = internalAction({
  args: {
    type: v.string(),
    to: v.string(),
    subject: v.string(),
    text: v.string(),
    html: v.string(),
    code: v.optional(v.string()),
    url: v.optional(v.string()),
    expiresAt: v.optional(v.number()),
    deadline: v.number(),
  },
  handler: async (_ctx, message) => {
    const response = await fetch("https://mail.example.com/v1/send", {
      method: "POST",
      headers: { "Content-Type": "application/json", Authorization: `Bearer ${process.env.MAIL_API_KEY ?? ""}` },
      body: JSON.stringify({ to: message.to, subject: message.subject, text: message.text, html: message.html }),
      signal: AbortSignal.timeout(Math.max(1, message.deadline - Date.now())),
    });
    if (!response.ok) throw new Error("the mail service refused the message");
  },
});

Convex also needs the email job, which sends the sign-in, sign-up, reset and address-change messages after the request has been answered. It is two lines. First, export the job from a file such as convex/auth.ts:

ts
import { createEmailJob } from "@evo-auth/convex";
import { validateConfig } from "@evo-auth/core";
import { components } from "./_generated/api.js";

const config = validateConfig({ publicUrl: "https://app.example.com/auth" });

export const emailJob = createEmailJob(components.evoauth, { config });

In your app, config is the shared config from the Convex guide. Second, give the job to registerRoutes in convex/http.ts:

ts
registerRoutes(http, components.evoauth, { config, emailJob: internal.auth.emailJob });

registerRoutes refuses to run without emailJob while any of emailAuth.code, emailAuth.link or emailAuth.password is on, even when only emailAuth.password is on. The error names emailJob and every setting that is on.

What Evo Auth emails ​

The sender is given one message at a time. A message holds type, to, subject, text and html, and code, url and expiresAt when it has them. expiresAt is when the code, link or invitation stops working, in milliseconds since the epoch.

typeSent whenCarries
sign_inSomeone asks for a code or link at POST {basePath}/email/sign-in/code.The code while emailAuth.code is on, and the link while emailAuth.link is on.
sign_upA password sign-up.A code always, and a link only while emailAuth.link is on.
verify_addressA signed-in person adds or changes their address: this is the message POST {basePath}/email/add sends.A code.
reset_passwordA password reset is asked for.A code.
reverifyA signed-in person asks for a code to confirm it is them.A code.
existing_account_noticeA password sign-up for an address that already has an account.A link to your sign-in page and no code.
password_disabledThe 100th failed password in a row turned a password off.A link to your sign-in page and no code.
invitationAn organisation invitation is sent to an address.The invitation link.

expiresAt is missing from existing_account_notice and password_disabled, which carry nothing that expires. Every other message has it.

The code and the link sign someone in, so your sender must not log them, store them or pass them to any service except the one that delivers the mail.

Every message has a plain-text part. The code never appears in a subject. Names that come from people (your app's name, an organisation's, an inviter's) are escaped in the HTML. The only link is the url Evo Auth gives, which is your own signInUrl or invitation page. A message loads no image, pixel or style from another site, holds no password, and never says whether an address has an account, apart from the two notices, which go to that address.

Signing in by code or link ​

With emailAuth.code or emailAuth.link on, POST {basePath}/email/sign-in/code with { "email": "..." } starts a sign-in. The address is trimmed, put in Unicode NFC and lower-cased; nothing else changes, so Ada@Example.com and ada@example.com are one address and a dot or a + part is kept. The answer is 200 { "sent": true } with a cookie that names the browser that asked.

The route never looks up the account and does the same work for every address, so a known address does not answer later than an unknown one. It only records the challenge. A job that holds nothing but the challenge's id decides what happens next, after the answer has gone:

  • For an address with an account whose user may sign in, the job makes the code, the link token or both, saves only their hashes, and calls your sender.
  • For an address with no account, with emailAuth.signUp off, the answer is the same and no mail is sent.
  • For an address with no account, with emailAuth.signUp on, the mail is sent and using the code or link makes the user and their email account. The account has no password. The user's display name is the part of the address before the @, as normalised and in lower case, and the person can change it in UserProfile's Name section.

A new code voids the earlier unused ones for the same address and purpose, so only the newest works. With only emailAuth.code on, a sign-in message carries a code and no link. With only emailAuth.link on, it carries a link and no code. In both cases the challenge holds only the hash of what was sent.

The code and the link work once and last 10 minutes. Five wrong codes void the challenge, and then the right code is refused too.

RouteMounted whileTakes
POST {basePath}/email/sign-in/codeemailAuth.code or emailAuth.link is on{ "email" }
POST {basePath}/email/verifyemailAuth.code is on, or emailAuth.password and emailAuth.signUp are both on{ "code" }
POST {basePath}/email/verify-linkemailAuth.link is on{ "token" }

/email/verify takes sign-in purposes only and ignores any bearer token: a signed-in browser cannot use it to confirm identity, which has its own route. A code or link completes only in the browser that asked for it. A link opened in another browser answers 400 invalid_request with the reason email_other_browser, so the page can tell the person to open it where they asked, and it signs nobody in. The link's page makes the person press a button, so a mail scanner that opens links cannot use it up. Every other failure of a code or a link is the same 400 invalid_request: a wrong, used, replaced, voided or expired one, or a missing cookie. An address that is not an address is 400 invalid_request with the reason email_address.

React components has the screens for all of this.

Limits ​

  • Two buckets count the emails asked for, before anything is written or sent: email_send, 10 an hour per client address, and email_recipient, 5 an hour per address, whichever client asks, so nobody can flood an inbox through your app. A full bucket answers 429 rate_limited. Both are rateLimits settings on the reference.
  • A code or link for sign-in, sign-up, a reset, a new address or confirming identity lasts 10 minutes. An invitation has its own expiry.
  • The email cookie, __Host-evo_email with the default prefix, lives 10 minutes and holds the challenge's id and a binding to the browser.

Limits on a send ​

A send is waited for at most 30 seconds. On the Node server the sender is given an AbortSignal, which is aborted at 30 seconds; pass it to your fetch. On Convex the job and the HTTP action also stop waiting at 30 seconds, but your sender action cannot be cancelled. It is passed deadline, the time in milliseconds since the epoch at which Evo Auth stops waiting, so it can set its own request timeout.

A sender that throws, or that has not answered in 30 seconds, is logged as email.send_failed, with no address, code or link, and is not retried. The answer to the person's request does not change, so the person presses "Send a new code". Retries cover the job's storage steps and never the send. A crash between saving the hashes and sending loses that one message, and "Send a new code" covers it. On Convex a scheduled action runs at most once, so a storage failure inside the job loses that message too: that is an accepted limit of that adapter.

Invitations by email ​

While email.sender is set, publicConfig says emailDelivery: true, and the invitation forms of OrganizationProfile and the admin page show an optional "Send the invitation to" address. Without a sender the field is not shown. The address is for delivery only: it is never stored, and the link works for whoever opens it. An invitation sent to an address is sent during the request, after the invitation is saved, and counts toward the same two buckets. The app's own server-side createInvitation sends no email; it gives you the link (see Invitations).

Changing the words ​

email.templates has one entry per message type, each with up to three functions, subject, text and html. A function you give replaces the part of the same name and leaves the others. It receives the message's details: type, siteName, to, code, url, expiresAt, expiresInMinutes, organizationName and inviterName.

ts
import { type EmailSender, type EmailTemplateContext, validateConfig } from "@evo-auth/core";

declare const send: EmailSender;

export default validateConfig({
  publicUrl: "https://app.example.com/auth",
  email: {
    sender: send,
    templates: { sign_in: { subject: ({ siteName }: EmailTemplateContext) => `Your ${siteName} login code` } },
  },
  emailAuth: { code: true },
});

Empty text falls back to the built-in text, and a subject that holds the code falls back to the built-in subject. An html function must escape what it puts in the HTML.

The development mailbox ​

memorySender() from @evo-auth/core/testing is a sender that sends nothing. It keeps every message in memory (messages, lastTo(address) and clear()), for tests and for the examples' development mailbox pages: http://localhost:3000/mailbox in examples/tanstack-convex and http://localhost:3010/mailbox in examples/tanstack-server.

The development mailbox works only when the app is reached on this machine: a local Convex backend, or the Node example opened at localhost. On a cloud dev deployment, or through a tunnel, it is switched off, because its messages hold live codes and sign-in links. To receive codes there, set email.sender to a real sender. See the Convex guide.

The development sender ​

devConsoleSender() from @evo-auth/core sends nothing: it prints each message's address, subject, code and link in the auth side's terminal, so a first sign-up needs no mail account. evo-auth init --stack sets it as email.sender (see the command line).

ts
import { devConsoleSender, validateConfig } from "@evo-auth/core";

export default validateConfig({
  publicUrl: "http://localhost:3000/auth",
  cookies: { devMode: true },
  providers: [],
  emailAuth: { password: true, signUp: true },
  email: { sender: devConsoleSender() },
});

It is the one sender that may log a code, so it is held to local development twice:

  • validateConfig refuses it unless cookies.devMode is on.
  • Each send refuses unless the host says the auth side is local. Core never decides this itself and never judges from anything a request carries:
    • On the Node server (evo-auth-server start, which the TanStack and Next.js server stacks run), the auth side is local once listen() has bound a loopback address such as 127.0.0.1, so the code shows in that server's terminal. An app that mounts the server's handler in its own Node server and calls only start() is never counted as local, because the configured host is not where a mounted handler is served: every send there is refused.
    • On Convex, the auth side is local when the deployment's own address, CONVEX_CLOUD_URL, is on a loopback host: a local backend, so the code shows in the npx convex dev terminal. A cloud deployment made by npx convex dev runs the same config with devMode on, and there it refuses. On a self-hosted backend, set CONVEX_CLOUD_ORIGIN before anyone reaches it from elsewhere, because left at its loopback default it counts as local.

A refused send writes nothing; Evo Auth logs email.send_failed, with no code, and the person's answer does not change. Replace it with a sender that calls your mail service before you deploy.

A host you write yourself says the auth side is local through the optional localAuthSide member of auth.handler's and auth.sendEmailChallenge's context; a sender reads it from its second argument.

What stays out ​

  • SMS.
  • A sender built into core: you always give your own.
  • Tracking of opens or clicks.
  • Links that work in any browser: a link completes only where the address was asked for.
  • Codes that last longer than 10 minutes.
